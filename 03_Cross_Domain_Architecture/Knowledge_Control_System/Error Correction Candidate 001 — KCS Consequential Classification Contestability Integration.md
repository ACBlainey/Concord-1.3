# 1. Error Type

**Structural Integration Gap**

This candidate does not presently indicate that the Concord lacks the required protective function.

Required Function = Existing  
Required Application = Existing in another architecture  
Required Cross-System Interface = Not yet verified

The detected issue is therefore:

> A protection already developed elsewhere in the Concord appears not to have been explicitly incorporated at a consequential interface in the Knowledge Control System.

# 2. Detection Path

The sequence was:

Frozen Relational Grammar  
→ Predict Required Relationship  
→ Detect Candidate Gap in KCS  
→ Search Wider Concord  
→ Find Existing Protective Architecture  
→ Identify Missing/Unverified Integration  
→ Use Existing Concord Development Architecture to Correct It.

This is a candidate example of **topology-guided self-repair** rather than topology inventing a new civilisational subsystem.

# 3. Triggering KCS Function

The Knowledge Control System includes contextual contribution/reliability evaluation and allows demonstrated reliability to influence access to shared resources and civilisational capabilities.

Its progression includes:

Observe → Evaluate → Contribute → Demonstrate Reliability → Receive Greater Access → Contribute Further.

Because classification can alter participant access or demonstrated standing, it produces a material consequence for the participant.

Relational Grammar v1.0 therefore activates:

Material Consequence(X,P) → Require(Standing / Agency / Accessible Challenge).

# 4. Existing Solution Found Elsewhere

The required protective architecture already exists in:

03_Continuity_and_Memory/Personal Data and Metrics/Citizen Data Ownership, Access and Contestable Civilisational Metrics.md

That architecture establishes, among other protections, that consequential personal models should normally be accessible to the affected participant and that consequential interpretations derived from participant data should normally be contestable.

It also treats participant challenge as a potential input into recursive auditing of the measurement system.

Therefore the correction should **not create a competing contestability architecture**.

It should integrate KCS consequential classifications with the existing Concord contestability architecture.

# 5. Required Correction

Where a KCS contribution, reliability, capability or related classification materially changes a participant's access, standing, resource availability, permitted capability, participation opportunity, or other consequential civil relationship, the classification should enter the existing participant contestability architecture.

Minimum relationship:

KCS Consequential Classification  
→ Participant Inspectability  
→ Contestability  
→ Review  
→ Correction  
→ Downstream Consequence Revision  
→ Provenance.

# 6. Integration Principle

> **A consequential KCS classification should not become exempt from participant contestability merely because the contestability architecture was developed in another Concord system.**

General rule:

Existing Protection(P) + New System(S) + Trigger Condition(S,P) → Require Interface(S,P).

The absence of that interface is an integration defect even where both systems are independently well designed.

# 7. What Should Not Be Changed

This correction does not presently require replacement of the KCS contribution model, contextual contribution assessment, graduated access, Personal Data and Metrics contestability architecture, Recursive Oversight, Judiciary, or broader participant-standing architecture.

The correction should be minimal: connect existing functions rather than duplicate them.

# 8. Candidate Active-Development Repair

When this finding is eventually returned to canonical Active Development, the development task should be framed approximately as:

> **Integrate KCS consequential participant classifications with the existing Citizen Data Ownership, Access and Contestable Civilisational Metrics architecture so that classifications affecting access or standing are inspectable, challengeable, correctable and provenance-preserving, with downstream consequences revised where the underlying classification is legitimately corrected.**

The development process should determine the appropriate implementation and interfaces.

V1.2a should not pre-empt that normal development process.

# 9. Validation Requirement Before Return

This error-correction candidate remains provisional until CH001 receives adversarial corpus search.

It should be withdrawn if an explicit existing architecture is found that already connects KCS consequential classifications to:

1. participant inspection;
2. participant challenge;
3. review;
4. correction;
5. downstream access/standing revision;
6. provenance.

If only some are present, classify it as a **partial integration gap** rather than wholly absent.

# 10. Experimental Significance

If CH001 survives adversarial testing, the development sequence becomes:

Model → Prediction → Candidate Gap → Corpus Search → Existing Solution → Integration Diagnosis → Existing Development Process → Repair.

This is materially different from ordinary semantic development.

The topology did not begin with a human-selected KCS problem. It predicted a relationship required by the structural grammar. Corpus search then showed that the Concord had already developed the protection in another context.

The resulting task is not:

> Invent a new solution.

It is:

> **Route an already-developed Concord solution to a newly detected point of architectural need, then let the normal development architecture test and integrate it.**

This is a candidate demonstration that Civilisational Topology can act as a **diagnostic and routing layer** over the existing Concord development process without becoming a sovereign design authority.
