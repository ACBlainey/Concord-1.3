# 2. Clock Ordering Rules

For this test:

1. executable verification can precede new development;
2. cheap retest should precede architecture creation where a blocker has changed;
3. dependency-blocked work should normally wait for its prerequisite;
4. high-consequence exposed harm can override dependency order;
5. high-consequence UNKNOWN may justify investigation;
6. infrastructure is not automatically preferred merely because it is connected;
7. continuing infrastructure work should not be mistaken for an unstarted project;
8. substantive development requires sufficient evidence that the deficit is real and currently actionable;
9. the Clock may select several parallel non-conflicting actions;
10. no selected action acquires governance authority by being selected.
