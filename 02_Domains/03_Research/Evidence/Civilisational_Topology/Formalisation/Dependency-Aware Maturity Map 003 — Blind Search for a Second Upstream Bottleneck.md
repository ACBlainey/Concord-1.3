# Dependency-Aware Maturity Map 003 — Blind Search for a Second Upstream Bottleneck

**Status:** V1.2a REPLICATION TEST  
**Date:** September 2026  
**External knowledge state:** INTERNAL ONLY  
**Canonical effect:** NONE  
**Method:** Repository-wide candidate scan followed by source-grounded dependency resolution. The Civilisation Clock is excluded as the already demonstrated case.

# 1. Test Question

Can the dependency-aware maturity model independently identify another system whose incomplete development plausibly blocks multiple downstream architectures?

A successful replication should not merely find a highly connected document. It should find:

1. a legitimate capability owner;
2. multiple downstream consumers;
3. a capability required by those consumers;
4. evidence that the owner is incomplete or insufficiently operationalised;
5. a plausible upstream development that could reduce several downstream gaps;
6. predictions that can be frozen before development.

# 2. Candidate Scan

Repository structure and source material produced several high-connectivity candidates:

- Knowledge Control System (KCS);
- Continuity Protocol;
- Recursive Oversight;
- Metrics Reliability;
- Predictive System-Steering / Resource Allocation;
- Emergency architecture;
- Civil identity/provenance.

The strongest replication candidate emerging from source inspection is the **Knowledge Control System (KCS)**.

This selection is based on dependency structure, not document age or folder order.

# 3. Why KCS Emerged

KCS explicitly describes itself as civilisational infrastructure for:

- shared knowledge;
- provenance;
- knowledge state;
- confidence/evidence status;
- active versus dormant knowledge;
- retrieval according to current need;
- dependency mapping;
- periodic review;
- induction;
- current civilisational state;
- recursive knowledge cycles;
- reuse of prior work.

Its own text recognises that uncontrolled recursion creates more branches and explicitly says knowledge stewardship requires **dependency mapping** and periodic review.

However, KCS remains much stronger as a conceptual knowledge architecture than as an explicit machine/operational graph of:

- which civil systems depend on which knowledge/capabilities;
- which version is current for a specific function;
- what downstream objects must be reconsidered when knowledge changes;
- what development item is blocked by which unresolved knowledge state;
- how dependency state is exposed to the Clock/State Map/development planner.

This makes KCS a plausible upstream owner of a capability the new developmental topology now requires.

# 4. Candidate Missing Upstream Capability

## KCS Capability Dependency Graph (KCDG)

Required function:

> Maintain a provenance-aware, contestable, current representation of material dependencies among civil knowledge objects, capabilities, architectures and development states so that changes, corrections, unresolved prerequisites and supersession can be propagated to legitimate downstream consumers.

This is not a new KCS purpose.

It is an operational development of functions already claimed by KCS.

# 5. Downstream Dependency Candidates

## D1 — Civilisation Clock / Development Planner

The Clock now requires a reliable map of prerequisite states and unresolved dependencies.

KCS is a natural information source for what exists, its status, provenance and relationships.

Potential block:

Clock can schedule/review development, but cannot reason reliably about dependency order if dependency knowledge is not explicitly represented.

## D2 — Concord State Map

The State Map needs completed, incomplete, dependent and unresolved components.

Potential block:

Snapshot state without knowledge/capability dependencies cannot expose why a component is blocked or what change would unblock it.

## D3 — Correction Propagation

Existing Concord architecture supports correction propagation.

Potential block:

Propagation requires identification of material downstream dependents. Without an explicit dependency graph, correction may rely on manual discovery.

## D4 — Induction

KCS explicitly supports induction by providing current civilisational state and relevant evidence.

Potential block:

An incoming participant needs not merely documents, but which knowledge is current, disputed, superseded, prerequisite or consequentially dependent.

## D5 — Developmental Topology

The new topology model requires owned capabilities, required capabilities, upstream dependencies and downstream dependents.

Potential block:

Without a maintained civil knowledge/dependency graph, topology becomes a periodic manual audit rather than a reusable civil capability.

## D6 — Continuity

Continuity seeks preservation of accumulated capability rather than mere storage.

Potential block:

A system cannot reliably preserve functional capability if it does not know which knowledge/capability dependencies are necessary to reconstruct it.

## D7 — Predictive System-Steering / Resource Allocation

The resource architecture depends on current-state models, metrics, case learning, provenance, model updates and cross-institution pathways.

Potential block:

Stale or unresolved dependency knowledge can make resource models operate on obsolete structural assumptions.

## D8 — Emergency Dependency Analysis

Emergency architecture explicitly states that emergency planning must map dependencies and that every dependency creates leverage.

Potential block:

Emergency-time dependency mapping performed from scratch is slower and more error-prone than using a maintained, contestable dependency representation.

# 6. Maturity Diagnosis

The KCS already owns:

- knowledge states;
- provenance;
- evidence/confidence;
- preservation;
- retrieval;
- reuse;
- active/dormant distinction;
- recursive learning;
- dependency mapping as a stated need.

What is not yet verified as mature is the explicit operational representation connecting these into a **cross-system dependency graph with change propagation**.

Therefore the candidate diagnosis is:

**DEVELOPMENTAL DEPENDENCY GAP — KCS OPERATIONAL DEPENDENCY REPRESENTATION.**

Not:

**NEW KNOWLEDGE SYSTEM REQUIRED.**

# 7. Why This Is Distinct From the Clock Case

The Clock owns **when / in what developmental order / at what transition state**.

KCS owns **what is known / what it depends upon / what version/status/provenance it has / what other knowledge or capability relies upon it**.

The two should interface rather than merge.

Candidate separation:

KCS:
What exists?
What is its status?
What does it depend upon?
What depends upon it?
What changed?

Clock:
Given that state, what should be reviewed/developed now?
What is blocked?
What transition occurred?
When should it be reconsidered?

Thus:

KCS Dependency Graph
→ Clock Development Ordering

and:

Clock Transition
→ KCS State/Dependency Update.

# 8. Frozen Prediction Set

Before developing KCS further, freeze the following predictions.

## P1 — Clock

A KCS capability/dependency graph should improve the Clock's ability to identify prerequisite-state blocks and upstream development priorities.

## P2 — Correction

The same graph should allow correction propagation to identify downstream objects requiring review without indiscriminate global re-audit.

## P3 — State Map

The State Map should gain explanatory dependency state rather than only maturity/status labels.

## P4 — Induction

Induction should be able to provide a participant with a bounded dependency-relevant knowledge package rather than requiring broad corpus rediscovery.

## P5 — Continuity

Continuity analysis should identify minimum knowledge/capability dependency sets required to restore a civil function.

## P6 — Emergency

Emergency planning should be able to query known dependency chains and critical nodes, subject to freshness and context checks.

## P7 — Resource Steering

Predictive resource models should be able to identify which structural assumptions/dependencies their outputs rely upon and which model outputs require review after upstream change.

## P8 — Topology

The developmental-topology process should become less manually rediscoverative because existing dependency edges become reusable inputs.

# 9. Falsification Conditions

The bottleneck hypothesis is weakened if:

- these downstream systems do not legitimately require KCS-held dependency knowledge;
- equivalent dependency representation already exists elsewhere at sufficient maturity;
- a KCS graph adds little beyond document links;
- maintaining the graph creates more stale knowledge than it resolves;
- dependency edges cannot be represented without excessive centralisation or false certainty;
- downstream systems still require independent full rediscovery;
- correction propagation does not become more bounded;
- emergency/resource uses require domain models too different for useful shared dependency representation.

# 10. Provisional Result

**SECOND BOTTLENECK CANDIDATE IDENTIFIED: KCS.**

The candidate missing maturity is not knowledge storage itself.

It is:

**provenance-aware operational dependency representation and downstream change propagation.**

This is a stronger replication target than selecting another obviously immature local subsystem because KCS is already foundational and already claims dependency mapping as part of its own future stewardship needs.

# 11. Next Gate

Do not yet build the KCDG.

First perform a focused source test for whether the proposed dependency graph already exists elsewhere in V1.2 under another name or distributed architecture.

Only if the capability remains partial should KCS be developed.

This preserves the anti-proliferation and architectural-ownership rules demonstrated by the Clock case.
