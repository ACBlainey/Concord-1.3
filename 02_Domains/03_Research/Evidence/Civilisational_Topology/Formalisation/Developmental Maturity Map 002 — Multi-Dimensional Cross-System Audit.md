# 1. Purpose

Map 001 tested one relational family: consequential participant classification and contestability.

Map 002 asks whether uneven development remains visible when the analysis is widened to multiple architectural dimensions.

This is not a document-quality ranking and not a demand that every system contain every feature.

Every apparent absence must first pass an **applicability test**.

# 2. Relational Dimensions

The following dimensions are drawn from the frozen relational grammar and prior topology work:

**D1 — Bounded Scope**  
Does the architecture define or constrain the scope of its function, authority or intervention where scope matters?

**D2 — Legitimate / Non-Self-Justifying Authority**  
Where power or authority exists, is its legitimate basis distinguished from mere capability, status or self-assertion?

**D3 — Temporal Revision / Exit / Termination**  
Where functions, permissions, interventions or participation can change over time, is contraction, exit, sunset, termination or re-justification represented?

**D4 — Contestability / Correction / Repair**  
Where consequential error can occur, is there a path to challenge, correction, remedy or revision?

**D5 — Participant Standing / Agency**  
Where participants are affected, is their agency, rights, standing, voice or relevant role preserved?

**D6 — Asymmetry / Anti-Capture Compensation**  
Where material asymmetry exists, are capture, domination, concentration or vulnerability addressed?

**D7 — Effective Access**  
Where formal availability is insufficient, does the system account for practical accessibility, barriers, interface or translation?

**D8 — Function-over-Form / Replaceability**  
Where institutional or implementation form can become stale, is the required function distinguished from its current implementation and can the form adapt or be replaced?

**D9 — Recursive Review**  
Can the system, its oversight, or its implementation itself be reviewed/audited where appropriate?

**D10 — Provenance / Learning**  
Does the architecture preserve enough reasoning/history/provenance to support learning and later correction?

Statuses:

- **PRESENT**
- **PARTIAL**
- **NOT ESTABLISHED**
- **N/A / NOT TRIGGERED**

# 6. Source-Grounded Findings

## 6.1 Judiciary V2 — high recursive maturity

Judiciary V2 is a useful mature control.

It explicitly develops:

- constitutional and jurisdictional boundaries;
- challenge to public authority;
- rights and legal standing;
- remedies and appeals;
- temporary intervention;
- minority-reasoning preservation;
- capture analysis;
- meaningful practical accessibility;
- implementation variables versus constitutional invariants;
- institutional replacement;
- recursive review of judicial architecture;
- preservation of reasoning and provenance.

Particularly important is the explicit distinction:

> review the system without commanding the judgement.

This is exactly the kind of meta-boundary predicted by:

MetaAuthority -> MetaConstraint.

The Judiciary therefore shows that an older foundational domain can become highly mature through extensive recursive reconstruction. This is evidence against a simplistic:

old = immature

model.

It instead supports:

developmental maturity = age + recursive redevelopment + later learning applied.

## 6.2 Constitutional Emergency V2 — mature bounded exceptional-power architecture

Emergency architecture strongly represents:

- defined bounds;
- proportionality;
- constitutional derivation of emergency authority;
- temporary powers;
- time limitation;
- review;
- anti-permanence safeguards;
- correction and restoration;
- provenance and later scrutiny.

This again demonstrates that a domain exposed to repeated recursive development can contain later safeguards even where the underlying civil problem is old.

## 6.3 Recursive Oversight V2 — explicit recursive architecture

Recursive Oversight is a particularly strong control because its subject is correction itself.

It states that consequential authority and oversight remain subject to review, challenge and correction.

It explicitly guards against:

- oversight capture;
- correction mechanisms becoming sovereign;
- inaccessible challenge;
- permanent immunity;
- institutional indispensability;
- hidden implementation amendment.

It preserves:

Detection
-> Diagnosis
-> Containment
-> Correction
-> Recording
-> Learning
-> Architectural Revision.

It also explicitly develops institutional replacement and succession.

This system is close to a direct implementation of several dimensions in the current topology grammar.

Civil Contact Points strongly develops:

However, in the present source pass it does not comparably develop:

This does **not** yet establish three defects.

This is exactly the intended use of the maturity map: generate questions, not verdicts.

## 6.5 Reality Trees — domain-specific N/A values matter

Reality Trees demonstrates why maturity cannot be a raw feature count.

It strongly contains:

- bounded progression from speculation to real-world branch;
- changing evidential weights;
- challenge/refinement/discard;
- isolated experimentation;
- local failure producing learning;
- provenance and rationale.

But participant standing, authority legitimacy, anti-capture and practical civil access are not obviously triggered by the reasoning-method function itself.

Marking these as missing would falsely classify a specialised epistemic method as immature merely because it is not a government.

The correct model therefore requires:

Maturity(S) = completeness of **applicable** relations,

not:

Maturity(S) = number of universal boxes ticked.

Reality Trees does, however, generate a legitimate question around D9:

> Is the method itself recursively evaluated for systematic failure modes, rather than only allowing branches within the method to be challenged?

That remains a candidate question, not a gap finding.

# 8. Strong Support for the User-Supplied Development History

The observed structure is consistent with the stated development process:

- recursive redevelopment has historically been manually directed;
- areas remembered for further work have been revisited;
- no exhaustive formal propagation queue existed;
- newer lessons could therefore be applied deeply to some older systems while remaining unapplied elsewhere.

The Judiciary is especially important here.

It demonstrates that an older domain can sit near the mature end of the current map after extensive reconstruction.

Thus the temporal hypothesis should be refined from:

Older systems have more gaps

to:

Systems that have received fewer later recursive passes are more likely to retain earlier architectural states.

Formally:

GapLikelihood(S)
~ f(
  LaterLearningNotApplied(S),
  RecursivePassDeficit(S),
  InterfaceComplexity(S)
)

rather than simply:

GapLikelihood(S) ~ Age(S).

# 9. Emerging Developmental Coordinates

A single maturity number would destroy useful information.

A better representation is a vector:

M(S) =
[D1,D2,D3,D4,D5,D6,D7,D8,D9,D10]

with N/A preserved.

This allows two systems to be equally developed in different ways and allows the topology to identify exactly what kind of recursive work is pending.

For example:

Civil Contact Points:
strong in participant/access/exit/provenance;
candidate weakness in correction/asymmetry/recursive review.

Multisubstrate Economic Participation:
strong in authority distinction/standing/exit/provenance;
candidate weakness in asymmetry/effective access/recursive correction.

The development queue can therefore be generated from vectors rather than subjective rankings.

# 10. First Candidate Levelling Rule

A system is ready to be treated as audited at abstraction level L_n only when:

For every relation R_i in the frozen L_n grammar:

Trigger(S,R_i)
→
{Present, Distributed-and-Verified, Legitimately N/A, or Explicitly Accepted Development Candidate}.

Unknown relations remain visible.

This yields:

L_n* ≠ perfect system.

Instead:

L_n* = system whose applicable L_n relations have been explicitly examined and dispositioned.

This is much more achievable and falsifiable.

# 11. Implication for the Periodic Recursion Process

The map now suggests a concrete queue structure.

For every new abstract lesson L:

1. define Trigger(L);
2. query all mapped systems;
3. select systems satisfying Trigger(L);
4. inspect current relation state;
5. classify:
   - already present;
   - distributed existing function;
   - legitimate domain variation;
   - representation gap;
   - temporal propagation candidate;
   - genuine development candidate;
6. route only unresolved applicable cases to Active Development;
7. update maturity vector after review.

Thus one new solution can be tested against the entire architecture without blindly copying it everywhere.
