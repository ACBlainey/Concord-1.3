# 4. B01 — Clock + CRSTL

The Clock already owned:

State assessment
→ priority selection
→ task allocation
→ work
→ independent evaluation
→ state update
→ repeat.

It also owned dependency-aware priority, prerequisite-state deferral, consolidation, temporal review and developmental state.

CRSTL added explicit consequential state transitions, branch-aware state, consequence-relative ordering, uncertainty, correction/supersession and domain-bounded interfaces.

Therefore AL0–AL5 are strongly represented.

At AL6, however, the Clock explicitly interfaces with KMDI for persistent dependency knowledge.

That is not a failure.

It is correct architectural separation.

But cumulative AL completeness must ask whether AL6 requirements apply to the Clock itself or are legitimately satisfied through a civil interface.

This exposes a new issue in the ladder:

**system-level AL cannot always be measured as self-contained possession of every later capability.**

A system may satisfy a layer through a legitimate dependency on another system.

For this audit, Clock is provisionally recorded as:

**AL5 apparent, with AL6 supplied externally through KMDI interface.**

This classification should be revisited under an interface-satisfaction rule.

# 9. B06 — Reality Trees N/A Stress Test

Reality Trees is intentionally a portable cognitive/experimental method, not a governance institution.

This means many authority-specific requirements are legitimately N/A.

Examples:

- participant political standing — generally N/A to the method itself;
- authority termination — N/A where the method exercises no authority;
- institutional replacement — N/A;
- civil enforcement — N/A.

Yet the method still has applicable abstraction requirements.

AL0 is strong:

- purpose;
- method;
- scope;
- evidence relationship;
- explicit uncertainty.

AL1 is largely satisfied through epistemic boundedness:

a branch is not truth;
confidence is not certainty;
exploration is not endorsement;
Reality remains final arbiter.

AL2 is strong:

branches are tested, refined, retained or discarded as evidence changes.

AL3 is substantially present:

failed branches remain information;
provenance/assumptions/method/results should be retained;
evidence is integrated into future reasoning.

AL4 is harder.

Reality Trees can expose alternatives and dependencies within a tree, but it is not presently a cross-system capability-ownership/development-routing method.

Some AL4 requirements are N/A to a portable cognitive module; others may become applicable when Reality Trees are used for civilisational experimentation.

Because applicability changes by deployment context, the conservative classification is:

**AL3 apparent, AL4 applicability partly conditional.**

This supports the frozen N/A prediction and exposes the need for **context-sensitive applicability**.

# 10. Major Methodological Discovery 1 — Interface Satisfaction

The audit exposes a problem not visible before measurement.

Suppose:

Clock requires persistent dependency knowledge.

KMDI legitimately owns persistent dependency knowledge.

Clock has a defined interface to KMDI.

If AL6 requires every system to internally implement KMDI-like functionality, the ladder would reward duplication and violate Developmental Topology.

Therefore:

**Layer completeness must permit legitimate interface satisfaction.**

Candidate rule:

Requirement(S,r)
may be satisfied by:

1. INTERNAL — S legitimately owns and implements r;
2. INTERFACE — another legitimate owner O implements r and S has a sufficient bounded interface to O;
3. N/A — trigger does not apply.

Thus:

Complete(S,n)
does not require
DuplicateEveryCivilCapabilityInside(S).

This rule must be frozen before broad audit.

# 11. Major Methodological Discovery 2 — Context-Sensitive Applicability

Reality Trees exposes a second issue.

A portable method may have different AL applicability depending on use.

Reality Trees used for private hypothesis exploration does not exercise civil authority.

Reality Trees used to structure high-consequence civil experimentation may acquire additional participant/provenance/review requirements.

Therefore applicability is not always a property of the artefact alone.

It may be:

Applicability(requirement)
= f(system, deployment context, consequence class).

The State Map should therefore avoid one context-free AL where deployment materially changes triggered requirements.

- exposes the need for interface satisfaction instead of rewarding duplicated architecture.

The measuring system is therefore already correcting itself under use.

# 14. New Frozen Candidate Rules for Formalisation

Before Audit 003, formalise:

## Interface Satisfaction Rule

An applicable requirement may be satisfied through a legitimate external owner only if:

- owner is identifiable;
- capability is actually present;
- interface is explicit enough for the required function;
- scope/authority remains bounded;
- dependency is represented;
- failure/unavailability is not silently treated as local satisfaction;
- correction/review can propagate appropriately.

## Context Applicability Rule

Where requirement triggers vary by deployment:

AL classification must state the audited deployment context.

No context-specific N/A may be universalised without justification.
