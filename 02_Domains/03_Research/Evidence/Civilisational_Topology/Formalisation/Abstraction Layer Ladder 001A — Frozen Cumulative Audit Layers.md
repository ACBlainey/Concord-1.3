# Abstraction Layer Ladder 001A — Frozen Cumulative Audit Layers

**Status:** V1.2a FROZEN PRE-AUDIT LADDER  
**Date:** September 2026  
**Canonical effect:** NONE  
**External knowledge state:** INTERNAL ONLY  
**Derived from:** Abstraction Layer Derivation 001

# 1. Purpose

This file freezes the first cumulative abstraction-layer ladder before any broad system-level AL assignment.

The ladder is an audit structure, not a claim that Concord history occurred in perfectly discrete stages.

The underlying abstraction structure is partially ordered.

The ladder groups those relations into cumulative levels so systems and the wider architecture can be compared consistently.

# 2. AL0 — Identifiable Architecture

A system is AL0-complete when its basic architectural object is sufficiently identifiable to audit.

Applicable requirements:

- purpose/need is identifiable;
- function is identifiable;
- system/domain boundary is sufficiently identifiable;
- inputs/outputs or material consequences are sufficiently identifiable;
- provenance/source basis exists sufficiently for audit.

AL0 means **auditable architecture exists**.

It does not imply adequate safeguards.

# 3. AL1 — Bounded and Consequence-Aware Function

AL1 adds constraints around what the system may do and whom it affects.

Applicable requirements:

- legitimate function distinguished from mere capability;
- scope is bounded;
- scope expansion requires renewed justification;
- materially affected participants are identifiable;
- participant standing/agency/challenge exists where triggered;
- material asymmetry triggers anti-domination/stronger review where applicable.

AL1 asks:

> Is the function bounded and are its consequential relationships recognised?

# 4. AL2 — Correctable and Temporally Revisable Architecture

AL2 adds correction through time.

Applicable requirements:

- review path;
- correction/repair;
- revision;
- termination/contraction/re-justification where applicable;
- continuity preserves necessary function without making one implementation sovereign;
- replacement/exit path where applicable;
- escalation does not silently create permanent authority.

AL2 asks:

> Can this architecture discover and act upon the fact that its present form is wrong, excessive, obsolete or failed?

# 5. AL3 — Provenance, Learning and Recursive Constraint

AL3 adds persistent learning and self-application.

Applicable requirements:

- material decisions/corrections preserve provenance;
- learning propagates from outcomes/failures;
- supersession does not erase relevant history;
- meta-functions are subject to relevant constraints they impose;
- oversight/measurement/review architecture is itself reviewable;
- implementation cannot silently manufacture new authority.

AL3 asks:

> Does correction become durable learning, including when the system itself performs meta-functions?

# 6. AL4 — Cross-System Ownership and Developmental Dependency

AL4 moves beyond local system completeness.

Applicable requirements:

- required capabilities have identifiable legitimate owners where possible;
- local gaps are tested for upstream ownership before local invention;
- structural, integration and developmental dependency gaps are distinguished;
- requirements can propagate upstream;
- developed capabilities can propagate downstream;
- interface maturity is distinguishable from internal maturity;
- shared upstream bottlenecks can be identified.

AL4 asks:

> Does the system understand that some of its apparent gaps are properties of the wider architecture rather than itself?

# 7. AL5 — Explicit Civil State and Consequence-Relative Transition

AL5 makes changing civil state an explicit architectural object.

Applicable requirements:

- meaningful state transitions are representable;
- prior and current state can be distinguished;
- correction/supersession is representable;
- legitimate concurrency/branching can be represented where relevant;
- temporal evidence is not confused with universal causal/material order;
- unknown-but-material ordering can remain explicit;
- consequential state change can be distinguished from irrelevant change.

AL5 asks:

> Can the architecture represent how civil state changes without forcing false temporal simplicity?

# 8. AL6 — Persistent Dependency Knowledge and Propagation

AL6 makes material dependency relations persistent, provenance-aware knowledge.

Applicable requirements:

- material dependency edges can be recorded;
- dependency type/scope can be represented;
- provenance and epistemic state accompany consequential edges;
- downstream exposure can be discovered;
- upstream correction can trigger bounded downstream review;
- dependency history/supersession is preserved;
- unknown/missing edges do not imply absence;
- circular/recursive dependencies can remain visible;
- criticality does not create sovereignty.

AL6 asks:

> Can the civilisation remember and update why systems depend upon one another?

# 9. AL7 — Current Civil-State Synthesis

AL7 integrates distributed state into a reusable current representation.

Applicable requirements:

- current unit identity and ownership;
- capabilities and unresolved state;
- internal and interface maturity kept distinct;
- upstream blockers/downstream dependents;
- validation/evidence state;
- provenance;
- uncertainty/dispute;
- freshness/staleness;
- temporal references/history;
- bounded views for legitimate consumers;
- partial-map humility;
- correction/contestability of the map itself.

AL7 asks:

> Can civilisation answer, with bounded uncertainty: “Where are we now?”

# 10. AL8 — Abstraction-Depth Levelling and Development Frontier

AL8 adds explicit recursive-development depth.

Applicable requirements:

- version is separated from abstraction level;
- abstraction requirements are frozen before assignment;
- applicable requirements are classified Satisfied / Unsatisfied / N/A / Unknown / Disputed;
- contiguous completeness is enforced;
- apparent and verified AL are distinguished;
- next unmet layer is explicit;
- floor-defining systems are identifiable;
- frontier deficits can be traced to dependency owners;
- civilisational floor can be calculated over an explicit required-system set;
- downward revision remains possible.

AL8 asks:

> Can civilisation determine how deeply later architectural learning has propagated through its required systems?

# 11. AL9 — Recursive Self-Development of the Development Architecture

AL9 applies the development process to itself.

Applicable requirements:

- development mechanism is represented as an auditable system;
- its own gaps can be detected through use;
- those gaps can enter the same source-resolution/development process;
- changes to the development mechanism preserve provenance;
- predictions are frozen where possible before self-modification;
- self-generated complexity must demonstrate useful developmental consequences;
- external/independent review remains possible;
- self-development does not imply self-legitimating authority.

AL9 asks:

> Can the civilisation improve the mechanism by which it decides how to improve, without exempting that mechanism from correction?

# 12. Cumulative Rule

AL_n includes every applicable requirement from AL0 through AL_n.

Therefore a system cannot be AL7-complete while retaining an unresolved applicable AL2 requirement.

Higher-layer feature exposure is recorded separately.

# 13. N/A Rule

A requirement may be N/A only when its trigger condition does not apply to the system.

Examples:

- participant challenge may be N/A to a purely epistemic reasoning method with no material participant consequence;
- authority termination may be N/A where no authority is exercised;
- cross-system transition ordering may be N/A to a static reference object.

N/A requires rationale and remains reviewable.

# 14. Experimental Boundary

AL0–AL8 are derived from architectural relations already developed and used in the current experiment.

AL9 is more weakly evidenced.

It is included because Recursive Self-Development Event 001 supplies one observed architectural-level instance, but AL9 should be treated as **experimental** until repeated.

# 15. No Universal-Civilisation Claim

This ladder is initially a **Concord-derived civilisational architecture ladder**.

It must not yet be represented as a universal scale for all possible civilisations.

Cross-civilisation applicability would require separate testing.

# 16. Frozen First-Audit Predictions

Before assigning systems, freeze these predictions.

**P-AL1 — Version mismatch:** version numbers will not reliably predict AL.

**P-AL2 — Uneven landscape:** required Concord systems will occupy different apparent ALs.

**P-AL3 — Later-feature exposure:** some systems will contain features from layers above their contiguous complete AL.

**P-AL4 — Dependency blocking:** at least some next-layer deficits will be blocked by upstream systems rather than local absence.

**P-AL5 — Mature reconstructed systems:** some older-origin systems that received substantial recursive redevelopment will score above less-recursively-developed newer/other systems.

**P-AL6 — N/A necessity:** specialised systems will require legitimate N/A classifications to avoid false low-AL results.

**P-AL7 — Current floor uncertainty:** the first bounded audit will probably be able to establish only an apparent/domain floor, not a verified whole-Concord civilisational level.

# 17. First Audit Rule

The first audit must:

1. sample systems from different domains/development histories;
2. record version independently;
3. classify each AL requirement using source evidence;
4. stop contiguous AL at the first unresolved applicable layer;
5. record higher feature exposure separately;
6. preserve Unknown rather than infer absence;
7. source-resolve any candidate floor-defining deficit before treating it as real.

The ladder is now frozen for the first audit.
