**Status:** V1.2a CANDIDATE OUTPUT FOR HUMAN-REVIEWED INTEGRATION INTO V1.2  
**Date:** September 2026  
**Canonical effect:** NONE until explicitly reviewed and integrated  
**Origin:** V1.2a topology/formalisation experiment  
**Purpose:** Define what is ready to leave the experimental environment, what must remain experimental, and the development route by which canonical Concord V1.2 can be brought toward approximately level architectural maturity.

# 1. Why This Package Exists

V1.2a began as a counterfactual test: whether a civilisation generated from the independently derived U1-U8 ethical kernel would substantially reproduce the architecture already present in Concord V1.2.

The experiment expanded into a more consequential discovery.

It produced a method for asking:

> What civilisational functions should exist, which of them are already present, how mature are they, what depends upon them, which incomplete upstream system is blocking other systems, and therefore what should be developed next?

That capability should not remain merely an experimental research procedure if it survives final review.

It is a candidate civilisational architecture for **recursive, non-sovereign developmental levelling**.

The objective is not to make every Concord document the same length or every system equally complex.

The objective is:

> **Bring every required civilisational function to sufficient maturity for its consequence, while preventing immature upstream systems from silently limiting the rest of the civilisation.**

# 2. What the Experiment Established

The V1.2a work presently supports the following provisional findings.

## 2.1 A bounded candidate topology exists

The current hierarchy is:

- L0 — root civilisational functions;
- L1 — cross-system coordination requirements;
- L2 — whole-civilisation coordination requirements;
- L3 — meta-coherence, deep-change, boundary and self-model requirements.

A deliberate L4 search produced no irreducible new node.

Therefore:

[
T = L_0 cup L_1 cup L_2 cup L_3
]

is the current bounded candidate topology.

This is not proof of completeness. L4 remains reopenable if a later irreducible function is demonstrated.

## 2.2 Presence and maturity are different

The tests found no demonstrated empty node through L3 when the current developmental-topology system itself is counted in the experimental civilisation.

But many nodes are unevenly mature.

Therefore:

[
NodePresence 
eq NodeMaturity.
]

## 2.3 Document maturity and civilisational maturity are different

A long or frequently revised paper may represent an immature civil function.

A short interface may satisfy a mature function by connecting legitimate owners.

Therefore:

[
DocumentDevelopment 
eq ArchitecturalDevelopment.
]

## 2.4 Local gaps may be supplied elsewhere

A missing capability in one document or system is not automatically a civilisational gap.

Before declaring absence:

[
LocalDeficit
ightarrow SourceResolution
ightarrow OwnershipTest
ightarrow InterfaceTest
ightarrow GapClassification.
]

This operationalises the Evaluation-Space Completeness Problem.

## 2.5 Development order can be dependency-derived

The Clock, KCS and State Map tests showed that a downstream deficit may be caused by an immature upstream owner.

Therefore:

[
DownstreamWeakness

otRightarrow
DevelopDownstreamFirst.
]

Instead:

[
Weakness
ightarrow RequiredCapability
ightarrow LegitimateOwner
ightarrow UpstreamDependencies
ightarrow DevelopmentTarget.
]

# 3. Candidate Canonical System

Provisional system name:

# **Civilisational Developmental Topology and Levelling Architecture**

Short name:

**CDTLA**

The name is descriptive rather than constitutional branding and may be changed during integration.

Its function is to maintain a corrigible representation of required civilisational functions and their developmental relationships so that the civilisation can identify consequential maturity deficits and develop them in a rational dependency-aware order.

# 4. Core Constitutional Boundary

CDTLA is not a government.

It does not possess authority merely because it identifies a bottleneck.

It does not determine ethics.

It does not automatically allocate resources.

It does not decide constitutional adoption.

It does not define reality merely by representing it.

Its outputs are evidence for legitimate development and governance processes.

# 5. Core Components

## C1 — Ethical/Constitutional Constraint Layer

Defines the ethical constraints against which civil functions and developments are evaluated.

The topology does not replace the constitutional core.

## C2 — Required-Function Topology

Represents L0-L3 required civilisational functions and their relationships.

## C3 — Ownership and Interface Map

Records which system legitimately owns which function and where capability is supplied through interfaces rather than duplication.

## C4 — Dependency Graph

Represents material prerequisites, downstream dependents, alternatives, shared upstream exposure and failure propagation.

## C5 — Maturity / Abstraction State

Records whether a required function is present, partial, interface-satisfied, dependency-blocked, unknown or disputed, and how far it is developed for the relevant consequence.

## C6 — Current Civil State Map

Produces a provenance-aware snapshot of the civilisation's current architectural state.

## C7 — Civilisation Clock / Transition Layer

Represents developmental state transitions, prerequisite ordering, legitimate concurrency, branches, correction and review periods.

## C8 — Gap and Bottleneck Resolver

Distinguishes:

- true architectural absence;
- developmental gap;
- integration/interface gap;
- dependency-blocked function;
- representation gap;
- unknown/disputed state.

## C9 — Development Queue

Uses consequence, dependency, ownership and maturity evidence to propose which system should be developed next.

## C10 — Retest and Learning Loop

Freezes predicted effects, develops the legitimate owner, retests downstream dependents, updates state and recomputes the queue.

# 7. Levelling Principle

The goal is not literal equality.

Different systems have different complexity and consequence.

Define a context-sensitive sufficiency threshold:

[
Q(S,c)
]

where S is a required civil system/function and c is the deployment/consequence context.

A system is sufficiently developed for the current civil state when its applicable requirements meet the threshold necessary for its consequences and legitimate dependents.

The levelling objective is therefore:

[
orall S in T,quad M(S,c) ge Q(S,c)
]

for currently applicable consequential contexts, subject to explicit UNKNOWN and DISPUTED states.

This is **sufficient maturity**, not identical maturity.

# 8. Development Priority

Priority must not be reduced to graph centrality.

A candidate development target should consider:

[
P(S)=f(H,E,D,B,L,U,R)
]

where:

- H = potential harm/consequence severity;
- E = current exposure;
- D = dependency criticality;
- B = degree of upstream blockage;
- L = development leverage across legitimate dependents;
- U = uncertainty;
- R = reversibility/risk of intervention.

No single scalar score is required initially.

A structured multi-factor state is safer than false mathematical precision.

# 9. Required Status Vocabulary

- INTERFACE-SATISFIED
- PRESENT / DEPENDENCY-BLOCKED
- PARTIAL
- CANDIDATE-ABSENT
- UNKNOWN
- DISPUTED

Maturity and presence must remain separate fields.

# 10. Required Interface-Satisfaction Rule

A function may be satisfied by another legitimate owner if:

1. the owner is legitimate;
2. the owner actually possesses the capability;
3. the interface is sufficient for the consequence;
4. authority remains bounded;
5. the dependency is visible;
6. owner/interface failure is represented;
7. correction/review can propagate where materially required;
8. the arrangement does not create hidden sovereignty or an unreviewable monopoly.

This prevents the levelling process from forcing every system to duplicate every capability.

# 11. Canonical Development Route After Integration

Once CDTLA is integrated into V1.2, development should proceed in cycles.

## Phase 1 — Formalise the topology

Create stable identifiers and formal definitions for:

- systems/functions;
- nodes;
- typed relations;
- ownership;
- context;
- maturity;
- dependency;
- failure;
- correction;
- review;
- uncertainty;
- evidence/provenance.

Do not yet claim the representation is complete or machine-authoritative.

## Phase 2 — Operationalise KCS dependency representation

KCS should maintain live knowledge about:

- what exists;
- current status/version;
- provenance;
- dependencies;
- dependents;
- supersession;
- correction propagation;
- freshness.

The topology defines the grammar; KCS maintains the live knowledge state.

## Phase 3 — Populate a canonical civil-state snapshot

Use actual V1.2 systems.

Do not infer maturity from document count or length.

Record evidence, owner, dependencies, applicable context, unresolved requirements and confidence.

## Phase 4 — Generate the first canonical development queue

The queue must be generated from represented state.

Freeze it before deep investigation of proposed targets.

Then source-resolve each candidate.

This tests whether CDTLA can select useful development rather than merely describe prior reasoning.

## Phase 5 — Develop the first graph-selected target

Use:

Reuse
→ Interface
→ Integrate
→ Develop Owner
→ Invent only if necessary.

Apply minimum necessary intervention.

## Phase 6 — Retest

Measure predicted downstream changes.

Update state.

Recompute the queue.

## Phase 7 — Repeat until levelling criterion is met

Continue while consequential required systems remain below context-appropriate sufficiency.

The system must be able to output:

**NO DEVELOPMENT REQUIRED AT PRESENT**

when no justified target exceeds the development threshold.

# 19. Success Criterion

The canonical system succeeds if a future Concord instance can:

1. inspect the current civil architecture;
2. determine which required functions are sufficiently developed;
3. identify partial/dependency-blocked functions;
4. trace legitimate upstream owners;
5. distinguish local gaps from civil gaps;
6. propose a justified development order;
7. explain why the order was selected;
8. predict downstream effects;
9. retest after development;
10. revise its own map when wrong;
11. stop when further development is not presently justified.

The system fails if it becomes merely a document index, a central planner, an authority generator, or an endlessly expanding abstraction exercise.
