# Invention Frontier Existing-Solution Test 001C — Residual Civil Reachability Capability Positions

**Status:** V1.2a PROSPECTIVE FRONTIER TEST  
**Date:** September 2026  
**Canonical effect:** NONE  
**Parent tests:** Historical Test 001A and 001B  
**Residuals tested:** RF-1 through RF-5

# 1. Purpose

Historical Test 001B left five residual capability positions after comparing the later Citizen ID / communications architecture with the frozen pre-solution specification.

This pass asks whether those residuals are:

- already solved elsewhere;
- distributed but insufficiently interfaced;
- partial architecture;
- or still unresolved enough to qualify as prospective Invention Frontier candidates.

The search is Concord-wide but remains subject to ESCP.

# 2. RF-1 — Guaranteed Structural Plurality

**Question:** How is civil reachability prevented from depending on one resolver/provider/institution even when endpoints are technically changeable?

## Existing evidence

The later identity threat audit recognises the central-resolver problem and lists candidate approaches including:

- distributed resolution;
- blind or privacy-preserving relays;
- minimised routing logs.

Civil Contact Points already permits multiple current contact points.

The Continuity Protocol independently treats single points of failure as undesirable and states that good stewardship includes making oneself replaceable.

## Classification

**PARTIAL ARCHITECTURE / NO VERIFIED COMPLETE CIVIL-REACHABILITY PLURALITY MECHANISM.**

The design requirement is recognised and candidate techniques exist, but no reviewed source establishes a complete architecture ensuring that official civil reachability remains available without a structurally indispensable resolver/provider.

### Frontier status

**IF-001 — PROSPECTIVE INVENTION / ARCHITECTURE CANDIDATE.**

Required capability:

> A civil reachability architecture whose ordinary operation, migration and recovery do not depend upon any single resolver, provider or administrative operator, while preserving authoritative delivery, privacy, accessibility and provenance.

This may be solved by architecture rather than new physical technology.

# 3. RF-2 — Provider / Administrator Replacement Governance

**Question:** How is a captured or failed civil communications operator replaced without disrupting participant continuity?

## Existing evidence

The Continuity Protocol supplies a powerful general principle:

- continuity mechanisms must themselves possess continuity;
- responsibility/authority/stewardship transitions should preserve practical continuity;
- good stewardship includes making oneself replaceable;
- this protects civilisation from single points of failure.

The later communications architecture makes routing technology replaceable.

However, the reviewed sources do not specify the operational succession mechanism for a failed/captured civil communications resolver or Contact Point administrator.

## Classification

**DISTRIBUTED GENERAL SOLUTION PRINCIPLE + MISSING DOMAIN IMPLEMENTATION.**

This is not presently a pure invention gap because the higher-order solution grammar already exists:

Operator Failure
→ Succession / Replacement
→ Preserve Function
→ Preserve Records/Provenance
→ Continue Service.

What remains is domain engineering.

### Frontier status

**NOT PROMOTED TO INVENTION FRONTIER.**

Route to recursive integration / domain implementation.

# 4. RF-3 — Full Civil-State Portability

**Question:** How do correspondence, pending notices, participation state and relevant records migrate safely between implementations/providers?

## Existing evidence

Civil Contact Points explicitly asks:

- can records transfer elsewhere?
- what happens to pending communications?
- how quickly can a point be transferred?

The later Citizen ID architecture preserves identity while endpoints/routes change.

The Continuity Protocol strongly supports preservation of identity, records, provenance and function across transition.

But no reviewed architecture specifies an integrated transaction for migrating:

Contact State
+ Pending Official Communications
+ Relevant Records
+ Participation/Service State
+ Provenance
+ Delivery Obligations

between providers/implementations.

## Classification

**PARTIAL ARCHITECTURE / INTEGRATION AND PROTOCOL GAP.**

The components largely exist. The missing object appears to be a portability protocol rather than an unknown civil principle.

### Frontier status

**IF-002 — PROSPECTIVE PROTOCOL-INVENTION CANDIDATE.**

Required capability:

> An atomic or failure-safe civil-state migration protocol that transfers the minimum necessary contact/communication state between replaceable providers without loss, duplication, silent omission, surveillance expansion or interruption of legal/civil obligations.

“Invention” here means a presently unavailable protocol architecture, not necessarily new technology.

# 5. RF-4 — Contact-Specific Remedy Routing

**Question:** How does a participant challenge a provider/admin action and ensure the remedy propagates through identity/contact/service state?

## Existing evidence

Layer-Zero Systems Interface explicitly routes ownership/access/correction/contestability and institutional failure to the relevant architectures.

Citizen Data Ownership / Contestable Metrics and Judiciary provide general correction and adjudication functions.

The distributed Civil Submission and Receipt Layer explicitly supports appeals and requests for review with tamper-evident provenance.

CH003 already classified the Contact Point case as:

**distributed existing function + partial structural integration gap.**

## Classification

**EXISTING DISTRIBUTED SOLUTION + INTERFACE GAP.**

### Frontier status

**NOT AN INVENTION FRONTIER CANDIDATE.**

This should remain in recursive integration/development rather than invention search.

# 6. RF-5 — Non-Digital / Cross-Modality Access

**Question:** What equivalent civil-reachability paths exist for participants unable to use a particular digital mode?

## Existing evidence

Civil Contact Points explicitly identifies exclusion of people unable to use digital systems as a failure mode requiring development.

Layer-Zero Systems Interface treats:

- digital access;
- physical accessibility;
- cognitive accessibility;
- actual participant access

as distinct from formal availability.

CP-06 Meaningful Accessibility and System-Level Adaptation states that civil systems should be judged partly by whether participants can realistically exercise their claimed rights/services/pathways, and system/environment adaptation should normally be considered before unnecessary participant restriction.

These provide a strong normative and diagnostic requirement.

No reviewed source supplies a complete cross-modality civil-reachability mechanism guaranteeing equivalent official contact through digital and non-digital paths.

## Classification

**REQUIRED FUNCTION WELL ESTABLISHED / IMPLEMENTATION NOT ESTABLISHED.**

This is closer to a genuine capability position than an unnoticed ethical gap.

### Frontier status

**IF-003 — PROSPECTIVE ARCHITECTURAL INVENTION CANDIDATE.**

Required capability:

> A substrate- and modality-flexible civil reachability architecture that preserves authoritative notice, participant response, privacy, provenance and practical accessibility when a participant cannot use the default digital channel.

# 7. Frontier After Existing-Solution Test

Five residuals entered the test.

Two collapse into existing architecture/integration work:

- RF-2 → general succession/replaceability solution exists; domain implementation required.
- RF-4 → correction/remedy architecture exists; Contact Point interface requires integration.

Three remain:

## IF-001 — Non-Single-Provider Civil Reachability

No verified complete mechanism yet found.

## IF-002 — Failure-Safe Civil-State Migration

No verified integrated portability protocol yet found.

## IF-003 — Cross-Modality Authoritative Civil Reachability

Requirement is strong; complete implementation not established.

# 8. Important Result

The invention-frontier method has therefore discriminated between:

**Need already solved abstractly**
→ integrate it;

and:

**Need whose required capability is clear but no satisfying mechanism is yet verified**
→ candidate invention/search target.

This is the distinction the protocol was designed to test.

# 9. Are These Truly Inventions?

Not yet established.

Before claiming that IF-001–IF-003 require novel invention, the protocol requires an external-state-of-the-art check where real-world technology/protocols may already supply a solution.

Therefore their current status is:

> **NO VERIFIED SATISFYING CONCORD MECHANISM FOUND — EXTERNAL DISCOVERY / INVENTION CANDIDATE.**

The next phase must test existing real-world architectures such as distributed naming/resolution, federated messaging, portable identity, store-and-forward systems, resilient notification, accessibility channels and migration protocols.

If an external mechanism satisfies the frozen specification, the correct action is adoption/adaptation rather than invention.

# 11. ESCP

Repository search is not proof of absence.

IF-001–IF-003 remain candidates.

Their significance is that the topology has converted a broad known failure mode into three precise, testable capability specifications before any new solution has been selected.

That is already useful even if all three are subsequently solved by existing external technology.


# 12. External Knowledge Firewall — Discovery Must Not Become Import

The next falsification stage requires a strict separation between **external existence checking** and **Concord solution generation**.

The experiment is testing whether the Concord's own topology can:

- identify a need;
- derive the required function;
- specify the properties of a satisfying solution;
- expose an empty or incomplete internal solution position;
- and potentially generate its own candidate architecture.

Importing an external solution into that position before the Concord has attempted its own derivation would contaminate the experiment.

Therefore external research must operate under an **External Knowledge Firewall**.

## 12.1 Permitted External Result

For each frozen frontier specification, external checking may return only:

- **EXISTENCE CONFIRMED** — at least one external architecture appears to address substantially the same functional problem;
- **PARTIAL EXISTENCE CONFIRMED** — external work addresses part of the functional problem;
- **NO MATCH CONFIRMED IN BOUNDED SEARCH** — no adequate match was established in the defined search;
- **UNDETERMINED**.

Where necessary for auditability, provenance may record the source/category demonstrating existence.

## 12.2 Information That Must Not Enter the Generative Phase

Before the Concord independently generates and freezes its own candidate solution, the working model must not use external details such as:

- mechanism design;
- protocol structure;
- algorithm;
- implementation sequence;
- architecture diagram;
- component arrangement;
- technical trick;
- external solution's terminology where it reveals mechanism;
- performance optimisation;
- implementation-specific failure repair.

The existence check answers:

> Does humanity already appear to possess a solution to this kind of requirement?

It does **not** answer:

> How did humanity solve it?

## 12.3 Two Independent Tracks

The workflow therefore splits:

### Track A — Concord-Internal Generative Track

Frozen Need
→ Frozen Functional Specification
→ Concord-Internal Candidate Generation
→ Candidate Freeze
→ Internal Testing.

### Track B — External Existence Track

Same Frozen Functional Specification
→ External Search
→ Existence Classification Only
→ Sealed External Mechanism Detail.

The tracks must remain separated until the Concord candidate has been frozen.

## 12.4 Post-Freeze Comparison

Only after Track A has produced a frozen solution may external mechanism details be unsealed.

Then compare:

Concord-Derived Solution
vs
External Solution(s)

for:

- convergence;
- divergence;
- independently discovered common constraints;
- different mechanisms satisfying the same function;
- external advantages;
- Concord advantages;
- failure modes;
- possible synthesis.

Any later synthesis is a **separate development stage** and must not be represented as independently generated Concord architecture.

## 12.5 Stronger Experimental Test

This creates a stronger test than simply checking whether an external solution exists.

If:

1. topology independently derives the need;
2. topology freezes the solution specification;
3. external search confirms that the problem is real/recognised but withholds the mechanism;
4. Concord independently generates a solution;
5. later unsealing shows structural convergence with mature external solutions;

then the experiment has evidence of independent generative convergence.

If the Concord solution differs but satisfies the frozen specification, that may be equally interesting.

## 12.6 Provenance States

Every frontier item should carry an external-knowledge state:

- **E0 — No external search performed**
- **E1 — Existence-only search performed; mechanism sealed**
- **E2 — Concord candidate frozen**
- **E3 — External mechanism unsealed for comparison**
- **E4 — Post-comparison synthesis permitted**

No item should move from E1 to E3 before E2.

## 12.7 Contamination Rule

If external mechanism detail is accidentally exposed before the Concord candidate is frozen, the item must be marked:

**GENERATIVE INDEPENDENCE CONTAMINATED**

It may still be useful for architecture development, but it can no longer serve as clean evidence that the Concord independently generated the solution.

## 12.8 Implication for IF-001 to IF-003

IF-001, IF-002 and IF-003 currently remain at:

**E0 — NO EXTERNAL SEARCH PERFORMED**

The next external operation should therefore be an existence-only check designed to minimise mechanism exposure.

No external mechanism should be imported into the V1.2a generative work before independent candidate solutions are frozen.
