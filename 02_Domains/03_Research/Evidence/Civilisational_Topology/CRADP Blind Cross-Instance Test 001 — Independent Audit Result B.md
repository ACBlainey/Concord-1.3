# 1. Audit Object

The audited object is the portable **Triadic Decision Making Module**.

Its intended function is to reduce single-decision-maker failure through a three-member decision architecture incorporating:

- substantially equivalent information;
- independent preliminary reasoning;
- deliberation;
- For / Against / Abstain states;
- majority authorisation for state change;
- preservation of disagreement;
- escalation;
- decision records;
- post-decision review;
- and institutional learning.

The module explicitly presents itself as portable beyond the wider Concord architecture.

It may therefore be used by governance bodies, courts, organisations, research institutions, AI-governance systems and emergency-management structures.

That portability materially affects the audit.

# 2. Audited Deployment Context

The audit does **not** evaluate the Triadic module merely as an abstract description of a voting mechanism.

The audited context is:

> **A standalone deployment of the portable Triadic Decision Making Module for a consequential decision affecting identifiable participants, where the triad exercises real delegated decision authority.**

This context was selected because it is directly contemplated by the module itself and activates the civil-consequence requirements of the frozen Abstraction Layer Ladder.

A purely advisory or experimental triad with no authority and no material participant consequences would have a different applicability profile and therefore potentially a different abstraction level.

The result below is consequently:

**A(Triadic Decision Making | consequential standalone authority context).**

# 6. AL1 — Bounded and Consequence-Aware Function

AL1 introduces requirements concerning legitimate function, bounded scope and consequential relationships.

## Legitimate function distinguished from capability

**SATISFIED-INTERNAL**

The module explicitly requires the decision authority to be identified.

It also distinguishes AI analytical capability from constitutional authority and rejects accidental acquisition of authority through dependence on AI recommendations.

## Scope bounded

**PARTIALLY SATISFIED / CONTEXT-DEPENDENT**

The module requires identification of the authority under which the triad acts.

It recognises jurisdictional limits and escalation when authority or competence is insufficient.

However, the portable mechanism does not itself define the substantive boundary of the authority.

This is legitimate because a portable decision mechanism should not manufacture the authority within which it operates.

The boundary must normally be supplied by the host architecture.

## Scope expansion requires renewed justification

**UNSATISFIED AS A PORTABLE INTERFACE REQUIREMENT**

The target requires the existing decision authority to be identified.

It does not, however, make explicit in the minimal portable protocol that:

> authority valid for Scope A does not automatically authorise Scope B.

Nor does the portable implementation require a renewed authority/legitimacy check when the decision's effective scope expands.

This is significant because the frozen Relational Grammar explicitly establishes the Scope Expansion Rule:

> Existing legitimacy for one scope does not establish legitimacy for a new scope.

The target contains concepts compatible with this principle but does not operationalise the requirement in its portable procedure.

This is the **first unresolved applicable requirement encountered in the cumulative audit**.

## Materially affected participants identifiable

**PARTIALLY SATISFIED**

The independent-reasoning stage asks decision-makers to consider foreseeable harms and benefits.

The wider discussion of decisions clearly recognises consequences.

However, the minimal portable protocol does not require an explicit affected-participant identification step.

## Participant standing / agency / challenge

**UNSATISFIED LOCALLY; EXTERNAL SATISFACTION POSSIBLE**

The module provides review and recognises ordinary institutional challenge.

It does not itself define a portable participant challenge mechanism.

This omission is not automatically a structural defect in Triadic Decision Making.

Challenge may legitimately belong to a judiciary, appeals architecture, governance-review system or equivalent host institution.

The Concord Judiciary, for example, explicitly provides mechanisms through which individuals and institutions may challenge exercises of power.

The important issue is therefore not whether the triad itself contains a court.

It should not.

The issue is whether the portable triad requires a **defined interface** to the legitimate challenge/review owner when the deployment creates materially consequential authority.

At present that interface is not sufficiently specified in the portable implementation.

## Material asymmetry / anti-domination / stronger review

**PARTIALLY SATISFIED / INTERFACE-DEPENDENT**

The module is explicitly concerned with capture, authority, review and accountability.

But where a triad exercises materially asymmetric authority over affected participants, the portable protocol does not independently require identification of the stronger review/anti-domination mechanism that applies.

Again, this capability need not belong inside the triad.

It requires an interface.

# 10. Requirement Satisfaction Mode

For the first unresolved requirement:

**Current state: UNSATISFIED / PARTIALLY INTERFACE-DEPENDENT**

The requirement should not necessarily be implemented internally by the triad.

A portable triad cannot legitimately determine the boundaries of its own authority merely by adding another internal rule.

The authority boundary must come from the architecture that delegates the authority.

Therefore the likely correct satisfaction mode is:

> **SATISFIED-INTERFACE**

provided the necessary interface is made explicit and meets the interface-satisfaction conditions.

# 14. Gap Classification

The primary diagnosis is:

> **INTEGRATION GAP**

The target is not missing the concept of authority.

The wider architecture is not demonstrably missing authority-bounding or challenge functions.

Instead, the portable module can be detached from the architecture that supplies those safeguards without requiring the implementer to reconstruct the interfaces.

That creates a portability hazard.

The module is portable at the level of voting mechanics more successfully than it is portable at the level of authority-bound deployment.

A secondary interpretation is that some host architectures may themselves lack the required capabilities.

In such deployments, the deficit would become a **Developmental Dependency Gap** in the host architecture.

That cannot be assumed from the target alone.

# 16. Frozen Prediction

Before proposing the intervention, the following prediction is frozen:

> **P-BXIT001-B:** If the Triadic Decision Making Module is amended so that consequential deployments must explicitly identify (a) the source and scope of delegated authority, (b) whether the proposed decision expands that scope and therefore requires renewed justification, (c) materially affected participants, and (d) the legitimate review/challenge interface available to those participants, then the identified AL1 deficit should materially contract without changing the triadic decision mechanism itself.

A second prediction follows:

> If the host architecture cannot supply one of those required interfaces, CRADP should relocate the unresolved requirement upstream rather than instructing the Triadic module to invent the missing civil capability locally.

This prediction is frozen before intervention.

# 17. Minimum Necessary Intervention

Do not redesign Triadic Decision Making.

Do not change the 2-of-3 rule.

Do not add additional permanent decision-makers.

Do not duplicate Judiciary or Governance.

Add a small **Authority and Standing Interface Gate** before consequential use.

The minimal portable implementation could require the deployment record to establish:

1. **Authority source** — What architecture authorises this triad?
2. **Authority scope** — What exactly may it decide?
3. **Scope-change test** — Does this decision extend that authority into a materially new scope?
4. **Affected participants** — Who may materially bear the consequences?
5. **Standing/challenge owner** — Through what legitimate mechanism may affected participants contest the exercise of authority where applicable?
6. **Review strength** — Does material asymmetry require stronger review?
7. **Failure state** — What happens if the required authority or challenge interface is unavailable?

If authority cannot be established:

> **No authority to perform the state-changing decision.**

If the decision exceeds established scope:

> **Renewed justification/delegation required.**

If participant challenge is applicable but no legitimate challenge route can be established:

> **The interface requirement remains unresolved and consequential deployment should not be represented as fully architecturally satisfied.**

This is a small integration addition rather than a redesign.

# 22. Possible CRADP Defect Discovered

One methodological ambiguity was exposed.

CRADP correctly requires a deployment context before AL assignment.

However, a highly portable module may intentionally support radically different deployment contexts:

- advisory;
- organisational;
- judicial;
- governmental;
- emergency;
- AI-assisted;
- experimental.

A single audit can therefore produce a misleadingly general-looking AL result unless the output prominently binds the AL result to the selected context.

Suggested clarification for future CRADP versions:

> **For portable modules with materially different authority/consequence profiles, an AL result must always be represented as A(S|c), and no context-specific result may be silently generalised to the module in all deployments.**

This is not a failure of CRADP.

It is a useful precision improvement exposed through use.

A second possible clarification concerns multiple failures within the first incomplete layer.

CRADP says to identify the first unresolved applicable requirement, while the cumulative model technically establishes completeness at layer granularity.

Where several requirements within the same first incomplete layer fail, the audit should:

1. identify the first requirement under the frozen ordering;
2. preserve the other same-layer residuals;
3. avoid implying that repairing the first item automatically completes the layer.

This test required that distinction.
