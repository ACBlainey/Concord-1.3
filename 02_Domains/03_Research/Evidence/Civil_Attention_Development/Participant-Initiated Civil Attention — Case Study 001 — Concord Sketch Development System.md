# 1. Purpose

The Concord already contains a functioning bottom-up developmental intake system in `08_Active_Development/00_SKETCH_IDEAS/`.

That system was built for research and architectural development rather than civil administration.

Nevertheless, it performs a structurally similar function:

> **A participant notices something → the observation is preserved → it is separated from authority → it is developed → routed → tested where possible → integrated if justified → retained as provenance.**

This makes the Sketch Development System a useful first internal case study for the developing Participant-Initiated Civil Attention architecture.

The purpose of this case is not to assume that a research-development workflow can simply be copied into civilisation-wide governance.

It is to determine:

1. which functions already work;
2. which functions generalise;
3. which functions are Concord-research-specific;
4. which failure modes become visible through actual use;
5. which improvements discovered in the civil-attention programme should be back-propagated into the live Sketch Development System.

The relationship is therefore deliberately recursive:

> **Existing Sketch System → Extract General Civil-Attention Functions → Develop/Test → Identify Improvements → Back-Propagate Justified Improvements → Observe → Refine**

# 3. Existing Sketch Intake Function

The Sketch README defines the folder as an earliest-stage development space.

A sketch may begin as:
- observation;
- question;
- analogy;
- thought experiment;
- possible failure mode;
- connection between systems;
- speculative hypothesis;
- operational suggestion;
- possible test;
- unresolved contradiction.

Its primary rule is:

> **Preserve first. Resolve later.**

This is already close to a general civil-attention requirement.

A participant should not have to know:
- the final solution;
- the correct authority;
- the correct evidential classification;
- the appropriate constitutional layer;
- whether anyone else agrees;

before an observation can enter legitimate attention.

---

# 4. Existing Sketch Pipeline

The README currently expresses the development path as:

**SKETCH IDEA**
→ **DEVELOPMENT NOTE**
→ **QUESTION / PROBLEM DEFINITION**
→ **HYPOTHESIS / PROPOSED PRINCIPLE**
→ **CRITICAL EXAMINATION**
→ **MODEL / MECHANISM**
→ **TEST / SIMULATION / COMPARISON**
→ **EVIDENCE / EVALUATION**
→ **CONCORDIAN PRINCIPLE**
→ **CONSTITUTIONAL CONSTRAINT**
→ **OPERATIONAL ARCHITECTURE**
→ **IMPLEMENTATION / MODULE**
→ **REVIEW**
→ **ACTIVE / SUPERSEDED / ARCHIVED**

The README also explicitly permits:
- stopping;
- failure;
- splitting;
- merging;
- permanent speculation;
- later promotion.

This is important because it prevents the intake stage from prejudging the correct outcome.

# 5. Mapping to the Civil-Attention Architecture

The current Civil Attention Development Note proposes:

**Participant Trigger**
→ **Receipt**
→ **Preservation**
→ **Mechanism Classification**
→ **Functional/Jurisdictional Routing**
→ **Epistemic State**
→ **Priority / Consequence Review**
→ **Legitimate Examination**
→ **Disposition**
→ **Feedback**
→ **Appeal / Escalation Where Applicable**
→ **Outcome Observation / Learning**

The sketch system can be mapped provisionally:

| Civil-attention function | Sketch-system analogue |
|---|---|
| Participant Trigger | new sketch / author observation / AI-assisted finding |
| Receipt | repository/file creation provides practical evidence of capture, but no dedicated receipt mechanism |
| Preservation | sketch retained in live queue or archive |
| Mechanism Classification | sketch/question/hypothesis/test-case/etc. classification |
| Functional Routing | promotion to Development Note, experiment, test case, existing system or archive |
| Epistemic State | SKETCH / UNTESTED / NON-CANONICAL and later development statuses |
| Priority / Consequence Review | portfolio review and dependency/topology judgement |
| Legitimate Examination | source resolution, critical examination, tests and audits |
| Disposition | promote / split / merge / hold / reformulate / overtake / close / archive |
| Feedback | development records, portfolio audits and status reports |
| Appeal / Reclassification | not yet formalised as a distinct sketch mechanism |
| Outcome Observation / Learning | portfolio reassessment and back-propagation |

This mapping is sufficiently strong to justify using the sketch system as a case study.

It is not strong enough to claim that the two systems are identical.

# 6. What the Sketch System Already Demonstrates

## 6.1 Low-threshold intake has value

An idea can be preserved before it is mature enough to justify a Development Note.

This reduces the risk that useful observations disappear merely because the observer cannot yet prove or formalise them.

## 6.2 Preservation and endorsement can be separated

The explicit status:

> **SKETCH / UNTESTED / NON-CANONICAL**

allows preservation without authority.

Civil attention needs an equivalent separation:

> **Received ≠ Verified ≠ Accepted ≠ Authorised**

## 6.3 Classification can change

Recent portfolio work has shown sketches can become:
- Development Notes;
- experiments;
- test cases;
- synthesis projects;
- source-owned elsewhere;
- decomposed residuals;
- archived provenance.

This supports the Civil Attention Development Note's requirement that classification must not permanently trap a matter.

## 6.4 Provenance survives promotion

The graduated-sketch archive preserves the origin after substantive ownership moves elsewhere.

That suggests a general civil rule:

> **Routing Should Transfer Responsibility Without Erasing Origin**

## 6.5 One submission may contain several different problems

The consolidated civilisational-boundary sketch required decomposition into:
- already-owned work;
- residual research questions;
- test concepts;
- speculative work.

Therefore:

> **One Submission ≠ One Required Disposition**

Civil intake should support splitting while preserving the common origin.

## 6.6 Later development can change the status of earlier intake

The Dynamic Status and Back-Propagation section of the Sketch README explicitly recognises that later evidence may:
- answer;
- overtake;
- reformulate;
- unblock;
- or reroute earlier sketches.

Civil attention may need the same property.

A submission closed today may become relevant again if the evidence or architecture changes.

# 7. Important Differences Between Sketch Development and Civil Attention

The analogy has limits.

## 7.1 Consequence

A research sketch can often wait.

A safety report, rights violation or urgent civil failure may not.

Civil attention therefore requires consequence-sensitive escalation absent from ordinary sketch incubation.

## 7.2 Adversarial incentives

The sketch system currently operates inside a collaborative research project.

Civil systems must expect:
- spam;
- strategic flooding;
- retaliation;
- fabricated evidence;
- synthetic support;
- coordinated manipulation;
- institutional self-protection.

## 7.3 Reporter protection

Sketch authorship is generally useful provenance.

Civil problem reporting may require:
- anonymity;
- sealed identity;
- whistleblower protection;
- protected evidence.

## 7.4 Formal duties

A research project may choose what to develop.

A legitimate civil system may acquire duties to process some classes of submission.

## 7.5 Multiple participants and conflicting interests

Civil submissions may affect parties who dispute the report, remedy or classification.

## 7.6 Appeal and remedy

The sketch system has informal reconsideration and portfolio reassessment.

Civil attention may require explicit review, appeal, remedy and independent escalation.

Therefore the sketch system is a **functional analogue**, not a ready-made civil portal.

# 8. First Generalised Functional Model

The case study suggests a more explicit general sequence:

**NOTICE**
→ **CAPTURE**
→ **PRESERVE**
→ **ACKNOWLEDGE**
→ **CLASSIFY PROVISIONALLY**
→ **ROUTE**
→ **EXAMINE**
→ **RECLASSIFY / SPLIT / MERGE IF NEEDED**
→ **DISPOSE**
→ **EXPLAIN**
→ **REVIEW / ESCALATE WHERE JUSTIFIED**
→ **OBSERVE OUTCOME**
→ **LEARN**
→ **REOPEN IF MATERIAL CONDITIONS CHANGE**

This adds three useful features to the earlier abstract architecture:

1. **classification is explicitly provisional**;
2. **split/merge/reclassification is an ordinary processing function**;
3. **reopening after changed conditions is explicit**.

These are candidate improvements, not yet canonical requirements.

---

# 9. Submission Object Versus Development Object

The sketch workflow exposes a useful distinction.

An original intake object should not necessarily become the working development object.

For example:

**Original Sketch S**
→ **Development Note D**
→ **Test T**
→ **Architecture A**

S remains the provenance object.

D, T and A are later work products.

Generalising:

> **Submission Object ≠ Investigation Object ≠ Decision Object ≠ Implementation Object**

This separation can prevent later editing from rewriting what the participant originally submitted.

Candidate rule:

> **Preserve the original intake object; create linked downstream objects for later processing.**

This aligns naturally with the Civil Submission and Receipt architecture.

---

# 10. Parent–Child Provenance

Where one submission splits:

**S**
→ **S-A**
→ **S-B**
→ **S-C**

the system should preserve:
- common parent;
- reason for split;
- new owner/routes;
- individual status;
- closure relationship.

Where several submissions merge into one investigation:

**S1 + S2 + S3**
→ **I1**

the originals should remain individually recoverable.

Therefore:

> **Merge for Processing ≠ Erase Individual Provenance**

and:

> **Split for Routing ≠ Rewrite Original Submission**

This is directly supported by recent sketch decomposition experience.

---

# 11. Provisional Classification

The sketch system's recent use suggests classification should be understood as a working hypothesis.

Candidate status form:

**Classification = Type + Reason + Confidence + Time + Classifier + Reviewability**

This would make it possible to ask:
- why was this called a suggestion rather than a problem report?
- what evidence supported the classification?
- who/what classified it?
- when?
- can it be challenged?
- did later evidence change it?

This is stronger than a simple category label.

# 12. Disposition Vocabulary

The sketch system has developed a useful status vocabulary:
- open;
- source resolution required;
- ready for Development Note;
- ready for bounded experiment;
- ready for synthesis;
- infrastructure task;
- partially supplied;
- overtaken;
- test case;
- graduated;
- hold;
- reformulation required;
- closed;
- retained for provenance.

Civil attention will require a different vocabulary, but the underlying lesson generalises:

> **A binary Open/Closed state is too weak for complex attention systems.**

A future civil disposition model may need to distinguish:
- received;
- routed;
- awaiting evidence;
- investigating;
- split;
- merged;
- transferred;
- deferred with reason;
- action taken;
- no action justified;
- outside current jurisdiction;
- unresolved;
- escalated;
- closed subject to reopening.

No final vocabulary is established here.

---

# 13. Feedback as a Processing Function

The sketch workflow works partly because the development state remains visible.

A civil system should not merely provide a receipt.

It should provide enough status information to distinguish:
- processing;
- legitimate delay;
- transfer;
- investigation;
- disposition;
- closure.

This reinforces the parent Development Note:

> **Receipt Alone Can Become Feedback Theatre**

A useful feedback object may eventually contain:

**Current State + Reason + Responsible Function + Last Material Action + Next Review Condition**

subject to privacy/security constraints.

---

# 14. Reopening

The sketch system's dynamic-status rule reveals an important civil analogue.

A matter may be legitimately closed on current evidence and later require reopening because:
- new evidence appears;
- severity changes;
- another submission corroborates it;
- a pattern emerges;
- law/architecture changes;
- an earlier classification is shown to be wrong;
- a supposedly isolated event becomes systemic.

Therefore:

> **Closure ≠ Erasure**

and:

> **Closure on Current Evidence ≠ Permanent Immunity From Reconsideration**

Reopening criteria require future development to prevent endless relitigation.

# 15. Candidate Back-Propagation Improvements to the Sketch System

The civil-attention comparison immediately exposes several possible improvements to the existing development system.

These should not be implemented merely because they sound useful.

They should be tested against the actual development workflow.

### BP-01 — Explicit Intake Identifier
Each sketch could have a stable identifier independent of filename/location.

Potential benefit: provenance survives rename, split and archive.

### BP-02 — Explicit Parent/Child Links
Split sketches and promoted Development Notes could record their source object and descendants consistently.

### BP-03 — Provisional Classification Record
A sketch's current classification could include reason/date rather than status alone.

### BP-04 — Explicit Disposition Record
When promoted, split, merged, overtaken or closed, record why and where substantive ownership moved.

Recent archive work already approximates this.

### BP-05 — Reopening Rule
Define when an archived/closed sketch can legitimately return to active development.

### BP-06 — Submission/Working-Object Separation
Preserve original rough source where materially important while allowing later formalisation to proceed separately.

### BP-07 — Reviewability of Classification
Allow a portfolio audit or later source evidence to challenge an earlier route.

This already happens in practice but could become explicit.

### BP-08 — Processing-State Visibility
A compact register could show current owner/status for live sketches without requiring full-file inspection.

These are **candidate back-propagation deltas**, not approved changes.

# 17. Evaluation Rule

A candidate improvement should back-propagate into the Sketch Development System only if:

1. it solves an observed or credible failure;
2. it does not create disproportionate process burden;
3. it preserves low-threshold idea capture;
4. it does not turn sketch intake into premature bureaucracy;
5. it improves provenance, routing, reviewability or learning;
6. it survives at least one contrasting-case check.

Therefore:

> **More Process ≠ Better Intake**

and:

> **Civil-Attention Generalisation ≠ Automatic Sketch-System Upgrade**

This preserves the same discrimination logic established elsewhere in Concord development.

---

# 18. Relationship to BPM

If the civil-attention programme produces a justified improvement to the Sketch Development System, the return path is conceptually similar to BPM but is not automatically a PMEDG/BPM cycle.

The source system here is an **active development methodology**, not necessarily a graduated portable module.

A bounded development feedback route is:

**Observed Sketch Practice**
→ **Civil-Attention Generalisation**
→ **Test**
→ **Delta**
→ **Source Relevance**
→ **Bounded Sketch-System Improvement**
→ **Regression Against Low-Threshold Capture**
→ **Record**

If repeated use demonstrates a need for a formal general method, that can be developed later.

Do not create another methodology prematurely.
