# 1. Purpose

Case Study 001 selected five contrasting completed sketch histories to test whether the Concord Sketch Development System contains generalisable civil-attention functions and whether the eight candidate back-propagation deltas solve real problems.

This paper reconstructs those five paths.

The objective is not to judge the substantive quality of the ideas. It is to examine the **processing architecture**:

**Trigger → Capture → Classification → Development → Reclassification → Disposition → Provenance → Learning**

---

# 2. Case A — Straight Promotion
## Empirical Testing of Portable Modules

### Path

**Trigger:** author asks whether portable modules can be empirically tested and whether their use in developing Concord counts as evidence.

**Capture:** preserved as *Sketch Idea — Empirical Testing of Portable Modules*.

**Initial state:** **SKETCH / UNTESTED / NON-CANONICAL**.

**Development threshold:** the sketch already contains:
- a clear question;
- relationship to the portable-module programme;
- evidentiary risks;
- development questions;
- possible tests.

**Disposition:** promoted to:

`Empirical Validation of Portable Modules — Development Note 001.md`

**Provenance:** archived source explicitly records:
- Development Transfer;
- Promotion Date;
- original observation;
- validation boundary.

### What worked

This is the cleanest path.

The original question remained recoverable while substantive ownership moved to a later object.

The sketch did not need to become the Development Note itself.

### Friction / information gap

The provenance link is readable to a human, but there is no standard object-level identifier or standard transition record shared across all sketches.

The process relies on file path and prose metadata.

### Civil-attention analogue

A participant suggestion may be accepted for structured examination without implying acceptance of the proposal.

> **Accepted for Development ≠ Accepted as Correct**

### Candidate deltas supported

- **BP-01 stable intake identifier:** moderately supported.
- **BP-02 parent/child links:** strongly supported.
- **BP-04 disposition record:** strongly supported.
- **BP-06 submission/working-object separation:** strongly supported.
- **BP-08 processing-state visibility:** moderately supported.

No evidence from this case alone supports adding heavy classification bureaucracy.

# 3. Case B — Split / Decomposition
## Civilisational Autonomy, Intelligence, Stewardship, Harm, Identity and Recursive Learning

### Path

**Trigger:** twelve partially related sketch notes consolidated for preservation.

**Capture:** one broad source object.

**Later source resolution:** substantial subsequent Concord development overtook or separately owned several components.

**Reclassification:** whole-document promotion rejected.

The later decomposition found:
- already-owned work;
- substantially overtaken work;
- five bounded residual research/implementation questions;
- two bounded test concepts;
- one isolated speculative workstream.

**Disposition:** original consolidated object archived as a decomposition/source-ownership record.

### What worked

The process avoided the common error:

> **One Intake Object → One Development Object**

Instead:

> **One Intake Object → Multiple Dispositions**

The source remained intact as provenance while later ownership was distributed.

### Friction / information gap

This case required substantial contextual reconstruction.

Without broad repository knowledge, it would have been easy to:
- duplicate existing work;
- promote the whole source;
- lose residual questions;
- mistake an overtaken idea for an open gap.

The resulting decomposition is human-readable, but the relationships among parent source, five residuals, two tests and existing owners are not represented in a standard machine-readable form.

### Civil-attention analogue

A single participant report may contain:
- a safety issue;
- a service complaint;
- a rights issue;
- a policy suggestion;
- irrelevant or speculative material.

A legitimate system must be able to split these without forcing the participant to know the internal organisation in advance.

> **Mixed Submission ≠ Invalid Submission**

### Candidate deltas supported

- **BP-01 stable intake identifier:** strongly supported.
- **BP-02 parent/child links:** very strongly supported.
- **BP-03 provisional classification:** strongly supported.
- **BP-04 disposition record:** very strongly supported.
- **BP-07 classification reviewability:** very strongly supported.
- **BP-08 processing-state visibility:** strongly supported.

This case provides the strongest evidence so far for explicit split/merge provenance.

# 4. Case C — Reroute to Existing Architecture
## Galaxy Quest Dilemma

### Path

**Trigger:** thought experiment about ethical success, cultural forgetting and loss of defensive recognition capacity.

**Capture:** preserved as a sketch.

**Initial apparent route:** possible defensive-memory architecture.

**Source-aware examination:** later Concord systems already owned much of the operational space.

**Reclassification:** operational core became **GQD-001**, an adversarial scenario/test case.

**Disposition:**
- operational core → EVA test route;
- defensive-memory architecture → no duplicate system created;
- cooperative-ecosystem hypothesis → speculative;
- first-contact/Fermi branch → speculative;
- source sketch → archived provenance.

### What worked

The process allowed a potentially architectural idea to become a **test of existing architecture**.

This is a major generalisable function.

> **Reported Need ≠ Necessarily Missing Institution**

Sometimes the correct response to a submission is to test whether an existing system already covers it.

### Friction / information gap

The initial classification could easily have hardened into an architecture before source resolution.

The system currently depends heavily on reviewers remembering to ask:

> **Does this already have a legitimate owner?**

### Civil-attention analogue

A participant may report “we need a new agency/system/rule.”

The legitimate civil question is first:

> **What function is missing, and is that function already owned?**

The participant's proposed remedy should not determine institutional structure.

### Candidate deltas supported

- **BP-03 provisional classification:** very strongly supported.
- **BP-04 disposition record:** strongly supported.
- **BP-07 classification reviewability:** very strongly supported.
- **BP-08 processing-state visibility:** moderately supported.

This case also suggests a new general requirement:

### BP-09 — Source/Owner Resolution Before Structural Expansion
Before creating a new development owner, determine whether the reported function is already legitimately owned elsewhere.

This is the civil-attention analogue of ESCP/source-family resolution.

# 5. Case D — Multiple Evidentiary Objects
## Unified Paths Comparative Ethics Book and Religion-as-Transmission Hypothesis

### Path

**Trigger:** one sketch connected:
- a possible comparative ethics book;
- a religion-as-transmission hypothesis;
- a direction-of-ethical-application hypothesis.

**Capture:** preserved together because they arose from the same Unified Paths work.

**Examination:** later review identified that the components had different evidentiary status.

**Reclassification:**
- comparative ethics book → synthesis/publication project;
- religion-as-transmission → unvalidated historical/anthropological hypothesis;
- direction-of-application → comparative research dimension.

**Disposition:** no whole-sketch promotion and no duplicate Development Note.

### What worked

Common origin did not force common evidentiary status.

This is important:

> **Shared Provenance ≠ Shared Evidentiary Status**

and:

> **Shared Submission ≠ Shared Processing Standard**

### Friction / information gap

The original combined object could have allowed support for the completed Unified Paths extraction work to leak into the unvalidated historical hypothesis.

The later decomposition had to explicitly create non-inference rules.

### Civil-attention analogue

A participant may submit:
- an observed fact;
- an interpretation;
- a causal explanation;
- a proposed remedy;

in one report.

These should remain linked but must not inherit one another's evidentiary status.

### Candidate deltas supported

- **BP-02 parent/child links:** strongly supported.
- **BP-03 provisional classification:** strongly supported.
- **BP-04 disposition record:** strongly supported.
- **BP-06 original/working-object separation:** strongly supported.
- **BP-07 classification reviewability:** strongly supported.

This case suggests another general requirement:

### BP-10 — Claim-Level Evidentiary Separation
Where one intake object contains materially different claim types, preserve their common provenance while allowing separate epistemic states and dispositions.

# 6. Case E — Development → Method → Back-Propagation
## Portable-Module Back-Propagation

### Path

**Trigger:** observation that portable-module development may produce improvements absent from source Concord systems.

**Capture:** *Sketch Idea — Back-Propagation of Graduated Portable-Module Improvements into Concord Systems*.

**Development:** formal Development Note and operational programme.

**Testing through use:** SMM and STRA cycles demonstrated that the trigger identified a real maintenance problem.

**Formalisation:** repeated cycles produced **Portable-Module Back-Propagation Method — BPM v1.0**.

**Operationalisation:** module-specific audits, bounded companion upgrades, interface regression and permanent records.

**Disposition:** sketch archived as **GRADUATED TO DEVELOPMENT PROGRAMME / METHOD TRIGGER CONFIRMED — IMPLEMENTED AND REPEATEDLY USED**.

### What worked

This case demonstrates a complete recursive path:

**Observation**
→ **Development**
→ **Operational Method**
→ **Repeated Use**
→ **Evidence**
→ **Source-System Improvement**

It also demonstrates that the correct result of back-propagation can be **no source change**.

### Friction / information gap

The formal method emerged after repeated practical cycles.

Earlier cycles therefore depended on more implicit process knowledge than later ones.

This is not necessarily a defect: premature formalisation could have frozen a weak method.

### Civil-attention analogue

A participant report may eventually reveal not merely a local defect but a defect in the civilisation's **way of processing defects**.

A legitimate recursive system must be capable of improving its own intake and response process.

### Candidate deltas supported

- **BP-02 parent/child links:** strongly supported.
- **BP-04 disposition record:** very strongly supported.
- **BP-05 reopening/dynamic review:** moderately supported.
- **BP-07 reviewability:** strongly supported.
- **BP-08 state visibility:** strongly supported.

It also supports the core programme premise:

> **Civil-Attention Development May Legitimately Improve the Civil-Attention Development Process**

without implying that every improvement should automatically return to the source system.

# 7. Cross-Case Findings

Across all five cases, several functions recur.

## Finding F1 — Original capture should survive later formalisation

All five histories benefit from preserving the original trigger separately from later work.

Supported candidate:
**BP-06 — Submission/Working-Object Separation**

**Evidence strength in this case set:** STRONG.

---

## Finding F2 — Routing is not a one-time decision

Cases B, C and D required material reclassification.

Supported candidates:
**BP-03 — Provisional Classification Record**
**BP-07 — Reviewability of Classification**

**Evidence strength:** STRONG.

---

## Finding F3 — Split and merge require explicit provenance

Cases B and D especially show that one source can produce multiple children with different owners and epistemic states.

Supported candidate:
**BP-02 — Parent/Child Links**

**Evidence strength:** VERY STRONG.

---

## Finding F4 — Disposition is itself valuable knowledge

Knowing that an idea was:
- promoted;
- rerouted;
- overtaken;
- decomposed;
- retained as speculative;
- or source-owned elsewhere

prevents duplicate work and reconstructs why the current architecture exists.

Supported candidate:
**BP-04 — Explicit Disposition Record**

**Evidence strength:** VERY STRONG.

---

## Finding F5 — File paths alone are fragile identity

Promotion and archiving move objects.

A stable intake identifier would make lineage easier to follow independently of path.

Supported candidate:
**BP-01 — Explicit Intake Identifier**

**Evidence strength:** MODERATE-TO-STRONG.

The case set demonstrates utility, but does not yet establish the best identifier format.

---

## Finding F6 — Current state should be visible without reconstructing the whole history

The portfolio review had to inspect many documents to determine current ownership/status.

Supported candidate:
**BP-08 — Processing-State Visibility**

**Evidence strength:** STRONG.

A register may solve this, but its maintenance burden must be tested.

---

## Finding F7 — Reopening is conceptually necessary but not yet well exercised

Dynamic status is explicit in the Sketch README.

However, the five selected cases contain stronger evidence for reclassification and back-propagation than for reopening a genuinely closed item.

Supported candidate:
**BP-05 — Reopening Rule**

**Evidence strength:** PLAUSIBLE / NOT YET STRONGLY DEMONSTRATED.

Do not back-propagate a detailed reopening mechanism yet.

---

## Finding F8 — Source/owner resolution is a missing explicit intake safeguard

Case C and the broader recent portfolio audit repeatedly required checking whether an apparent new problem was already owned elsewhere.

New candidate:
**BP-09 — Source/Owner Resolution Before Structural Expansion**

**Evidence strength:** STRONG.

This should not prevent low-threshold capture. It applies before creating a new substantive owner, not before accepting a sketch.

---

## Finding F9 — Claim-level evidentiary separation matters

Case D demonstrates that one source object can contain claims with radically different evidentiary status.

New candidate:
**BP-10 — Claim-Level Evidentiary Separation**

**Evidence strength:** STRONG.

This is particularly important for civil reports mixing observation, inference, accusation and requested remedy.

# 8. Candidate Back-Propagation Decision

The five-case comparison does **not** justify implementing all ten candidates.

A first bounded improvement should solve the strongest observed problems without turning sketch capture into administration.

The best first package is:

### Adopt in principle for bounded Sketch-System back-propagation
- **BP-02 — Parent/Child Links**
- **BP-04 — Explicit Disposition Record**
- **BP-07 — Classification Reviewability**
- **BP-09 — Source/Owner Resolution Before Structural Expansion**

These mostly formalise practices already shown useful.

### Pilot, do not yet require universally
- **BP-01 — Stable Intake Identifier**
- **BP-03 — Provisional Classification Record**
- **BP-08 — Compact Processing-State Register**
- **BP-10 — Claim-Level Evidentiary Separation**

These may add substantial value but require a lightweight implementation design.

### Hold
- **BP-05 — Formal Reopening Rule**

Need stronger case evidence before specifying it.

### Preserve existing practice
- **BP-06 — Submission/Working-Object Separation**

This is already effectively demonstrated by the archive/development-note structure. The immediate need is to state it clearly rather than invent a new mechanism.

# 9. First Civil-Attention Architecture Refinements

The historical cases support five refinements to the parent Civil Attention Development Note.

## CA-R1 — Classification Is Provisional

> **Initial Classification = Routing Hypothesis, Not Final Truth**

A matter must be capable of reclassification when evidence or source resolution changes.

## CA-R2 — Intake and Processing Objects Are Distinct

> **Original Submission ≠ Investigation Record ≠ Finding ≠ Decision ≠ Implementation**

Preserve the original.

## CA-R3 — Split/Merge Must Preserve Provenance

A submission may split into multiple matters or several submissions may merge into one investigation.

Neither operation should erase source lineage.

## CA-R4 — Source/Owner Resolution Precedes New Structural Creation

A reported need can justify attention without proving a new institution is required.

> **Observed Problem ≠ Missing Owner**

## CA-R5 — Claims Within One Submission May Need Different Epistemic States

> **Common Origin ≠ Common Evidentiary Status**

This is especially important where observation, inference, accusation, preference and remedy appear together.

---

# 10. Regression Against Low-Threshold Capture

The main danger is over-formalising the Sketch System.

A new sketch should **not** require:
- an identifier chosen by the author;
- a complete classification;
- source-family resolution;
- claim decomposition;
- a known owner;
- evidentiary assessment;
- a disposition;
- or a development route

before capture.

The correct sequence remains:

> **Capture First → Structure Later**

Therefore any back-propagated metadata should be added by later processing where useful, not imposed as a submission burden.

This is likely to generalise directly to civil attention:

> **The Participant Should Not Need to Understand the Civil Machine in Order to Alert It.**

---

# 11. Recommended First Source-System Upgrade

The evidence supports a **small README-level upgrade**, not a new sketch bureaucracy.

Add a lightweight rule to the Sketch Development System:

1. preserve the original sketch as the intake/provenance object;
2. treat classification as provisional and reviewable;
3. before creating a new Development Note/system, source-resolve whether the function already has an owner;
4. when splitting, merging, rerouting or promoting, record the disposition and linked destination(s);
5. do not require these fields before initial capture.

A register/ID system should be piloted separately before adoption.

This is a bounded back-propagation candidate because it mostly formalises practices already exercised successfully.
