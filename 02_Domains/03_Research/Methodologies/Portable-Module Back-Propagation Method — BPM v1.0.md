# Portable-Module Back-Propagation Method — BPM v1.0

**Author:** Alexander C. Blainey — Independent Researcher
**Project:** The Concord Framework
**Status:** OPERATIONAL CORRIGIBLE METHODOLOGY / REPEATEDLY EXERCISED
**Version:** 1.0
**Date:** 24 September 2026
**Developmental origin:** Sketch Idea — Back-Propagation of Graduated Portable-Module Improvements into Concord Systems
**Method pilot:** Portable-Module Back-Propagation Audit — Development Note 001
**Evidence base:** SMM, STRA, KCS Change Propagation, Architectural Unit Resolution, Contextual Wrapper Architecture

---

## 1. Purpose

Portable-module extraction is not necessarily a one-way transformation.

PMEDG may expose failure modes, clarify interfaces, recover source-family architecture, formalise previously experimental methods, or produce other evidence-supported refinements after a module has been extracted from its Concord source.

The required return path is:

**Concord Source**
→ **Portable Extraction**
→ **PMEDG Development**
→ **Graduated Module**
→ **Back-Propagation Source Resolution**
→ **Delta Classification**
→ **Source-Relevance Decision**
→ **Bounded Integration Where Justified**
→ **Architectural Interface Regression**
→ **Permanent Record**

The method exists to prevent useful development becoming stranded in portable modules while also preventing portable differences from being copied back indiscriminately.

## 2. Core constraints

> **Portable Difference ≠ Source-System Improvement**

> **Validated Portable Refinement ≠ Automatic Canonical Amendment**

> **Local Source Absence ≠ Concord-Wide Absence**

> **Source Recovery ≠ New Invention**

> **Back-Propagation Success ≠ Quantity of Change Returned**

> **Back-Propagation Success = Correct Disposition of the Delta**

A valid audit may produce substantial source change, small clarification, source-family consolidation, method promotion, no source change, or a hold.

## 3. Entry condition

BPM normally begins only after the portable module has graduated under PMEDG.

Graduation and back-propagation answer different questions:

- **PMEDG:** is this a stable transferable portable artifact?
- **BPM:** did portable development produce or expose anything that should alter, clarify, consolidate or promote the Concord source architecture?

An exceptional pre-graduation source correction may be handled through ordinary Active Development, but it is not a BPM completion.

## 4. Evidence set

Resolve at minimum:

1. graduated portable module;
2. PMEDG source-resolution/extraction audit;
3. blind-test evaluations;
4. convergence/revision evidence where present;
5. graduation review;
6. immediate originating Concord source;
7. declared neighbouring/source-family architecture where materially relevant;
8. current source-side companions or later developments;
9. prior back-propagation records affecting the same interfaces.

Do not compare only the portable module with one old source file when the architecture is explicitly distributed.

## 5. Source-family resolution gate

Before declaring a portable/source difference to be a missing Concord capability, ask:

1. Is it absent from the immediate source?
2. Is it present in a declared neighbour?
3. Is it present in another source-grounded functional owner?
4. Is the portable form integrating several existing Concord mechanisms?
5. Is the search/evaluation space sufficient to justify an absence claim?

This is the BPM application of ESCP.

Possible findings include:

- genuinely post-extraction development;
- source mechanism already present but clearer in portable form;
- wider Concord mechanism under-represented in immediate source;
- portable-only adaptation;
- unresolved provenance.

Where source-family evidence changes the interpretation, record that explicitly.

## 6. Delta classification

Classify each material delta using one or more of:

- **P — Portability-only:** useful to generic hosts but not required by the Concord source.
- **C — Clarification/formalisation:** source mechanism substantially exists; portable form makes it more precise.
- **G — General improvement:** evidence-supported refinement applicable to the Concord source itself.
- **F — Failure-mode correction:** closes a weakness exposed by testing that also exists in the Concord source.
- **I — Interface improvement:** improves exchange with another Concord system or representation.
- **R — Recovered architecture / source-family consolidation:** absent or under-represented locally, but wider source resolution shows the architecture already exists elsewhere in Concord.
- **S — Source-specific review required:** applicability cannot safely be decided from the portable evidence alone.

Multiple classifications may apply.

R is especially important for provenance:

> **Recovered Existing Architecture Must Not Be Relabelled as Portable Invention**

## 7. Source-relevance decision

For each delta determine:

- evidence origin;
- source applicability;
- authority implications;
- whether literal portable syntax is required or only semantic behaviour;
- whether a neighbouring system already owns the function;
- whether integration would duplicate architecture;
- whether the source has changed since extraction;
- whether uncertainty requires HOLD rather than incorporation.

A portable module may reveal a source problem without owning the solution.

## 8. Integration disposition

After classification, choose the smallest justified disposition.

### BPM-D0 — NO SOURCE CHANGE REQUIRED

Portable difference is host-specific, already adequately represented, unsupported, or otherwise does not justify source modification.

### BPM-D1 — CLARIFICATION / CROSS-REFERENCE

The source needs only a semantic clarification, provenance note, or explicit relationship to existing architecture.

### BPM-D2 — BOUNDED COMPANION UPGRADE

Source kernel remains sound but evidence supports additive operational, interface or failure-mode refinements.

### BPM-D3 — SOURCE-FAMILY CONSOLIDATION

The immediate source under-represents architecture already present across wider Concord sources. Integrate/cross-reference that architecture without falsely claiming invention or collapsing ownership boundaries.

### BPM-D4 — METHOD / ARCHITECTURE PROMOTION

An experimental, provisional or non-canonical source has accumulated sufficient evidence through portable development to justify promotion into current corrigible Concord architecture.

Promotion must preserve the frozen/provisional source as provenance.

### BPM-D5 — HOLD / FURTHER DEVELOPMENT REQUIRED

Evidence, source ownership, conflict, failed regression or unresolved architecture prevents safe integration.

### BPM-D6 — SOURCE-SPECIFIC CORRECTION / OTHER BOUNDED ROUTE

Use where a justified source correction does not fit D1–D5. State why the route is necessary.

These are dispositions, not quality rankings.

## 9. Integration construction rules

Where integration is justified:

1. preserve source provenance;
2. do not silently rewrite historical/frozen sources;
3. prefer additive companion/cross-reference where replacement is unnecessary;
4. preserve legitimate system ownership;
5. preserve UNKNOWN/DISPUTED states;
6. do not import portable host syntax unless Concord needs it;
7. do not transfer authority merely because the portable module represents a decision;
8. distinguish recovered architecture from newly developed architecture;
9. record the portable evidence that justified the return;
10. identify required interface regressions before declaring integration complete.

## 10. Architectural interface regression

A source-side artifact is not integrated merely because it has been written.

Retest materially affected interfaces.

Regression should ask:

- Does the returned architecture conflict with its source kernel?
- Does it duplicate or seize a neighbouring system's function?
- Does it create authority?
- Does it erase uncertainty?
- Does it change dependency semantics?
- Does it weaken consent, privacy, rights, safe-space or constitutional boundaries?
- Does it introduce circular evidence?
- Does it break current interface assumptions?
- Does it convert bounded evidence into universal claims?

Record bounded follow-ups separately from blocking failures.

Possible regression results:

- **PASS**
- **PASS WITH BOUNDED FOLLOW-UPS**
- **FAIL / HOLD**

Only PASS or PASS WITH BOUNDED FOLLOW-UPS may advance to integrated status.

## 11. One-cycle operating procedure

Once the evidence set is available, the normal BPM execution is one continuous cycle:

**1. SOURCE RESOLVE**
→ identify immediate source and material source family.

**2. COMPARE**
→ identify post-extraction/material portable-source deltas.

**3. CLASSIFY**
→ apply P/C/G/F/I/R/S and evidence provenance.

**4. DISPOSE**
→ choose BPM-D0 through BPM-D6.

**5. INTEGRATE IF JUSTIFIED**
→ create the smallest legitimate source-side artifact.

**6. REGRESS**
→ test affected architectural interfaces.

**7. FINALISE**
→ assign final back-propagation state.

**8. RECORD**
→ create module-specific permanent record and update portfolio register.

The cycle should stop only when:

- source ownership cannot be resolved;
- required evidence is missing;
- a materially new development problem has been exposed;
- integration requires a decision outside the method's authority;
- regression fails;
- or user/research review is genuinely required.

Routine intermediate confirmation is not methodologically necessary.

## 12. Back-propagation states

Portfolio states are:

- **NOT YET AUDITED**
- **AUDIT ACTIVE**
- **NO SOURCE CHANGE REQUIRED**
- **SOURCE UPDATE CANDIDATE**
- **AWAITING INTEGRATION / RETEST**
- **INTEGRATED / ARCHITECTURAL INTERFACE RETEST PASSED**
- **HOLD / FURTHER EVIDENCE REQUIRED**

These describe BPM state only and do not alter portable graduation status.

## 13. Permanent record requirement

Each completed audit should preserve:

- module and version;
- source/source-family;
- material deltas;
- evidence origin;
- classifications;
- disposition;
- source-side artifact(s), if any;
- regression result;
- bounded follow-ups;
- final state;
- methodological significance where unusual.

The Back-Propagation Register is the portfolio index.

The source-side architecture remains authoritative for integrated content.

## 14. Discrimination check

Before finalising, ask:

> **Would this audit still be considered successful if it returned no source change?**

If the answer is no, the process has become biased toward expansion.

A correct BPM result may be:

> **NO SOURCE CHANGE REQUIRED**

KCS Change Propagation demonstrated that a mature source may require only bounded refinements.

Future modules may legitimately require none.

The method must not reward document growth.

## 15. Provenance and anti-circularity

Portable validation may justify returning a refinement to the source.

Once returned, the updated source must not then be cited as independent evidence that the portable refinement was correct.

Maintain the direction:

**source → extraction → independent portable evidence → justified return**

Do not transform it into:

**portable claim → copied source claim → source cited as confirmation of portable claim**.

## 16. Relationship to Active Development

BPM is a maintenance/integration method, not a substitute for Active Development.

If back-propagation exposes a genuinely new unresolved problem requiring hypothesis formation, mechanism design or testing, route that problem into Active Development and place BPM on HOLD where necessary.

Do not solve substantial new architecture inside a nominal integration audit merely to complete the cycle.

## 17. Relationship to PMEDG

PMEDG ends with a graduated portable artifact.

BPM begins after graduation.

PMEDG evidence is an input to BPM, but BPM does not retroactively change whether the module graduated.

A later BPM failure may reveal a source-integration problem without invalidating portability, and a portable module may remain valid even when BPM-D0 determines that no source change is required.

## 18. Evidence from completed cycles

### SMM
Pattern: substantial evidence-supported operational/interface refinements returned through a bounded companion.

### STRA
Pattern: operational and failure-mode refinements returned without replacing the source kernel.

### KCS Change Propagation
Pattern: already-mature source required only bounded refinement, demonstrating methodological discrimination.

### Architectural Unit Resolution
Pattern: experimental source method accumulated enough portable evidence for promotion into current corrigible methodology while frozen provenance was preserved.

### Contextual Wrapper Architecture
Pattern: portable development exposed under-representation in the primary source; wider ESCP source recovery found existing Concord architecture; back-propagation therefore performed source-family consolidation rather than falsely claiming invention.

Together these cases establish that BPM must support multiple legitimate dispositions.

## 19. Current validation status

BPM v1.0 has been derived from five completed module cycles with materially different outcomes.

This establishes repeated operational use across several source conditions.

It does not establish universal validity.

The method remains corrigible and should itself be reviewed when:

- a new disposition type appears;
- a regression exposes a systematic blind spot;
- source-family resolution repeatedly fails;
- portfolio use shows classification ambiguity;
- or BPM begins producing unnecessary architecture/document growth.

## 20. Compact rule

> **Resolve widely enough to know what changed.**
>
> **Classify why it changed.**
>
> **Return only what belongs.**
>
> **Preserve who owns it.**
>
> **Retest what it touches.**
>
> **Record what happened.**
>
> **Treat no-change as a valid success.**
