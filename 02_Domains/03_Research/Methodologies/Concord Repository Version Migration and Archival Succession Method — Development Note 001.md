# Concord Repository Version Migration and Archival Succession Method — Development Note 001

**Status:** ACTIVE METHODOLOGY DEVELOPMENT / FIRST FORMAL APPLICATION: V1.2 → V1.3

## 1. Purpose

The Concord has now passed through multiple repository generations. Version transition is therefore no longer an exceptional housekeeping event. It is a recurring civilisational-development process that should be explicit, repeatable, auditable and resistant to accidental historical loss.

This method governs transition from one live Concord repository/version to its successor.

It is not primarily a file-copy method.

It is a method for deciding:

- what remains live;
- what has graduated;
- what remains unfinished;
- what is superseded;
- what must be preserved;
- what must migrate;
- what must not migrate;
- how the predecessor becomes an intact Historical object;
- and when the successor may legitimately become the live Concord architecture.

> **Migrate the Living Result; Archive the Developmental Path.**

## 2. Repository succession model

A version transition should normally follow:

**LIVE VERSION N**
→ architecture and state assessment
→ migration map
→ selective extraction
→ successor construction
→ dependency/interface validation
→ migration audit
→ successor activation
→ predecessor freeze
→ Historical custodianship

The transition is therefore a form of **architectural succession**, not repository cleanup.

> **New Version != Cleaned Old Version**

> **Version Migration != Bulk File Transfer**

## 3. Whole-version archival principle

Once Version N+1 becomes the validated live architecture, Version N becomes a coherent predecessor state under the custodianship of Historical.

The predecessor should normally remain structurally intact.

Its value includes not only document contents but:

- folder relationships;
- classification decisions;
- development states;
- duplicate or competing formulations;
- unresolved questions;
- experimental branches;
- mistakes;
- abandoned paths;
- transitional structures;
- naming conventions;
- contextual assumptions;
- and evidence of how the architecture changed.

> **Archive the Predecessor as a Coherent State, Not Merely as a Collection of Obsolete Files.**

Post-migration cleanup of the predecessor can destroy historical information and should therefore be avoided except where required for safety, legality, repository integrity or an explicitly documented archival correction.

## 4. Historical custody model

Historical has two different but related responsibilities after succession.

### 4.1 Live Historical architecture

The current version contains the active Historical-domain systems required by the living Concord.

### 4.2 Archived predecessor states

Prior repositories/versions are preserved as complete Historical objects.

Historical custody of a predecessor does **not** require copying all predecessor material into the current repository.

> **Historical Custody != Historical Duplication Inside the Live Architecture**

A current system may point backward to archived derivation without carrying that derivation forward.

## 5. Primary migration test

For every candidate object ask:

> **Does the successor need this object to operate, understand its current architecture, continue genuinely unfinished work, or verify an essential live dependency?**

If yes, it is a migration candidate.

If no, and its value is primarily:

- development history;
- provenance;
- superseded architecture;
- completed experimentation;
- closed sketches;
- derivational evidence;
- regression history;
- prior test states;
- completed comparative research;
- obsolete organisation;
- or historical context,

it should normally remain in the archived predecessor.

This is deliberately stricter than asking whether an object is useful or interesting.

## 6. Migration classes

Each significant object should be assigned one or more of the following migration dispositions.

### M1 — MIGRATE CURRENT

Current architecture required by the successor.

Examples:
- constitutional constraints;
- live domain specifications;
- current cross-domain architecture;
- current operational protocols;
- current authoritative schemas.

### M2 — MIGRATE GRADUATED RESULT

The current result of development migrates, but its developmental path remains archived.

Examples:
- graduated portable module;
- validated mechanism;
- established principle;
- current formal specification.

### M3 — CONTINUE ACTIVE DEVELOPMENT

The work is genuinely unfinished and intentionally continues in the successor.

Only the material necessary to continue the work should migrate. Completed precursor history may remain archived.

### M4 — MIGRATE ESSENTIAL DEPENDENCY OR SUMMARY

The full source need not migrate, but the successor requires a concise derivation summary, dependency description, provenance pointer, interface contract or other bounded information product.

### A1 — ARCHIVE IN PREDECESSOR

No physical migration required. The predecessor version is the authoritative historical location.

### A2 — ARCHIVE WITH LIVE REFERENCE

Remain in predecessor, but current architecture should explicitly reference the archived source because provenance or interpretation materially depends on it.

### X1 — EXCLUDE / SUPERSEDED

Do not migrate as live architecture. Preserve only through the predecessor archive.

These classes describe migration disposition, not civil authority.

## 7. Functional reclassification rule

Migration must not assume that the old folder location identifies the correct successor owner.

For each migrated object determine:

**Current location**
→ **actual function**
→ **architectural type**
→ **legitimate owner**
→ **successor destination**

The governing ontology remains:

**Repository Folder != System != Function != Operational Domain != Authority**

A development note in Governance may belong to Law.
A research method may become a Portable Module.
A protocol developed inside Economy may become cross-domain architecture.
A folder named Participation may actually be Research.

> **Where Something Was Developed Does Not Determine What It Is.**

## 8. Result/provenance separation

Where development has produced a live result, separate:

**CURRENT RESULT**
from
**DEVELOPMENTAL PROVENANCE**

The current result migrates where required.

The developmental provenance normally remains in the predecessor.

Examples:

### Portable Modules
Migrate:
- current graduated module;
- required current interface specification.

Archive:
- extraction history;
- candidate versions;
- graduation discussion;
- completed tests;
- superseded variants;
- regression history unless needed operationally.

### Active Development
Migrate:
- unfinished work intentionally continued;
- graduated outputs needed by live architecture.

Archive:
- completed sketches;
- superseded candidate architecture;
- closed development notes;
- completed experimental sequences.

### Comparative research
Migrate:
- current findings needed by architecture;
- genuinely active unresolved research.

Archive:
- completed comparison corpus;
- derivational passes;
- superseded hypotheses;
- source-processing history.

### Unified Paths of Light
Migrate:
- consequential current ethical findings;
- bounded provenance/derivation summary where required.

Archive:
- extraction corpus;
- comparison files;
- compression passes;
- methodological history;
- completed exploratory work.

## 9. Migration should reduce accidental inheritance

A successor should not inherit an object merely because it existed in the predecessor.

Every migration creates an implicit claim that the object remains relevant to the living architecture.

Therefore:

> **Copying Is an Architectural Decision.**

Bulk copying can accidentally preserve:
- obsolete assumptions;
- old authority relationships;
- misleading folder ownership;
- superseded terminology;
- dead development paths;
- duplicated authorities;
- unresolved experimental structures.

Selective migration is therefore a form of architectural control.

## 10. Domain-gap rule

A successor must not invent or migrate speculative material merely to make a domain appear complete.

Where a genuine civil domain exists but its operational architecture is incomplete, the successor should carry:

- domain purpose;
- boundaries;
- authority limits;
- known interfaces;
- established principles;
- current graduated mechanisms;
- explicit system gaps;
- live open questions where needed.

> **A Valid Domain Can Exist Before Its Operational Architecture Is Complete.**

> **Architectural Honesty Is More Valuable Than Folder Density.**

## 11. Open-question rule

Do not automatically migrate every historical open-question register.

Questions should be classified as:

- still live and consequential → migrate;
- resolved with current result → migrate result, archive question history;
- abandoned/superseded → archive;
- locally relevant but centrally indexed → migrate appropriate reference only.

The predecessor preserves the historical question state.

## 12. Naming rule

Do not automatically carry predecessor names into the successor.

Migration should distinguish:
- function;
- boundary;
- relationship;
- expectation created by name.

Where major architectural reorganisation occurs, perform a naming and expectation audit before finalising successor folder names.

> **Define the Function First. Derive the Boundary Second. Name the Structure Last.**

## 13. Migration phases

### Phase 1 — Freeze the target question

Define why a new version is being created and what kind of architectural change justifies succession.

### Phase 2 — Inventory the predecessor

Identify major roots, systems, modules, development areas, applications, open questions and experimental branches.

### Phase 3 — Discover target architecture

Determine the successor's intended civilisational topology before bulk movement.

Do not let predecessor folder structure silently become the target architecture.

### Phase 4 — Build migration map

For each major object record:
- predecessor location;
- actual function;
- architectural type;
- current state;
- legitimate owner;
- migration class;
- target location if migrating;
- archive/reference treatment;
- reason.

### Phase 5 — Resolve mixed folders

Descend into any folder containing multiple architectural types or owners.

Stop descending when the migration disposition is sufficiently uniform and no live dependency is likely to be lost.

### Phase 6 — Separate result from provenance

Apply the primary migration test.

Avoid carrying complete developmental corpora where a current result and archive pointer are sufficient.

### Phase 7 — Construct successor

Create the successor architecture from the migration map rather than by cloning and cleaning the predecessor.

### Phase 8 — Migrate live objects

Move/copy only approved live objects, current results, continuing work and essential summaries/dependencies.

### Phase 9 — Validate interfaces and dependencies

Check:
- missing dependencies;
- broken cross-references;
- duplicate authorities;
- ownerless functions;
- stale names;
- missing current modules;
- active work accidentally left behind;
- historical material accidentally treated as live.

### Phase 10 — Conformance audit

Test whether the successor can operate and be understood without requiring undocumented knowledge from the migration process.

Where an archived predecessor is a legitimate dependency, that dependency must be explicit.

### Phase 11 — Activation decision

Do not declare the successor live merely because files have been copied.

Activation requires a documented migration/graduation decision that the successor represents the intended current Concord architecture.

### Phase 12 — Predecessor archival succession

After activation:
- freeze the predecessor;
- identify it as superseded but preserved;
- place it under Historical custodianship;
- preserve branch/version context as appropriate;
- establish successor/predecessor references.

The predecessor should not be retroactively rewritten to resemble the successor.

## 14. Migration register minimum fields

A future standard migration register should contain at least:

| Field | Purpose |
|---|---|
| Source version | predecessor state |
| Source path/object | exact origin |
| Object/function | what it actually is |
| Architectural type | domain/cross-domain/module/etc. |
| Current status | live/developmental/graduated/superseded/etc. |
| Legitimate owner | current civil owner |
| Migration class | M1-M4/A1-A2/X1 |
| Target path | successor destination if any |
| Dependencies | required linked systems |
| Archive reference | predecessor provenance location |
| Reason | migration decision |
| Validation status | checked/not checked/issues |
| Notes | exceptions/ambiguities |

## 15. Success criteria

A successful migration should produce a successor that is:

- smaller where historical accumulation is unnecessary;
- clearer in ownership;
- closer to actual civilisational structure;
- explicit about gaps;
- free of accidental authority inheritance;
- able to trace consequential provenance;
- able to continue active work;
- able to locate archived derivation;
- and independently understandable as the current architecture.

Success is not measured by percentage of files copied.

> **Migration Completeness != File Transfer Completeness**

## 16. Failure modes

### FM-01 — Clone and clean
Copy everything and reorganise afterward.

Risk: accidental inheritance and destruction of predecessor state.

### FM-02 — Historical duplication
Copy all provenance into the successor merely because Historical owns it.

Risk: immediate recreation of repository accumulation.

### FM-03 — Result loss
Archive development corpus without migrating the current result.

Risk: successor loses operational architecture.

### FM-04 — Active-work abandonment
Treat all development as historical even where unresolved work must continue.

Risk: live research disappears at version boundary.

### FM-05 — Folder-name inheritance
Assume predecessor folder name equals successor owner.

Risk: structural mistakes become permanent.

### FM-06 — False completeness
Populate missing domains with speculative material to make them look mature.

Risk: research is mistaken for current architecture.

### FM-07 — Provenance severance
Migrate result without sufficient reference to its derivation where interpretation depends upon it.

Risk: current architecture becomes historically opaque.

### FM-08 — Archive rewriting
Reorganise predecessor after succession.

Risk: destruction of historical structure and state.

### FM-09 — Premature activation
Declare successor live before dependency/interface audit.

Risk: hidden functional gaps.

### FM-10 — Eternal migration
Continue analysing every predecessor file after sufficient classification has been achieved.

Risk: migration itself becomes an endless research programme.

Use sufficient-depth classification: descend only where needed to protect live architecture and dependencies.

## 17. Periodicity

Version migration should occur when architectural development justifies a new coherent civilisational state, not merely because a calendar interval has elapsed.

Potential triggers include:
- major topology change;
- accumulated graduated architecture making current organisation misleading;
- major domain reorganisation;
- substantial reduction of development-state material;
- new civilisational abstraction layer;
- architectural naming/boundary correction;
- repository complexity materially impairing comprehension or operation.

Periodic review may ask whether succession is warranted, but should not force version creation.

## 18. Relationship to other Concord methods

This method is complementary to, not a replacement for:

- Domain Development, Validation and Graduation;
- PMEDG;
- portable-module back-propagation;
- Reality Trees;
- Blaineyan Reasoning;
- KCS/change propagation;
- Historical provenance architecture.

Domain graduation determines whether a domain architecture is sufficiently developed.

PMEDG governs portable-module extraction/development/graduation.

This method governs **succession of the repository/civilisational version containing those objects**.

## 19. First formal application — V1.2 → V1.3

The current migration is the first formal worked application.

Important findings already produced by the application include:

1. V1.2 mixes a map of the civilisation, a map of its design tools and a map of its development journey.
2. V1.3 should primarily resemble the living civilisation.
3. Research and Development belongs within the Research domain.
4. Portable Modules remain root-visible but are custodied by Historical.
5. predecessor repositories become whole-version Historical objects.
6. development provenance usually need not be recopied.

## 20. Development status

This method should remain corrigible during the V1.2 → V1.3 migration.

Any failure, ambiguity or unnecessary work caused by the method should be recorded and used to refine it before graduation.

If the method survives the migration and proves reusable, its **current operational form should migrate into V1.3**.

This development note and the detailed history of how the method was derived should remain in archived V1.2.

That outcome would itself demonstrate the method:

> **Migrate the Living Result; Archive the Developmental Path.**


## 21. Legacy-established architecture rule

The first Portable Modules migration pass exposed a historical asymmetry.

Some Concord systems, methods or modules were developed, tested, adopted and incorporated into working architecture **before the later graduation methodologies existed or reached their current form**.

Absence of a PMEDG, domain-graduation or later validation record must therefore not be interpreted as evidence that the older system was undeveloped.

> **Absence of Later-Method Certification != Absence of Earlier Development or Operational Maturity**

A later methodology may improve how future systems are validated. It does not retroactively erase the architectural state that existed before that methodology.

Migration must distinguish at least:

1. **FORMALLY GRADUATED** — passed the applicable later formal methodology;
2. **LEGACY-ESTABLISHED** — demonstrably developed/adopted/incorporated before the formal methodology existed or stabilised;
3. **ACTIVE CANDIDATE** — genuinely still developmental;
4. **SUPERSEDED/ARCHIVAL** — no longer live.

### Legacy-established assessment

Where formal graduation evidence is absent, source-resolve the object's actual historical and operational state. Evidence may include:

- explicit adoption into Concord architecture;
- repeated operational use by other systems;
- dependencies from current architecture;
- integration into constitutional/domain/cross-domain systems;
- completed earlier testing or adversarial examination;
- later work treating the object as an established dependency rather than a proposal;
- stable current specification;
- evidence that the apparent status label predates or was never reconciled with later methodology.

Do not manufacture retrospective certification.

Instead record the object as **LEGACY-ESTABLISHED / RETROSPECTIVE STATUS REVIEW REQUIRED** where the evidence supports that classification.

A later methodology may then be used for **retrospective conformance checking**, but failure to have historically undergone that later process is not itself a failure.

> **Retrospective Validation May Test a Legacy System; It Must Not Rewrite the Fact That the System Previously Operated.**

This rule is especially important during repository succession because otherwise newer process standards can create false negatives and accidentally remove functioning inherited architecture.


## 22. Deferred legacy-state reconciliation

The same historical asymmetry identified for Portable Modules can occur anywhere in the Concord.

Earlier architecture may remain physically located in:
- Active Development;
- sketches;
- candidate-principle folders;
- experimental areas;
- research folders;
- old development notes;
- provisional architecture folders;
- or other locations whose labels imply an earlier maturity state,

even though later Concord systems already adopted, depended upon or operationalised the work.

Therefore:

> **Development Location != Current Development State**

> **Old Status Label != Necessarily Current Architectural Status**

Migration must not require complete retrospective maturity reconciliation before V1.3 can be constructed. For a corpus of this size, doing so could turn succession into an indefinite audit and obscure the cleaner architecture needed to detect the anomalies.

### Conservative migration rule

Where an object appears developmental but there is credible evidence that it may be current, incorporated, depended upon or historically established:

1. do not discard it solely because of location or stale status label;
2. source-resolve enough to determine whether leaving it behind creates a material risk;
3. if uncertainty remains and current relevance is plausible, migrate the minimum necessary object/state;
4. mark it **LEGACY STATUS UNRESOLVED — POST-MIGRATION AUDIT REQUIRED**;
5. do not automatically grant it new authority merely because it migrated.

This creates a bounded preference for preservation where classification uncertainty could otherwise destroy live architecture.

> **Migration Under Status Uncertainty Should Preserve Recoverability Without Manufacturing Authority.**

### First-stage V1.3 audit

A **Legacy Architecture State and Graduation Reconciliation Audit** should be one of the first major V1.3 tasks after structural migration and initial conformance checking.

Its purpose is to identify objects whose physical location, document header or recorded development state no longer matches their actual architectural maturity.

The audit should search especially for:
- operational systems still labelled development;
- incorporated principles still labelled candidate;
- modules used as dependencies but never formally graduated;
- completed development remaining in active queues;
- sketches whose results were adopted elsewhere;
- duplicated live and developmental forms;
- systems whose graduation predates the graduation methodology;
- stale TODO/open-question markers already resolved by later architecture;
- abandoned work accidentally migrated as live;
- current architecture accidentally left only in predecessor archives.

Possible outcomes:

**CONFIRM CURRENT / LEGACY-ESTABLISHED**
→ retain live; record status reconciliation.

**FORMALLY GRADUATE / NORMALISE**
→ where current methodology can appropriately confirm the existing architecture.

**RETURN TO DEVELOPMENT**
→ where operational use exceeded actual validation and further work is needed.

**ARCHIVE**
→ where work is completed, superseded or no longer live.

**SPLIT**
→ where a developmental source contains both live result and historical provenance.

**DUPLICATE RESOLUTION**
→ establish one current authority and archive/reference the rest.

### Why defer the full audit until V1.3

V1.2's development-oriented structure makes stale status difficult to distinguish from genuinely active development.

V1.3's domain-normalised structure should make anomalies easier to see because:
- current architecture will have explicit owners;
- active Research will be separated from operating domains;
- current Portable Modules will be separated from candidates;
- predecessor provenance will remain outside the live corpus;
- cross-domain architecture will have explicit identity;
- system gaps will be visible rather than hidden among development material.

Therefore the migration should perform **sufficient safety classification**, while V1.3 performs the **full maturity reconciliation**.

> **Migration Establishes the Cleaner Evaluation Space; V1.3 Uses That Space to Reconcile Legacy State.**
