# BTA Adversarial Test 002 — Branch/Merge Relational Information Loss

**Author:** Alexander C. Blainey — Independent Researcher  
**Project:** The Concord Framework  
**Framework Version:** Concord V1.3  
**Test Target:** Bounded Transition Architecture 001 — Consequential State-Change Integration Grammar  
**Prior Test:** BTA Adversarial Test 001 — Hidden Non-Propagation Dimension  
**Epistemic Lens:** Evaluation-Space Completeness Problem (ESCP)  
**Status:** ADVERSARIAL DEVELOPMENT TEST / NON-CANONICAL  
**Date:** September 2026

---

# 1. Test purpose

Test whether BTA can correctly represent:
- multiple source states;
- many→1 topology;
- provenance;
- surviving duties;
- non-propagation;
- authority;
- interface gates;
- resulting state;

while losing a consequential relation that existed **between** source branches.

The test is designed to determine whether the relational gap found in Test 001 independently reappears outside genomics.

---

# 2. Adversarial construction

Two independently operated infrastructure subsystems, A and B, are to be merged into one coordinated service C.

Each subsystem is individually valid.

Assume BTA correctly represents:

`A + B → C`

For both A and B:
- prior state vectors are complete within their local architectures;
- operational authority is valid;
- transition authority is valid;
- interface gates pass;
- assets and resources are accounted for;
- duties survive correctly;
- obsolete permissions terminate;
- provenance is retained;
- dependencies known to each subsystem are exposed;
- no identity, ownership, authority or liability is silently propagated;
- the resulting C state is internally valid.

On an object/node basis, the merge appears correct.

---

# 3. Hidden relation

A and B were independently configured so that each provided fallback capacity for the other during a rare failure mode.

Neither subsystem's ordinary local state requires a field saying:

`I am the other's independent fallback.`

The resilience property exists in the relation:

`R(A,B) = FailureDiversity + MutualFallback`

The merge into C standardises:
- control architecture;
- maintenance process;
- power conditioning;
- software;
- operational response;
- or another shared failure-sensitive layer.

After the merge, all represented functions of A and B remain present in C.

However, their **independent failure diversity** disappears.

The new system therefore retains nominal capacity while losing a relational recovery property.

---

# 4. Why node/state correctness is insufficient

Before:

`State(A) = valid`

`State(B) = valid`

`Relation(A,B) = independent fallback diversity`

After:

`State(C) = valid`

But:

`Relation(A,B)`

no longer exists in its prior form.

If BTA represents only the source objects, destination object, dependencies and transferred/surviving attributes, the merge can be locally correct while system resilience falls.

Therefore:

> **Preservation of Source-State Content != Preservation of Relational System Function.**

---

# 5. DependencyRefs challenge

Could the fallback relation simply be a dependency?

Possibly, if the wider architecture already represents it as such.

But the adversarial condition is that the relation is not encoded as a conventional operational dependency.

A and B can each function normally without the other.

The value appears specifically under a rare contingency.

Thus:

`NormalOperationDependency = false`

while:

`ContingentRecoveryRelation = true`

This matters because a dependency architecture optimised around normal functional prerequisites may not expose the relation.

Therefore:

> **Absence of Normal Dependency != Absence of Consequential Relationship.**

---

# 6. ESCP structure

The merge evaluator may correctly verify every represented BTA dimension.

Let:

`D_A = represented transition dimensions`

and let the missing relation be:

`d_r = contingent independent-recovery relation`

Then:

`Accurate(BTA | D_A) = true`

while:

`d_r ∉ D_A`

and:

`d_r ∈ D_R^{MergeDecision}`

The merge can therefore pass every represented check while producing a materially weaker system.

This is not measurement error.

It is evaluation-space incompleteness.

---

# 7. Test result

**RESULT: THE RELATIONAL GAP FROM TEST 001 REAPPEARS IN A STRUCTURALLY DIFFERENT DOMAIN.**

Test 001:
- nominal object: genomic representation;
- missing relation: consequence affecting a biological relative.

Test 002:
- nominal objects: infrastructure subsystems;
- missing relation: independent fallback/failure-diversity value between source branches.

The common structure is:

`CorrectObjectTransition`

plus:

`UnrepresentedMaterialRelation`

leading to:

`PotentiallyIncorrectConsequentialTransition`

This substantially weakens the hypothesis that Test 001 exposed only a genomics-specific edge case.

---

# 8. Branch/merge-specific finding

A many→1 transition has a special risk.

The merge may preserve:
- both source functions;
- both source records;
- all explicitly represented duties;
- all assets;
- all permissions that should survive;
- all provenance;

while destroying a property that existed only because the sources were distinct.

Therefore:

> **Merge of Functions != Preservation of Value Created by Separation.**

And:

> **Some System Properties Exist in the Relation Between Branches, Including Their Continued Independence.**

This is particularly relevant to:
- redundancy;
- failure diversity;
- checks and balances;
- independent verification;
- epistemic diversity;
- jurisdictional separation;
- competitive alternatives;
- backup systems;
- heterogeneous intelligence.

---

# 9. Symmetric branch risk

The inverse can occur in 1→many transitions.

A branch may correctly produce B and C from A while creating a new relation between B and C that did not exist before.

Examples include:
- conflicting authority;
- duplicated control;
- shared hidden dependency;
- correlated failure;
- incompatible obligations;
- rivalry over a formerly singular resource.

Thus:

> **Branching Can Create Relational State That Was Not an Attribute of the Parent.**

This parallels Test 001's finding that consequential state can be generated without attribute transfer.

---

# 10. Relational transition candidate

Two independent tests now support a provisional BTA concept:

`RelationalTransition = <RelationRef, ParticipantRefs, PriorRelationalState, TransitionEffect, NextRelationalState, Materiality, AuthorityOrConstraintRefs, Provenance, Uncertainty>`

This is deliberately provisional.

BTA should not attempt to own the semantics of every relationship.

It may instead need to:
1. identify that a material relationship exists;
2. record that the transition preserves, changes, creates or terminates it;
3. reference the system that owns its substantive semantics.

---

# 11. Relation to consequence horizon

Test 001 proposed:

`ConsequenceHorizon = <DirectObjectRefs, MaterialRelationshipRefs, MaterialAffectedPartyRefs, GeneratedConsequenceRefs, UnknownOrUnresolvedExternalEffectState, Provenance>`

Test 002 independently supports:
- `MaterialRelationshipRefs`;
- generated relational consequences;
- external effects beyond nominal object state.

This increases confidence that a **consequence horizon / relational transition layer** may be a genuine missing BTA component.

It does not yet establish the final field structure.

---

# 12. New candidate invariants

Supported by Tests 001 and 002:

> **The Boundary of the Transition Object != Necessarily the Boundary of the Transition's Consequences.**

> **Transition Can Generate Consequential Relational State Without Transferring an Existing Attribute.**

New from Test 002:

> **Preservation of Source-State Content != Preservation of Relational System Function.**

> **Merge of Functions != Preservation of Value Created by Separation.**

> **Branching or Merging Can Create, Alter or Destroy Material Relations Even When Every Participating Object Is Correctly Represented.**

---

# 13. Implication for transition topology

BTA currently supports:
- 1→1;
- 1→many;
- many→1;
- many→many;
- 1→none;
- unresolved.

Test 002 indicates that cardinality alone is insufficient.

Topology should eventually distinguish:

`ObjectTopology`

from:

`RelationTopology`

A many→1 object transition may simultaneously be:

`many relational nodes → terminated independence relation`

or:

`many relational nodes → new internal relation`

Thus:

> **Object Cardinality != Relational Topology.**

---

# 14. Anti-bureaucratisation boundary

This does not imply that every transition must map every possible relation.

The same materiality rule applies.

Relational review should escalate where:
- the transition is consequential;
- the relation plausibly carries safety, rights, resilience, authority, consent, standing, resource, continuity or epistemic value;
- the transition is difficult to reverse;
- or loss of the relation would be difficult to detect after transition.

---

# 15. Reversibility implication

This test reinforces ESCP's connection between reversibility and dimensional discovery.

If the merge is reversible, discovery that independent failure diversity was lost may permit restoration.

If irreversible, the missing dimension may only become visible after the corrective option has disappeared.

Therefore:

> **Where relational completeness is uncertain, reversibility can preserve the option to recover relational value discovered later.**

---

# 16. Development conclusion

The relational finding has now survived two structurally different adversarial tests.

It should no longer be treated merely as a genomics-specific anomaly.

However, before modifying the core BTA grammar, one further adversarial class should test whether the same structure appears in **conflicting transition authority**, where multiple actors are each legitimate over different represented dimensions.

If relational/external-effect incompleteness reappears there, the case for integrating a consequence-horizon/relational-transition mechanism becomes strong.
