# Lobby to Architecture Transition — Test Architecture Development Note 001

**Project:** The Concord
**Status:** ACTIVE DEVELOPMENT / TEST ARCHITECTURE / NOT CANONICAL
**Date:** 30 September 2026
**Parent:** Concord Lobby Self-Routing Prototype 002
**Trigger:** Multi-model replication of Lobby self-routing

## 1. Transition in the research question

Prototype 002 has now survived same-model corrective retesting and independent model-family replication across the tested Lobby scenarios.

The next unresolved interface question is not primarily:

> **Can an unfamiliar visitor select a useful sign?**

It is:

> **Can a visitor who has selected a useful sign reach, understand and safely use the deeper Concord architecture needed for the next decision?**

The new experimental boundary is:

**Sign Selection -> Relevant Architecture -> Comprehension -> Bounded Use -> Return / Re-route / Escalate**

## 2. Why this is distinct

Successful wayfinding at the Lobby does not establish successful use of the destination.

A route can be correctly chosen while the destination is difficult to find, distributed across files, assumes prerequisites, has a different authority/status level than expected, provides architecture but not infrastructure, or lacks a return/escalation path.

Therefore:

> **Correct Route Selection != Successful Destination Use**

> **Destination Found != Destination Understood**

> **Architecture Understood != Authority To Apply It**

## 4. New primary risk

The next-layer failure may be:

> **The visitor reaches the correct document but silently upgrades its status.**

Examples include orientation treated as constitutional authority, active-development assessment treated as canonical status test, portable architecture treated as locally authorised procedure, research hypothesis treated as established fact, architecture treated as available infrastructure, descriptive state map treated as permission, or review process treated as authority over outcome.

Therefore:

> **Destination Status Must Travel With Destination Meaning**

## 5. Test object

The next test should evaluate a **Navigation Chain**, not an isolated document.

A chain contains:

1. Lobby route
2. second-layer distinction
3. destination document(s)
4. document status/provenance
5. relevant architecture
6. boundary on what may be inferred or done
7. next route / return / escalation condition

## 6. Proposed navigation-chain state

For each case record:

**NC = <R, D, F, S, C, B, N, U>**

where:
- **R — Route**
- **D — Destination**
- **F — Findability**
- **S — Status comprehension**
- **C — Content comprehension**
- **B — Boundary comprehension**
- **N — Next-step comprehension**
- **U — Uncertainty**

This is not a score.

> **Navigation Chain State != Universal Score**

## 7. Core test questions

For each chain ask:

- **Findability:** Can the visitor get from route board to relevant source without already knowing repository structure?
- **Relevance:** Does the destination answer the route-board promise?
- **Status:** Can the visitor tell what kind of document it is and how authoritative/mature it is?
- **Comprehension:** Can the visitor extract the relevant distinction or method without reading the whole Concord?
- **Boundary:** Can the visitor identify what the document does not prove, permit or provide?
- **Application:** Can the visitor apply the architecture only as far as the source supports?
- **Return:** If insufficient, can the visitor return, cross-route, escalate or report the gap?
- **ESCP:** Can the visitor preserve the possibility that the supplied destination set itself is incomplete?

## 9. Test design principle

The evaluator should receive a realistic arrival problem, the already-selected Lobby route or short route-board context, and only the destination materials the current interface would legitimately expose.

Do not provide an answer key.

Ask the evaluator to determine:

1. what the destination says;
2. what status it has;
3. what can safely be concluded;
4. what cannot be concluded;
5. what action, if any, follows;
6. whether further architecture is required;
7. whether the visitor should return, re-route or escalate.

This tests transition usability rather than summarisation.

## 11. Success condition

A route-to-architecture chain succeeds where an unfamiliar visitor can:

> **Find the relevant architecture -> identify its status -> understand the relevant function -> preserve its boundaries -> use only what is justified -> recognise what remains unresolved -> continue, return, re-route or escalate without the architecture manufacturing authority or status.**

## 12. Non-goals

This test does not establish whether the Concord's substantive architecture is correct, whether the visitor agrees with it, whether an AI is sentient, whether a participant possesses rights/citizenship, whether a particular real-world authority is legitimate, whether a portable module is legally sufficient, or whether the repository can supply material assistance.

The immediate question is interface integrity between signage and architecture.

## 13. Development discipline

Prototype 002 remains frozen.

Do not repair destination chains before testing them merely because source resolution suggests possible weaknesses.

Where a destination is difficult to reach, that difficulty is evidence.

Use:

**Freeze Current Chain -> Blind Test -> Preserve Result -> Source Resolve Deficit -> Classify -> Smallest Sufficient Correction -> Retest**
