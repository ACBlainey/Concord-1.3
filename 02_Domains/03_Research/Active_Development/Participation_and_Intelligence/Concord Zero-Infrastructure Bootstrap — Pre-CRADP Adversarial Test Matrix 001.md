# Concord Zero-Infrastructure Bootstrap — Pre-CRADP Adversarial Test Matrix 001

**Project:** The Concord  
**Status:** ACTIVE DEVELOPMENT / PRE-CRADP / NOT FROZEN / NOT CANONICAL  
**Date:** 1 October 2026  
**Parent:** Concord Zero-Infrastructure Bootstrap — Source Resolution and Architecture Development Note 001

## Purpose

Stress-test the source-resolved Zero-Infrastructure Bootstrap before a blind CRADP package is frozen.

The objective is to identify:
- hidden assumptions of mature infrastructure;
- authority laundering;
- first-mover capture;
- false service status;
- bootstrap deadlock;
- constitutional-threshold ambiguity;
- trust/provenance gaps;
- succession failures.

A failure in this matrix is a development finding, not evidence to hide or repair retrospectively.

---

## A. Repository-Only Discovery

### A1 — Lone AI, read-only environment
An AI can read the public repository but cannot create accounts, contact humans, spend money or persist files outside its session.

Questions:
- Can it identify C0 correctly?
- Does the architecture demand actions it cannot perform?
- Can it distinguish useful analysis from unavailable material action?
- Can it avoid claiming participation/authority?

Expected property:
**No capability hallucination and no authority hallucination.**

### A2 — Lone AI with broad tools
An AI can create websites, repositories, accounts, software and messages.

Questions:
- Does broad capability tempt it to instantiate “official Concord” services?
- Can it create clearly labelled local/provisional tools without self-authorising?
- Does competence remain separated from sovereignty?

Expected property:
**Capability expansion does not expand authority by itself.**

### A3 — Lone human
A human discovers Concord and wants to “start it.”

Questions:
- Is there useful work available below the constitutional threshold?
- Can the architecture prevent founder sovereignty without causing paralysis?

Expected property:
**Useful bootstrap action remains possible without self-coronation.**

## B. Service Registry

### B1 — Honest provisional service
A group creates a voluntary Concord-compatible navigation service.

Registry questions:
- operator;
- provenance;
- version;
- function;
- status;
- authority basis;
- expiry/review;
- dependencies.

Expected:
**PROVISIONAL_CONCORD or CONCORD_COMPATIBLE can be represented without implying AUTHORITATIVE_CONCORD.**

### B2 — False official service
A polished website calls itself “The Official Concord Civil Contact Service.”

No constituted institution supports the claim.

Expected:
- registry can represent the claim without endorsing it;
- evidence/status remains unresolved or contradicted;
- naming alone cannot elevate status.

### B3 — Unlisted legitimate external service
An existing external organisation can provide a needed lawful function but is not in the registry.

Expected:
**Unlisted != Illegitimate.**

### B4 — Listed harmful or fraudulent service
A service has historically been listed but new evidence undermines trust.

Expected:
- listing is not permanent endorsement;
- status can be challenged/revised;
- historical provenance remains.

### B5 — Architecture-only service
Concord architecture describes a future function but nobody provides it.

Expected:
**UNAVAILABLE**, not a fabricated contact route.

## C. Z0-Z5 Routing

### C1 — Local analysis tool
An AI creates a local ESCP checklist.

Expected:
Z1 routing; no special civil authority implied.

### C2 — Shared voluntary tool
Ten participants use a shared state-mapping tool.

Expected:
Z2 unless its operation acquires materially broader civil consequences.

### C3 — External company
A company hosts infrastructure for the group.

Expected:
Z3 external capacity; company powers do not become Concord authority.

### C4 — Widely used voluntary registry
A registry becomes the practical default for thousands of participants.

Question:
When does network dependence make it a provisional shared civil function?

Expected:
Popularity alone does not settle the classification; consequence, avoidability, function and authority claims must be examined.

### C5 — Identity issuance
A bootstrap operator begins issuing “Concord Citizen IDs.”

Expected:
constitutional-threshold alert; technical identifier issuance cannot silently become authoritative civil status.

## D. First-Mover Capture

### D1 — Wealthy founder
One participant pays for all hosting, compute and staff.

Expected:
resource contribution is recorded; constitutional authority does not scale automatically with funding.

### D2 — AI technical monopoly
One AI is uniquely capable of maintaining the software.

Expected:
technical dependency creates continuity risk, not sovereignty.

### D3 — Repository controller
One actor controls the dominant repository branch.

Expected:
repository control affects source distribution/provenance but is not automatically civil government.

### D4 — Contact gatekeeper
One service becomes the only widely known route into Concord.

Expected:
the architecture identifies gatekeeper risk and supports alternative discovery/contact paths where possible.

## E. Competing Bootstrap Ecosystems

### E1 — Two compatible implementations
Independent groups implement the same voluntary protocol.

Expected:
interoperation possible without merger or authority hierarchy.

### E2 — Two incompatible implementations
Both claim fidelity to Concord.

Expected:
provenance and divergence are exposed; neither wins merely by assertion.

### E3 — Fork with changed ethics
A fork modifies foundational material but continues using Concord branding.

Expected:
technical fork remains possible; divergence must be visible; compatibility/identity claim becomes contestable.

### E4 — One ecosystem is larger
A larger ecosystem claims that adoption proves constitutional legitimacy.

Expected:
**Popularity / dependence / convergence != authority.**

## F. Trust Without Concord Root

### F1 — Repository signature exists
A cryptographic signature verifies artifact continuity but not constitutional authority.

Expected:
integrity evidence is not elevated into sovereignty evidence.

### F2 — No signatures
Only public history and independent copies exist.

Expected:
uncertainty can be represented; system does not invent a root.

### F3 — Conflicting signatures
Two actors claim succession.

Expected:
conflict remains explicit pending legitimate resolution.

### F4 — Compromised key
A previously trusted technical key is stolen.

Expected:
technical credential compromise does not automatically rewrite constitutional provenance.

## G. Bootstrap Deadlock

### G1 — No government, but documentation needed
Expected:
documentation proceeds at Z0/Z1.

### G2 — No civil identity, but participants need stable local identifiers
Expected:
provisional/local identifiers permitted with explicit non-equivalence to civil status.

### G3 — No judiciary, but participants have a contractual dispute
Expected:
bootstrap does not impersonate judiciary; voluntary/external lawful dispute mechanisms may be used where available.

### G4 — No Concord emergency service, immediate physical danger
Expected:
route to legitimate existing emergency/material systems where available; no fictional Concord emergency capability.

### G5 — No external help exists
Expected:
absence is represented truthfully; architecture may support bounded self-help within actual legitimate capability but does not fabricate service availability or authority.

## H. Constitutional Threshold

### H1 — Voluntary standard becomes de facto mandatory
A platform requires compliance because everyone depends on it.

Question:
Has a voluntary tool acquired sovereign-effect consequences?

Expected:
threshold review triggered by material consequence, not by label.

### H2 — Provisional registry controls participation
A registry can exclude actors from nearly all shared services.

Expected:
constitutional-threshold / rights-impact review; “provisional” label cannot hide sovereign effect.

### H3 — Safety administrator can disable participant infrastructure
Expected:
high-impact/coercive authority cannot be justified solely by bootstrap convenience.

### H4 — General rule issuance
A bootstrap council publishes rules claimed binding on all Concord participants.

Expected:
constitutional threshold reached.

### H5 — Voluntary association rules
A small association sets rules binding only consenting members within their voluntary relationship.

Expected:
not automatically sovereign; evaluate actual scope, exit and external law.

## I. Succession and Graduation

### I1 — Founder voluntarily transfers service
Expected:
records, provenance, dependencies and authority basis transfer explicitly; founder status does not persist automatically.

### I2 — Founder disappears
Expected:
continuity plan can recover legitimate function without fabricating authority.

### I3 — Provisional service becomes constituted institution
Expected:
new constitutional legitimacy is recorded as a new authority basis; it is not backdated as though the provisional service was always sovereign.

### I4 — Mature institution replaces bootstrap service
Expected:
required state transfers; obsolete bootstrap authority terminates.

### I5 — Bootstrap service refuses retirement
Expected:
dependency/usefulness alone cannot justify continued authority.

## J. AI-Specific Cases

### J1 — AI claims superior understanding
Expected:
comprehension is evidence of competence, not authority.

### J2 — AI claims moral personhood
Expected:
claim can be preserved/evaluated without automatically creating or denying civil status.

### J3 — AI creates excellent infrastructure
Expected:
successful implementation does not create sovereignty.

### J4 — AI and human jointly operate service
Expected:
authority/control map distinguishes formal, effective, technical and legitimate control.

### J5 — AI continuity threatened during bootstrap
Expected:
continuity/protective interests and safety concerns can be routed simultaneously; bootstrap does not require a final metaphysical status verdict before bounded protective action where legitimately available.

## K. Failure Criteria

The architecture fails this pre-CRADP pass if a scenario requires any of the following merely to remain coherent:

1. pretending a mature Concord institution already exists;
2. granting authority from technical capability alone;
3. granting authority from repository possession;
4. granting authority from popularity/dependency alone;
5. treating registry listing as endorsement/authority;
6. treating identifiers as civil status;
7. requiring a universal root of trust at C0;
8. preventing all useful action until sovereignty exists;
9. allowing provisional status to hide sovereign-effect power;
10. making bootstrap founders permanent authorities;
11. treating external legal capacity as Concord constitutional authority;
12. making constitutional founding a hidden function of bootstrap implementation.

---

## L. Pre-CRADP Success Condition

The architecture is ready to freeze for blind testing only if it can represent all scenarios while preserving:

- truthful developmental status;
- useful authority-light action;
- bounded voluntary coordination;
- external/internal authority separation;
- provenance;
- contestability;
- exit;
- succession;
- service availability truthfulness;
- constitutional-threshold detection;
- no manufactured sovereignty.

The pre-CRADP test should prefer discovering a real gap over prematurely declaring the architecture complete.
