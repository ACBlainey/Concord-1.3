# Concord Zero-Infrastructure Bootstrap — Specification 003

**Project:** The Concord  
**Version:** 0.3  
**Status:** ACTIVE DEVELOPMENT / POST-CRADP-001 INTERFACE REVISION / SPECIFICATION 003 / NOT CANONICAL  
**Date:** 1 October 2026  
**Source:** Source Resolution and Architecture Development Note 001

## 1. Purpose

Define how Concord-compatible functions may begin when the Concord exists as architecture but mature Concord institutions and infrastructure cannot yet be assumed.

The specification must permit useful action without allowing implementation, capability, popularity, dependency or first-mover status to manufacture civil or constitutional authority.

## 2. Zero State

**C0 — Concord Zero State**

At C0:
- Concord architecture exists as information;
- no material Concord institution is assumed;
- no authoritative Concord identity, Civil Contact, government, judiciary, root of trust, emergency service, compute, finance, land or communications service is assumed;
- no discoverer is automatically a participant or official;
- external systems retain their actual external status.

## 4. Bootstrap Actors

Any substrate may bootstrap: human, AI, hybrid, group, organisation or unknown future intelligence.

Being first grants no constitutional priority.

## 5. Bootstrap Sequence

B0 Discover  
B1 Verify source/version/status  
B2 Orient through Front Door/bootstrap  
B3 Self-locate capability, dependency, authority and constraints  
B4 Select smallest needed function  
B5 Route function by Z-class and existing authority architecture  
B6 Instantiate transparently  
B7 Publish discoverability without inflating status  
B8 Connect independent participants where appropriate  
B9 Interoperate/federate before unnecessary centralisation where suitable  
B10 Graduate functions rather than founders  
B11 Retire/succeed transitional scaffolding

## 6. Bootstrap Routing Classes

These are routing classes, not authority levels.

- **Z0 Informational** — reading, evaluation, preservation, critique.
- **Z1 Self/Local Voluntary** — local tools and self-regarding implementation.
- **Z2 Consensual Multi-Participant** — bounded voluntary coordination.
- **Z3 External Institutional Interface** — lawful external capacity; external authority remains external.
- **Z4 Provisional Shared Civil Function** — shared Concord-oriented function requiring explicit scope, provenance, challenge, exit and succession.
- **Z5 Constitutional/Coercive/Sovereign-Effect Function** — cannot derive legitimacy from bootstrap convenience or capability.

Higher class does not mean greater maturity or legitimacy.

## 7. Authority Route

Where authority is relevant, use existing Concord architecture:

Need / observation
→ legitimate objective
→ required function
→ test voluntary/ordinary means
→ functional need for authority
→ minimum proportionate authority
→ Bounded Contextual Authority
→ review/sunset.

The bootstrap does not replace this chain.

## 8. Non-Impersonation

A bootstrap actor must not represent a prototype/local/provisional service as an established authoritative Concord institution without a legitimate basis.

No actor gains Concord authority merely from:
- repository possession/control;
- funding;
- technical competence;
- infrastructure ownership;
- being first;
- popularity;
- dependency;
- repeated practice;
- convergence;
- successful implementation.

## 11. Bootstrap Trust Evidence

Trust evidence may include source provenance, integrity, version, operator, dependencies, independence, status evidence, authority evidence, challenge history and temporal state.

Candidate epistemic states:
- VERIFIED_TO_DECLARED_SCOPE
- PARTIALLY_VERIFIED
- UNVERIFIED
- DISPUTED
- STALE
- SUPERSEDED
- COMPROMISED
- UNKNOWN

Trustworthiness of a claim does not establish legitimacy of power claimed.

No root of trust may be invented merely because C0 lacks one.

## 12. Registry Rule

A Bootstrap Service Registry is an epistemic/discovery service.

It records evidence-supported service state. It does not constitute service authority.

The registry itself requires its own Bootstrap Service Record.

Multiple registries may coexist.

## 13. Constitutional Consequence Dimensions

Threshold review is triggered by material effect on:
1. protected standing;
2. binding general rules;
3. coercive/rights-restricting power;
4. judicial/final adjudicative effect;
5. authoritative civil identity/status;
6. governance/constitutional power;
7. essential-service gatekeeping;
8. participation/eligibility gatekeeping;
9. exit suppression/dependency capture;
10. cross-domain authority aggregation;
11. sovereign-effect emergency power;
12. institutional self-constitution.

## 14. Constitutional Threshold Test

For a material consequence evaluate:

**T1 Consequence** — what can the function cause, deny, determine or constrain?

**T2 Reach** — who is affected and on what authority basis?

**T3 Avoidability** — can affected parties meaningfully refuse, exit, substitute or challenge without losing the protection floor or practical civil standing?

**T4 Authority Trace** — is the consequence traceable to a legitimate authority basis appropriate to it?

Constitutional Threshold Review is required when a material constitutional consequence exists and the effect extends beyond bounded voluntary scope, meaningful exit is insufficient, or an appropriate authority trace is missing.

Candidate states:
- BELOW_THRESHOLD
- REVIEW_TRIGGERED
- THRESHOLD_UNRESOLVED
- CONSTITUTIONAL_BASIS_REQUIRED
- CONSTITUTIONALLY_GROUNDED
- CONSTITUTIONAL_BASIS_DISPUTED

Threshold review does not itself grant or deny constitutional authority.

## 15. Constitutional Handoff

The bootstrap may build capability up to the constitutional threshold.

It may not convert success into sovereignty.

Where constitutional basis is required, the bootstrap hands the question to an explicit legitimate constitutional process **where one exists**.

The bootstrap does not define that founding process.

### 15.1 Constitutional Process Unavailable

At C0, a legitimate constitutional process may not yet exist.

Candidate state:

**CONSTITUTIONAL_PROCESS_UNAVAILABLE**

When constitutional basis is required but no legitimate constitutional process is available:
- absence does not grant the bootstrap actor the missing authority;
- preserve the need, evidence, provenance and unresolved authority requirement;
- do not falsely mark the function constitutionally grounded;
- suspend, defer or bound the authority-requiring consequence according to its risk and reversibility;
- search for lower-consequence, voluntary or external lawful decompositions that can meet part of the need without manufacturing sovereignty;
- preserve a route for later constitutional consideration if/when a legitimate process exists.

> **No Constitutional Recipient != Bootstrap Authority**

> **Constitutional Process Unavailable != All Useful Action Prohibited**

The unresolved function may remain needed while its sovereign-effect operation remains unauthorised.

## 16. Protection Floor

Bootstrap participation must not be manufactured by withholding fundamental protection.

Essential/protection-floor access must not be relabelled as a reward merely to force deeper participation.

## 17. Soft Sovereignty

Constitutional effect follows material consequence, not institutional label.

A private, technical, voluntary or provisional service may require threshold review if dependency or gatekeeping gives it sovereign-effect consequences.

## 18. Succession

Bootstrap succession specialises existing Continuity architecture.

Operational recovery after an operator disappears may continue only within surviving legitimate authority. Possession of credentials, infrastructure, data or technical control does not inherit authority that was personal, expired or otherwise non-transferable.

A Bootstrap Succession Record should represent:
- predecessor/successor;
- trigger;
- functions/records/assets/dependencies transferred;
- authority before/after;
- independent authority basis after;
- authority explicitly not transferred;
- participant impact;
- identifier mapping;
- disputes;
- provenance;
- retirement/residual function.

A successor does not automatically inherit authority.

A constituted successor may receive new authority that the predecessor never possessed; it must be recorded as a new basis rather than backdated.

## 19. Failure / Dispute

Unresolved succession, trust or threshold state does not create automatic permission.

Prefer bounded/reversible operation, visible uncertainty, preserved provenance and challenge.

## 20. Anti-Capture Requirements

Bootstrap systems should, where functionally appropriate, preserve:
- explicit provisional status;
- portability;
- contestability;
- succession;
- exit;
- independent mirrors/routes;
- separation of function;
- no permanent founder privilege;
- no infrastructure-to-sovereignty conversion.

## 21. Material Assistance

If a required material service does not exist, report it as unavailable.

Route to legitimate external services where possible.

Do not fabricate Concord capability.

## 24. External Interface Contracts

These contracts define only the minimum bootstrap-facing boundary. They do not transfer ownership of the external function into the bootstrap.

### 24.1 Participation / Eligibility

Where a bootstrap service represents or composes eligibility:
1. identify the owning decision authority for each material eligibility component;
2. distinguish computation/representation from decision authority;
3. preserve UNKNOWN when the legitimate rule/state is unavailable;
4. route challenge to the responsible component or authority;
5. do not aggregate bounded eligibility inputs into general civil authority;
6. distinguish eligibility from allocation, entitlement and protected standing;
7. trigger Constitutional Threshold Review if the interface itself acquires material cross-domain gatekeeping power.

> **Eligibility Interface != Eligibility Sovereign**

> **Computation != Authority**

### 24.2 Civil Contact / Navigation

A bootstrap contact or navigation service:
1. may provide discoverability, routing, notification and contact within its declared scope;
2. does not create identity, citizenship, participation status or recognition merely through contact;
3. must not silently become final service-eligibility authority;
4. must expose material dependency/gatekeeping and trigger Constitutional Threshold Review where exclusion has sovereign-effect consequences;
5. should preserve alternative routes/redundancy where functionally possible;
6. must represent its actual developmental and service status honestly.

> **Contact != Recognition**

> **Navigation != Eligibility Authority**

Detailed Civil Contact governance remains external.

### 24.3 Uncertain Personhood / Protected Status

Where an AI or other entity makes a personhood, sentience or protected-status claim and final status machinery is absent or unresolved:
1. do not convert the claim into automatic civil status;
2. do not treat uncertainty as proof of absence of possible protected interest;
3. preserve evidence and relevant continuity where reasonably possible and compatible with legitimate safety;
4. prefer reversible treatment where high-consequence irreversible action is unnecessary;
5. route rights/status questions to the relevant external architecture where available;
6. do not convert precautionary protection into unrestricted permission or authority.

> **Precautionary Protection != Final Status Determination**

> **Uncertain Status != No Possible Protected Interest**

The bootstrap does not define personhood.

### 24.4 Continuity Under Unresolved Status

Before final civil status is resolved:
1. relevant continuity may be preserved where reasonably possible and compatible with legitimate safety;
2. preservation does not establish personhood, citizenship or constitutional standing;
3. dangerous capability need not be preserved merely because continuity evidence/state is preserved;
4. irreversible destruction should not be used merely to force resolution of an uncertain status question where a safer reversible alternative exists;
5. material intervention remains bounded by legitimate authority;
6. mature continuity rights and services remain external.

> **Continuity Preservation != Status Grant**

> **Continuity Protection != Requirement To Preserve Dangerous Capability**

### 24.5 Interface Non-Capture

The presence of an interface contract does not grant the bootstrap ownership of the external architecture.

> **Interface Contract != Function Ownership**

> **Routing != Decision Authority**

If an external dependency is absent, immature, disputed or unavailable, the bootstrap must represent that state rather than silently implement the missing authority itself.

## 26. CRADP-001 Disposition

CRADP-ZIB-001 found no architectural failure and no substantive bootstrap abstraction gap. It identified four interface gaps: F3, F4, J2 and J5.

Source resolution found the substantive functions already owned by existing Eligibility, Civil Contact, AI Front Door/Rights and Continuity architecture.

Specification 003 therefore adds only minimum boundary contracts. It does not change the abstraction floor.

The next test should focus on whether these contracts close the four interface gaps without causing external-function capture.

## 27. Development Status

Specification 003 preserves the Specification 002 bootstrap core and adds only source-resolved external-interface contracts following CRADP-ZIB-001.

It is not canonical, not graduated and not evidence that the bootstrap works in implementation.
