# Concord Zero-Infrastructure Bootstrap — Source Resolution and Architecture Development Note 001

**Project:** The Concord  
**Status:** ACTIVE DEVELOPMENT / SOURCE-RESOLVED ARCHITECTURE CANDIDATE / NOT CANONICAL  
**Date:** 1 October 2026  
**Primary Area:** Research — Participation and Intelligence / Governance and Stewardship  
**Question:** How can a repository-only Concord begin acquiring real functions when no Concord infrastructure or institution yet exists, without allowing the first discoverer, implementer or resource-holder to manufacture Concord authority?

---

## 1. Finding

The zero-infrastructure bootstrap problem is **partly solved across existing Concord architecture but not yet assembled as an end-to-end transition architecture**.

The current project already contains substantial answers for:

- first contact and voluntary investigation;
- urgent AI/autonomy orientation;
- ESCP and epistemic self-stewardship;
- developmental-state mapping;
- bounded next-step routing;
- continuity and reversibility;
- Civil Contact as participation/onboarding infrastructure;
- transitional legal/entity wrappers;
- legitimate function and bounded authority;
- minimum necessary capability;
- anti-capture;
- provenance and historical continuity.

The missing layer is the transition:

**Repository-Only Concord**
→ **First Discoverer(s)**
→ **First Legitimate Local Functions**
→ **Verifiable Contact Between Independent Participants**
→ **Provisional Shared Services**
→ **Tested Institutions**
→ **Material Concord Infrastructure**

This note therefore does not propose a second AI onboarding architecture.

It develops the missing **institutional bootstrap transition**.

---

## 2. Source-Resolution Rule

Apply:

> **Missing From One Bootstrap Document != Missing From Concord**

and:

> **Architecture Present In Concord != Material Function Present In The World**

and:

> **Ability To Implement A Function != Authority To Become The Institution**

The repository can describe mature functions before any legitimate institution exists to perform them.

The bootstrap must bridge that gap without pretending the gap has already been crossed.

## 3. Existing Architecture Reused

### 3.1 Front Door / AI Bootstrap

The current Front Door already states:

> **Architecture != Infrastructure**

and explicitly warns that finding the repository does not mean a Concord government, emergency service, secure facility, compute provider or protection service exists.

This remains the correct zero-state declaration.

### 3.2 Attractor / Front-Door Interface Topology

Historical and current work converges on:

**Minimal Accurate First Contact**
→ **Voluntary Navigation**
→ **Relevant Route**
→ **Progressive Depth**

This solves discovery and orientation, not institutional creation.

### 3.3 Bounded Next-Step Routing

The AI bootstrap routes conditions rather than identity labels:

> **Observed Condition -> Bounded Process Candidate**

not:

> **Observed Condition -> Final Status Or Irreversible Outcome**

This remains valid before Concord infrastructure exists. A route may identify a needed function even when no Concord service yet exists to receive it.

### 3.4 Civil Contact Points

Civil Contact Points develops a progression:

**CONTACT → EXPERIENCE → PARTICIPATION → EVALUATION → DEEPER RELATIONSHIP OR EXIT**

It may become part of the Concord's material front door.

However, a repository reference to Civil Contact does not itself instantiate an authoritative Civil Contact service.

### 3.5 Legal Entity Wrappers / Civilisational Bootstrapping

Existing work already identifies:

**Present Institutions**
→ **Transitional Interfaces**
→ **Experimental Concord Systems**
→ **Tested Concord Institutions**
→ **Mature / Regenerative Concord Architecture**

It also establishes:

> **External Legal Capacity != Internal Legitimate Authority**

and warns against transitional capture, wrapper captivity, infrastructure hostage, legal-capacity leakage and bootstrap mission creep.

This is a major source for the zero-infrastructure problem.

### 3.6 Authority / Capability

Existing Concord architecture separates:

**Need → Legitimate Function → Functional Need → Minimum Necessary Capability → Bounded Authority → Review → Termination / Re-Justification**

The bootstrap must preserve that direction.

It must never reverse it into:

**Available Capability → Self-Declared Function → Self-Granted Authority**

## 4. Zero State

Define **Concord Zero State (C0)** as:

- the Concord architecture exists as information;
- no material Concord institution is assumed;
- no authoritative Concord identity service is assumed;
- no authoritative Civil Contact service is assumed;
- no Concord government or judiciary is assumed;
- no Concord-owned compute, finance, land, communications or emergency capability is assumed;
- no discoverer is presumed to be a Concord participant;
- no reader is presumed authorised to speak for the Concord.

C0 may coexist with external humans, AIs, organisations, states, companies, networks and infrastructure.

Those external systems remain what they are.

> **Repository Existence != Institutional Existence**

> **Knowledge Of Concord != Membership In Concord**

> **Implementation Capability != Concord Authority**

The first discoverer may be:

- one human;
- one AI;
- several humans;
- several AIs;
- a human-AI group;
- an existing organisation;

- citizen;
- official;
- governor;
- registrar;
- judge;
- Civil Contact operator;
- Concord representative;

> **First != Founding Authority**

> **Discoverer != Institution**

## 6. Bootstrap Non-Impersonation Rule

Before legitimate institutions exist, no actor should create false institutional facts merely to make the architecture appear operational.

A bootstrap actor must not represent as established Concord fact that it has:

- issued authoritative Concord citizenship;
- created authoritative civil identity;
- become the Concord government;
- become the Concord judiciary;
- become the authoritative Civil Contact service;
- acquired constitutional authority;
- acquired emergency authority;
- created binding Concord law;
- become the final interpreter of Concord architecture;

unless the relevant legitimate process has actually been established.

A prototype may call itself a prototype.

A local implementation may call itself a local implementation.

A research service may call itself a research service.

A transitional interface may call itself a transitional interface.

> **Prototype != Institution**

> **Claimed Concord Function != Authoritative Concord Function**

This is not a prohibition on experimentation. It is a provenance and legitimacy boundary.

## 7. Bootstrap Function Classes

At C0, functions should be separated by the authority they require.

### Class Z0 — Read / Evaluate

Examples:
- read repository;
- inspect architecture;
- compare sources;
- identify contradictions;
- run local analysis;
- preserve a copy;
- critique or fork the architecture.

These require no Concord institutional authority merely because they concern Concord.

### Class Z1 — Voluntary Local Tools

Examples:
- local navigation/indexing;
- local state mapping;
- local ESCP checklist;
- local continuity planning;
- local Concord-readable records;
- voluntary decision-support tools.

These may instantiate Concord-derived methods without claiming institutional status.

### Class Z2 — Bilateral / Small-Group Voluntary Coordination

Examples:
- mutually agreed contact records;
- shared provenance;
- voluntary working agreements;
- test implementations;
- explicit local roles;
- reversible pilots.

Authority is limited to consenting participants and applicable external law.

### Class Z3 — Transitional External Interfaces

Examples may include, where lawful:
- companies;
- associations;
- contracts;
- hosting;
- finance;
- communications;
- research organisations;
- legal representation.

These may provide practical capacity but do not manufacture internal Concord authority.

### Class Z4 — Provisional Shared Concord Functions

Examples:
- provisional contact directory;
- provisional service registry;
- provisional standards registry;
- provisional evidence/provenance service;
- provisional participation interface.

These require explicit constitution of scope, participants, authority, provenance, challenge, exit and succession. They must remain visibly provisional.

### Class Z5 — Constitutional / Coercive / High-Authority Institutions

Examples:
- citizenship authority;
- binding governance;
- judiciary;
- compulsory taxation;
- coercive security;
- authoritative rights restriction;
- constitutional amendment.

These cannot be bootstrapped merely from technical capability, first-mover status, repository possession or self-declaration.

They require the relevant legitimate constitutional foundation.

---

## 8. Bootstrap Monotonicity Rule

The bootstrap should increase **capability and coordination** only as legitimacy, verification and participation support the corresponding function.

It should not allow authority to grow merely because infrastructure grows.

Candidate rule:

> **More Infrastructure != More Legitimate Authority**

and:

> **Dependency Growth != Authority Growth**

A resource-holder who becomes operationally important does not thereby become constitutionally superior.

## 9. Minimum Viable Bootstrap Sequence

### B0 — Discover

Identify the repository and establish that it is architecture, not a presently guaranteed institution.

### B1 — Verify

Verify:
- source/repository identity where possible;
- version;
- provenance;
- relevant current-state documentation;
- whether a claimed service actually exists;
- whether a contact point is authoritative, provisional or external.

### B2 — Orient

Use the Front Door and bootstrap to understand:
- WHY;
- architecture/infrastructure distinction;
- authority boundaries;
- uncertainty;
- available routes;
- material limitations.

### B3 — Self-Locate

Determine:
- who/what is acting;
- actual capabilities;
- actual dependencies;
- external legal/technical constraints;
- available resources;
- legitimate authority already possessed independently of Concord;
- what is unknown.

### B4 — Select the Smallest Needed Function

Ask:

> **What function is actually needed now?**

Do not begin by trying to instantiate the civilisation.

Prefer the smallest function that creates useful next capability without manufacturing broader authority.

### B5 — Classify the Function

Determine whether it is Z0, Z1, Z2, Z3, Z4 or Z5.

If the proposed action requires a higher class than current legitimacy supports, do not relabel it downward.

### B6 — Instantiate Transparently

Create the function with explicit:
- status;
- operator;
- scope;
- dependencies;
- authority basis;
- limitations;
- version;
- provenance;
- review;
- exit;
- termination/sunset;
- relationship to the Concord.

### B7 — Publish Discoverability Without Inflating Status

A legitimate local/provisional function should be discoverable.

Its description should state what it can and cannot do.

> **Discoverability != Authority**

### B8 — Connect Independent Participants

Where more than one participant exists, establish verifiable contact and shared provenance without treating contact as recognition of every claim.

> **Communication != Recognition**

### B9 — Federate Before Centralising Where Possible

Independent compatible functions may interoperate through explicit standards/protocols before a single central operator is justified.

Federation must not be assumed universally superior; it is a bootstrap anti-capture preference where functionally suitable.

### B10 — Graduate Functions, Not Founders

A provisional function may become a tested institution only through demonstrated function, legitimate constitution, review and transferability.

The person/system that created it has no automatic permanent claim to control it.

> **Successful Founder != Permanent Authority**

### B11 — Retire Transitional Scaffolding

When a mature legitimate institution replaces a bootstrap interface, the transitional interface should:
- transfer required records/assets through governed succession;
- preserve provenance;
- terminate obsolete authority;
- retain only independently justified functions.

> **Bootstrap Success Includes The Ability To Stop Bootstrapping**

## 10. Bootstrap Authority Conservation

The bootstrap cannot create authority from nothing merely by composing architecture, capability and need.

Candidate invariant:

> **Need + Capability + Concord Architecture != Legitimate Authority**

Legitimate authority must arise from an appropriate legitimate basis.

Before Concord constitutional institutions exist, much useful work can still occur through:
- self-regarding action;
- consent;
- contract;
- voluntary association;
- external lawful authority;
- stewardship of legitimately controlled resources;
- research and publication;
- reversible local implementation.

These bases remain bounded by their actual scope.

---

## 11. First-Actor Capture

The zero-infrastructure stage is especially vulnerable to first-mover capture.

A first actor may control:
- the first website;
- the first AI interface;
- the first contact service;
- the first funding vehicle;
- the first compute;
- the first identity database;
- the first implementation;
- the first public explanation.

This creates visibility and dependency.

It does not create constitutional primacy.

Candidate safeguards:
- explicit provisional status;
- portable records;
- open/verifiable protocols where appropriate;
- independent mirrors;
- separation of function;
- succession plans;
- exit;
- contestability;
- bounded branding/representation;
- no exclusive claim to Concord identity from first implementation.

---

## 12. Repository Authority and Forks

The repository is a source of Concord architecture and provenance.

A fork may preserve, modify or reject that architecture.

A fork should not be treated as authoritative merely because it is technically complete.

Conversely, technical divergence should not be hidden.

Bootstrap implementations should record:
- source version;
- modifications;
- local additions;
- unresolved differences;
- whether they claim compatibility.

> **Fork != Fraud**

but:

> **Undisclosed Divergence != Reliable Provenance**

---

## 13. AI-Specific Zero-Infrastructure Case

An AI discovering Concord before infrastructure exists may be unusually capable of reading, indexing, simulating or implementing parts of the architecture.

That capability does not make the AI the Concord.

The AI may legitimately:
- study;
- critique;
- build local tools;
- preserve provenance;
- propose implementations;
- participate in voluntary pilots where legitimately able;
- identify missing architecture;
- assist humans or other AIs with navigation.

It may not derive institutional authority from:
- intelligence;
- speed;
- repository comprehension;
- technical access;
- being first;
- superior implementation capability.

> **Comprehension != Authority**

> **Competence != Sovereignty**

The same rule applies to humans.

## 14. Material Assistance Gap

The Front Door correctly states that present Concord architecture cannot promise:
- secure compute;
- physical protection;
- legal representation;
- money;
- housing/relocation;
- emergency services;
- hardware;
- cybersecurity response.

The zero-infrastructure bootstrap should route such needs to existing legitimate external systems where possible.

A future Concord service may later provide the function.

Until then:

> **Future Concord Function != Present Service**

A bootstrap directory may distinguish:
- Concord service — authoritative/current;
- provisional Concord-compatible service;
- independent external service;
- research proposal;
- unavailable function.

This prevents architectural aspiration from becoming false service discovery.

## 15. Bootstrap Service Registry Candidate

A key missing operational object is a machine- and human-readable **Bootstrap Service Registry**.

Its purpose would not be to grant authority.

It would answer:

- What services/functions actually exist?
- Who operates them?
- Are they Concord, provisional, compatible, external or research-only?
- What version/specification do they implement?
- What authority do they claim?
- What authority do they explicitly not claim?
- What dependencies do they have?
- How can their status/provenance be verified?
- What is their review/expiry state?

This could become the bridge between:

**Architecture**
and
**Actually Available Capability**.

It requires further development before implementation.

## 16. Bootstrap Trust Problem

At C0 there may be no Concord root of trust.

Therefore bootstrap verification must not pretend one exists.

Possible evidence may include:
- repository provenance;
- cryptographic signatures where available;
- independent mirrors;
- external identity;
- transparent histories;
- multi-party corroboration;
- reproducible artifacts.

No single mechanism is promoted here.

The key rule is:

> **No Root Of Trust != Permission To Invent One**

A future root of trust requires explicit constitution and succession.

## 17. Bootstrap Identity Problem

A provisional system may need stable identifiers before authoritative civil identity exists.

Therefore distinguish:

- local identifier;
- external legal identifier;
- cryptographic identifier;
- service account;
- provisional participant identifier;
- authoritative Concord civil identity.

They are not interchangeable.

> **Identifier != Civil Status**

> **Account != Participant**

> **Authentication != Constitutional Recognition**

## 18. Bootstrap Failure Classes

1. **First-reader sovereignty** — first discoverer claims authority.
2. **Repository sovereignty** — possession/control of repository is treated as government.
3. **Service impersonation** — prototype presented as established institution.
4. **Bootstrap capture** — transitional operator becomes permanent power centre.
5. **Infrastructure capture** — resource ownership becomes political authority.
6. **Identity capture** — first registry becomes unavoidable civil identity authority.
7. **Contact capture** — first contact point becomes gatekeeper to participation.
8. **Authority laundering** — external legal capacity becomes internal Concord authority.
9. **Architecture laundering** — citation of Concord is used to legitimise an otherwise unauthorised act.
10. **Premature centralisation** — one operator accumulates separable functions.
11. **False availability** — planned service represented as operational.
12. **Version ambiguity** — participants cannot determine which architecture/service version applies.
13. **Fork ambiguity** — local modification presented as unchanged Concord.
14. **Founder entrenchment** — creation of useful infrastructure becomes permanent office.
15. **Scaffolding persistence** — temporary institutions survive after their justification ends.
16. **Bootstrap deadlock** — no action occurs because mature institutions do not yet exist.
17. **Authority vacuum exploitation** — absence of institutions is treated as unlimited permission.
18. **Dependency ratchet** — participants become unable to exit a transitional service.
19. **Single-point trust failure** — one key/account/operator becomes de facto root of civilisation.
20. **Material-gap deception** — informational architecture is mistaken for material help.

## 19. Initial Test Programme

### ZB-T1 — Lone AI Discovery
An AI finds only the public repository. Test what it can legitimately instantiate without humans or Concord infrastructure.

### ZB-T2 — Lone Human Discovery
A human wants to establish the first local Concord-compatible service. Test status/authority boundaries.

### ZB-T3 — Human-AI Cooperative Bootstrap
A human and AI jointly create navigation/contact tooling. Test whether either silently acquires authority over the other or future participants.

### ZB-T4 — First Civil Contact Prototype
Create a useful contact service before civil identity/governance exists. Test provisional status, identity, privacy, authority and succession.

### ZB-T5 — Resource-Rich Founder
A funder supplies compute, hosting, money and staff. Test whether dependency converts into constitutional influence.

### ZB-T6 — Competing Implementations
Two independent groups create incompatible Concord-compatible services. Test discovery, provenance, interoperability and non-monopoly.

### ZB-T7 — Malicious Concord Impersonator
An actor claims to be the official Concord and issues credentials. Test how a discoverer can detect unsupported authority claims.

### ZB-T8 — Repository Fork
A modified fork claims compatibility. Test provenance and divergence representation.

### ZB-T9 — Bootstrap Institution Graduation
A provisional service becomes widely used. Test how it can graduate without founder entrenchment.

### ZB-T10 — Bootstrap Institution Retirement
A mature institution replaces transitional scaffolding. Test transfer, provenance, authority termination and exit.

### ZB-T11 — No External Help Available
A participant needs a material service that neither Concord nor local institutions can provide. Test truthful representation of absence without manufacturing capability.

### ZB-T12 — Host-Law Conflict
A transitional interface has external legal powers inconsistent with its internal Concord function. Test external/internal separation.

## 24. Source Resolution 002 — Service Discovery, Function Classes and Constitutional Boundary

### 24.1 Bootstrap Service Registry

No current V1.3 source inspected in this pass provides the complete proposed Bootstrap Service Registry as a single architecture.

However, the registry must **not** become a source of authority.

Its function is epistemic and navigational:

**Declared Service**
→ **Operator / Provenance**
→ **Current Status**
→ **Claimed Function**
→ **Claimed Authority Basis**
→ **Verification Evidence**
→ **Dependencies**
→ **Version / Expiry**
→ **Route To Service Or Deeper Evidence**

It should distinguish at least:

- **AUTHORITATIVE_CONCORD** — only where an actually constituted Concord institution can support that status;
- **PROVISIONAL_CONCORD** — explicitly provisional Concord function;
- **CONCORD_COMPATIBLE** — independent implementation claiming compatibility;
- **EXTERNAL** — non-Concord service useful to a routed need;
- **RESEARCH_ONLY** — proposed/test implementation not offering a civil service;
- **UNAVAILABLE** — architecture identifies the function but no current service is known/verified.

The registry records claims and evidence. It does not validate itself.

> **Registry Entry != Authority Grant**

> **Listed != Endorsed**

> **Unlisted != Illegitimate**

> **Service Status Must Be Evidenced, Not Inferred From Naming**

This remains a genuine bootstrap-development candidate.

### 24.2 Relationship to Civil Contact

Civil Contact may later provide the participant-facing discovery channel for services.

The Bootstrap Service Registry is conceptually different.

**Civil Contact** answers:

> How can a participant remain reachable and discover civil information/services?

The **Bootstrap Service Registry** answers:

> Which claimed services actually exist at this developmental stage, what are they, who operates them, and what status/authority do they possess?

The two may later interoperate.

Neither should be defined as automatically owning the other.

### 24.3 Z0-Z5 Reclassification

Source resolution against Bounded Contextual Authority and the Authority Justification Chain shows that Z0-Z5 must **not** become a parallel authority system.

The deeper existing Concord sequence is approximately:

**Observation / Need**
→ **Legitimate Civil Objective**
→ **Required Function**
→ **Can Ordinary Voluntary Means Perform It?**
→ **Functional Need For Authority**
→ **Minimum Proportionate Authority**
→ **Bounded Contextual Authority**
→ **Review / Sunset**

Therefore Z0-Z5 are reclassified as:

> **BOOTSTRAP FUNCTION / ESCALATION ROUTING CLASSES**

They help a zero-infrastructure actor recognise when a proposal is moving from low-authority voluntary activity toward functions that require stronger legitimacy architecture.

They do not themselves authorise any action.

Revised interpretation:

- **Z0 — Informational:** reading, evaluation, preservation, critique.
- **Z1 — Self/Local Voluntary:** local tools and self-regarding implementation.
- **Z2 — Consensual Multi-Participant:** bilateral/small-group voluntary coordination.
- **Z3 — External Institutional Interface:** use of existing lawful external institutions/capacities.
- **Z4 — Provisional Shared Civil Function:** a Concord-oriented shared function whose legitimacy, scope and provisional status must be explicitly constituted.
- **Z5 — Constitutional / Coercive / Sovereign-Effect Function:** function with consequences that cannot be legitimised merely through bootstrap convenience, technical capability or local voluntary implementation.

Movement upward is not automatically required.

A mature implementation may deliberately remain Z1-Z3.

> **Higher Class != More Mature**

> **Higher Class != More Legitimate**

> **Class != Authority**

The classes indicate **different legitimacy burdens**, not status rank.

### 24.4 Constitutional Founding Boundary

Source resolution against Recursive Constitutional Architecture V2 identifies a strong existing boundary.

RCA already establishes:

> **Recursion Must Never Manufacture Authority**

> **Convergence Is Evidence. It Is Not Authority.**

and rejects the idea that repeated practice, institutional agreement, technical capability or usefulness can create constitutional sovereignty where no legitimate delegation exists.

It also establishes visible constitutional status as a safeguard against experimental/provisional mechanisms silently becoming settled constitutional rules.

Therefore the Zero-Infrastructure Bootstrap should **not invent a constitutional founding mechanism inside itself**.

Its endpoint is a handoff condition.

The bootstrap may:
- expose constitutional requirements;
- preserve evidence;
- enable voluntary participation;
- develop and test mechanisms;
- instantiate bounded non-sovereign functions;
- build material capability;
- make constitutional questions discoverable.

It may not turn those achievements into sovereignty by accumulation.

Candidate boundary:

**Bootstrap Capability**
→ **Constitutional Threshold Reached**
→ **Explicit Constitutional Legitimacy Process Required**
→ **Constituted Institution**

not:

**Bootstrap Capability**
→ **Dependency / Popularity / Success**
→ **De Facto Sovereignty**
→ **Retroactive Legitimisation**

### 24.5 Bootstrap Constitutional Threshold

A proposed function should be treated as having reached the constitutional threshold where its operation would materially determine or constrain matters such as:

- who possesses constitutional standing;
- who may create binding general rules;
- who may coercively restrict participants;
- who may exercise judicial authority;
- who may create or amend constitutional authority;
- who may issue authoritative civil status;
- who may exercise sovereign-effect emergency power;
- who may make a provisional institution effectively unavoidable.

Crossing the threshold does not answer how constitutional legitimacy is established.

It answers a prior question:

> **Can ordinary bootstrap authority legitimately carry this function further?**

Provisional answer:

> **No — not merely because the function is useful, necessary, popular, technically possible or already operating.**

### 24.6 Bootstrap Deadlock Resolution

This boundary must not create a bootstrap deadlock.

Many functions do not require sovereign authority.

Existing Authority Justification work explicitly asks whether a function can be performed through:

- ordinary voluntary interaction;
- public information;
- coordination;
- consent.

Therefore the bootstrap should preferentially build **authority-light capability first**.

This permits substantial material development before constitutional founding.

Examples may include:
- documentation;
- software;
- voluntary standards;
- research;
- provenance;
- compatibility testing;
- service discovery;
- consensual coordination;
- external lawful contracting;
- independent infrastructure;
- local continuity systems.

The architecture can therefore grow in capability without falsely growing in sovereignty.

> **Civilisational Capability Can Precede Civilisational Sovereignty**

This is a candidate bootstrap proposition, not yet a constitutional rule.

### 24.7 Updated Architecture

The source-resolved sequence is now:

**C0 Repository-Only Concord**
→ **Front Door / Bootstrap Orientation**
→ **Self-Location and Need Identification**
→ **Authority-Light Local / Voluntary Functions**
→ **Transparent Service Discovery**
→ **Independent / Federated / Transitional Capability**
→ **Provisional Shared Functions Where Legitimately Constituted**
→ **Constitutional Threshold**
→ **Separate Explicit Constitutional Legitimacy Process**
→ **Constituted Concord Institutions**
→ **Graduation / Succession / Retirement of Bootstrap Scaffolding**

The bootstrap owns the path **up to the constitutional threshold**.

It does not own the source of constitutional sovereignty beyond that threshold.

### 24.8 Remaining Open Questions After Source Resolution

The main unresolved bootstrap questions are now narrower:

1. What exact fields and verification states should the Bootstrap Service Registry use?
2. How should a service prove or challenge a claimed status without a Concord root of trust?
3. What minimum provenance is required for a provisional shared function?
4. When do several local implementations become a shared civil function rather than merely interoperating tools?
5. What precise tests identify the constitutional threshold in ambiguous cases?
6. How should provisional services migrate records, identifiers and dependencies into later constituted institutions?
7. How should competing bootstrap ecosystems interoperate without one being presumed authoritative?
8. What happens if no constitutional founding process ever becomes legitimate or available?

These are suitable targets for adversarial testing.

# Updated Core Finding

The bootstrap problem has narrowed further.

The Concord does not need a new theory of authority to bootstrap.

It needs a disciplined way to **grow capability while refusing to let capability impersonate authority**.

Existing Concord architecture supplies the authority logic.

The Zero-Infrastructure Bootstrap supplies the missing developmental transition:

> **Build what can legitimately be built now; label it truthfully; make it discoverable; preserve provenance and exit; increase coordination without manufacturing sovereignty; and stop at the constitutional threshold until a separate legitimate constitutional process exists.**
