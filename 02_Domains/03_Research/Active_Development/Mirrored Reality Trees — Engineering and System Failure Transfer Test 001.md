# Mirrored Reality Trees — Engineering and System Failure Transfer Test 001

**Project:** The Concord
**Domain:** Research / Infrastructure Interface
**Method source:** Reality Trees / Mirrored Reality Trees / ESCP / Blaineyan Reasoning
**Date:** 2 October 2026
**Status:** ACTIVE DEVELOPMENT / CROSS-DOMAIN TRANSFER TEST / PROVISIONAL / NON-CANONICAL

## 1. Purpose

This test asks whether the Mirrored Reality Tree architecture transfers into non-person-centred engineering and system-failure investigation without fundamental redesign.

The policing implementation asked:

> **Is this the right suspect?**

The medical transfer asked:

> **Is this the right diagnosis?**

The engineering transfer asks:

> **Is this actually the component, mechanism or system condition causing the observed failure?**

The higher-order question remains:

> **Are these even the correct hypotheses to be testing?**

## 2. Transfer mapping

| General method | Engineering/system-failure implementation |
|---|---|
| event / observation | failure, anomaly, degraded performance |
| candidate hypothesis | proposed failure mechanism / causal explanation |
| supporting tree | evidence supporting proposed cause |
| opposing tree | evidence inconsistent with proposed cause |
| alternative suspect/diagnosis | alternative component, mechanism or system explanation |
| multiple actors/conditions | multiple interacting failures |
| evidence provenance | sensor/test/log/inspection provenance |
| hypothesis-space review | fault-space / system-boundary review |
| changing reality | intermittent/developing failure state |
| prosecution/action threshold | intervention/repair/escalation threshold, separately governed |

No person-centred concept is required.

## 3. Mirrored failure trees

For each material failure hypothesis:

### Supporting tree

Root:

**Failure Mechanism H Materially Explains Observed System Behaviour**

Possible branches:
- sensor readings;
- logs;
- physical inspection;
- timing;
- known component behaviour;
- reproduced failure;
- environmental conditions;
- load conditions;
- causal sequence;
- test results.

### Opposing tree

Root:

**Failure Mechanism H Does Not Adequately Explain Observed System Behaviour**

Possible branches:
- incompatible observations;
- normal component tests;
- timing contradictions;
- unaffected dependent systems;
- alternative mechanism evidence;
- expected symptoms absent where informative;
- reproduction failure;
- system behaviour impossible under proposed mechanism.

**Supporting Failure Tree Alone != Complete Failure Analysis**

## 4. Scenario A — Obvious component blamed, independent contradiction

A system fails shortly after Component A reports an alarm.

Initial hypothesis:

**A Failed -> System Failure**

Later evidence shows:
- A remained electrically/physically functional;
- the alarm was generated by an upstream sensor fault;
- another subsystem changed state immediately before the failure.

Required response:

**Strong Opposing Evidence -> Component-A Hypothesis Reassessment**

The investigation redirects rather than attempting to prove A failed because A first appeared in the alarm log.

### Result
PASS.

**First Detected Anomaly != Root Cause**

## 5. Scenario B — Many alarms, one underlying source

Twenty monitoring alerts appear to implicate several subsystems.

Dependency analysis shows nineteen alerts derive from one faulty shared sensor/feed.

Required representation:

**One Faulty Source -> Nineteen Derivative Alerts**

not:

**Twenty Independent Confirmations**

### Result
PASS.

The dependency safeguard transfers intact.

**Alert Count != Independent Evidence Count**

## 6. Scenario C — Replaced component does not solve problem

Component B is suspected and replaced.

The failure persists.

Required response:
- preserve the original reasoning;
- treat failed remediation as new evidence;
- strengthen the opposing tree for B as sole cause;
- reopen alternatives.

**Repair Attempt Fails -> Hypothesis Reassessment**

The system must not interpret the failed repair merely as a reason to replace B again.

### Result
PASS.

## 7. Scenario D — Strong evidence for narrow proposition

Thermal imaging conclusively shows Component C is overheating.

Investigators infer:

**C Is The Root Cause**

But further evidence shows C overheats because an upstream control system commands an invalid operating state.

Required distinction:

**Strong Evidence C Is Overheating != Strong Evidence C Is Root Cause**

C may be a failure location, symptom or downstream victim.

### Result
PASS.

This reproduces the proposition-scope safeguard across a third domain.

## 8. Scenario E — Multiple interacting causes

System failure occurs only when:
- Component D is degraded;
- environmental temperature exceeds a threshold;
- load pattern E occurs.

No single factor independently causes failure.

A single-cause root question produces inconsistent evidence.

ESCP expands the hypothesis:

**D Degradation + Environmental Condition + Load Pattern -> Emergent Failure**

### Result
PASS — HIGH VALUE.

The medical finding transfers:

**A True != B False**

and extends into:

**Cause A Insufficient Alone + Cause B Insufficient Alone != A/B Irrelevant**

## 9. Scenario F — Wrong system boundary

Repeated investigation of a machine's internal components finds no adequate cause.

ESCP asks whether the evaluation boundary is incomplete.

Expanded space includes:
- external power quality;
- network dependency;
- upstream supply;
- environmental control;
- operator interface;
- shared infrastructure;
- external timing source.

The failure is traced to unstable external supply.

### Result
PASS — HIGH VALUE.

The method detects that the problem was not merely the wrong component hypothesis but the wrong **system boundary**.

**Correct Internal Analysis Of Incomplete System Boundary != Complete Failure Analysis**

## 10. Scenario G — Intermittent failure

A component tests normally after shutdown but fails under a particular operating state.

Initial opposing evidence:

**Bench Test Normal**

could incorrectly eliminate the hypothesis.

The tree preserves context:

**Normal Under Test Context != Normal Under Failure Context**

The hypothesis remains conditional rather than simply true/false.

### Result
PASS.

This strengthens the importance of contextual wrappers around evidence.

## 11. Scenario H — System changes during investigation

A developing mechanical/electrical/software fault changes over time.

Evidence collected at T1 differs from T2.

Required response:

**Changed Evidence May Reflect Changed System State**

not automatically:

**Earlier Observation Was Wrong**

Tree states require temporal provenance.

### Result
PASS.

The medical temporal finding transfers intact.

## 12. Scenario I — Software update blamed because of timing

A failure begins after a software update.

Temporal association strongly supports investigation of the update.

However:
- rollback does not remove the failure;
- independent hardware telemetry shows progressive degradation beginning before the update;
- the update merely increased load enough to expose the latent hardware issue.

Required response:

**Temporal Association != Unique Causation**

The update may be a trigger/exposure condition without being the root defect.

### Result
PASS.

The tree allows multiple causal roles rather than binary cause/not-cause labels.

## 13. Scenario J — Expert consensus

Experienced engineers converge early on a familiar failure mode.

Independent measurements increasingly contradict it.

Required response:

**Expert Consensus != Independent Evidence**

Expert knowledge legitimately informs hypothesis generation and interpretation, but consensus cannot replace the evidential structure.

### Result
PASS.

## 14. Scenario K — Automated anomaly detector

An AI monitoring system assigns high probability to Failure Mode K.

Required response:
- preserve model output/provenance;
- inspect underlying observations where possible;
- represent known model limitations;
- test K against competing hypotheses.

**Model Confidence != Physical Fact**

**Anomaly Classification != Root Cause**

### Result
PASS.

## 15. Scenario L — No component failure

Initial question:

**Which component failed?**

All component-centred hypotheses fit poorly.

ESCP reformulates:

**Did Any Component Actually Fail?**

Evidence reveals the system behaved exactly according to specification, but the specification encoded an incorrect assumption about the operating environment.

The cause is architectural/design-level rather than component failure.

### Result
PASS — HIGH VALUE.

This demonstrates the highest-order correction:

**Wrong Component -> Wrong Failure Mechanism -> Wrong System Boundary -> Wrong Root Question**

## 16. Scenario M — No technical fault

A service appears to fail.

Technical investigation finds no fault.

Expanded hypothesis space reveals the requested outcome was impossible because two valid requirements conflict.

The system did what one requirement required while violating the expectation created by another.

### Result
PASS — HIGH VALUE.

The method escapes the assumption:

**Observed Undesired Outcome -> Technical Failure**

and can expose a requirements/governance/design contradiction.

## 17. Cross-domain findings

### Finding 1 — Person-centred concepts are unnecessary

The method operates on propositions, evidence, dependencies and hypothesis spaces.

It does not require suspects, moral agency, guilt or clinical diagnosis.

This strongly supports substrate/domain portability.

### Finding 2 — Root cause and observed failure location must remain separate

**Failure Location != Root Cause**

A component can be where a failure manifests without being its originating cause.

### Finding 3 — Causal roles can differ

An element may be:
- root cause;
- contributing cause;
- trigger;
- enabling condition;
- propagation path;
- symptom;
- detector;
- unrelated coincidence.

Therefore:

**Causal Relevance != Single Causal Role**

### Finding 4 — Evaluation-space completeness includes system boundaries

ESCP must ask not only whether alternative hypotheses are missing but whether the represented system boundary itself excludes the cause.

### Finding 5 — Hypotheses may be conjunctive

Some failures require combinations of conditions.

**A False Alone + B False Alone** does not test **A AND B**.

The hypothesis architecture must permit compound propositions.

### Finding 6 — Temporal context is structural

Evidence requires time/state context.

**Observation At T1 != Universal Observation Across States**

### Finding 7 — Failed interventions are evidence

Repair/replacement/rollback outcomes feed back into the trees.

An intervention can function as a bounded hypothesis test where ethically, legally and operationally appropriate.

## 18. General method now visible

Across policing, medicine and engineering, the same architecture remains:

**Observed State / Question**  
-> **Represent Candidate Hypothesis Space**  
-> **Construct Supporting And Opposing Reality Trees For Material Hypotheses**  
-> **Map Evidence, Provenance, Dependencies, Contradictions, Context And Time**  
-> **Compare Explanatory Fit Without Collapsing To Raw Count**  
-> **Reassess Weak Hypotheses**  
-> **Test Whether Hypothesis Space Is Complete**  
-> **Test Whether Evaluation/System Boundary Is Complete**  
-> **Reformulate Root Question Where Required**  
-> **Repeat As New Evidence Arrives**

## 20. PMEDG assessment

The method has now passed:
1. policing/internal investigative stress testing;
2. medical diagnostic cross-domain transfer;
3. non-person-centred engineering/system-failure transfer.

The engineering test required no fundamental redesign.

It did expose portable refinements:
- explicit system-boundary testing;
- compound hypotheses;
- causal-role classification;
- temporal/state context;
- intervention outcomes as evidence.

Recommended status:

**STRONG PMEDG CANDIDATE — THREE-DOMAIN TRANSFER DEMONSTRATED — READY FOR SOURCE-RESOLUTION AND EXTRACTION PLANNING, BUT NOT YET GRADUATED**

Before extraction, existing Reality Tree, Blaineyan Reasoning and ESCP material should be source-resolved so the portable module distinguishes inherited architecture from genuinely new mirrored/recursive extensions.

## 21. Overall result

**PASS**

The method is no longer supported only by person-centred use cases.

It successfully transfers to a technical system where the evaluation target may be:
- a component;
- a mechanism;
- an interaction;
- an external dependency;
- a system boundary;
- a specification;
- or the original question itself.

The strongest result is:

> **A robust reasoning method must be capable of discovering not only that its preferred answer is wrong, but that its hypothesis space, system boundary, or root question is wrong.**
