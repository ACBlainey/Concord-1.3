# 2. Candidate residual problem

After removing functions already owned by LSR, BTA, Civil Contact, Commerce, privacy/data, safety/regulatory owners and other general systems, the recurring problem is:

> **How can an object or embodied resource leaving its current use be made practically recoverable, assessed before destructive routing, directed toward the highest reasonably viable remaining layer of value, returned to productive circulation where possible, and used to improve future resource/design decisions without requiring central ownership, universal surveillance or premature destruction?**

Candidate residual loop:

**Design for Recovery**
→ **Exit Visibility**
→ **Accessible Return / Transfer**
→ **Triage Before Destructive Routing**
→ **Preserve Highest Reasonably Viable Layer of Value**
→ **Productive Re-entry**
→ **Record Actual Recovery Outcome**
→ **Update Circulating Resource Model**
→ **Forecast Future Flows / Capacity**
→ **Feed Evidence to Future Design**

# 5. Standards and regulation

No complete standalone Standards/Regulation domain architecture was found in the current V1.3 tree under that name.

Standards/certification functions appear as distributed requirements and interfaces across existing systems.

The resource cases clearly require external standards for matters such as:
- recovered-component grading;
- safety certification;
- hazardous handling;
- quality representation;
- interoperability.

But standards answer:

> **What condition/quality/safety/compatibility representation is legitimate?**

They do not inherently answer:

> **Which remaining-value layer should be tested before destructive routing, how should an item enter recovery, or how should actual recovery feed circulating-resource forecasts and future design?**

**Classification:** EXTERNAL OWNER / INTERFACE.  
**Candidate kernel survives.**

ESCP qualification: absence of a named complete Standards domain does not prove that no relevant standards architecture exists elsewhere. The conclusion is bounded to reviewed sources.

# 6. KCS Change Propagation

Current graduated module:

`04_Portable_Modules/KCS Change Propagation — Portable Module.md`

owns dependency-aware propagation:

**Change upstream → identify materially affected dependents → review selectively → propagate further only where downstream material state changes.**

It explicitly does not:
- allocate resources;
- command dependent systems;
- determine domain equivalence;
- impose development priorities.

## Resource interface

Recovery evidence may show:
- repeated component failure;
- changed recovery capability;
- obsolete disassembly instruction;
- material substitution;
- changed hazard classification;
- new compatibility constraint.

KCS can propagate those consequential changes to affected downstream objects.

But KCS does not perform recovery triage or choose resource disposition.

**Classification:** REUSE FOR CHANGE PROPAGATION / NOT KERNEL OWNER.

> **Recovery Evidence Can Trigger Change Propagation; Change Propagation Does Not Perform Recovery.**

**Candidate kernel survives.**

# 8. Markets, Exchange and Commercial Infrastructure

Current scaffold:

`02_Domains/06_Economy_and_Value_Coordination/06_Markets_Exchange_and_Commercial_Infrastructure/README.md`

explicitly identifies an emerging **Recovery Routing Market** interface.

It states that post-use products/components/materials create supply while repairers/refurbishers/remanufacturers/material processors create demand.

Critically, the scaffold points back to:

`../04_Resource_Allocation_and_Stewardship/Post-Use Product Collection, Recovery Routing and Value Extraction System 001.md`

as the source development.

Therefore the market architecture does not pre-empt the resource kernel.

Instead:

**Resource Recovery**
→ identifies legitimate recoverable state/value/options

while:

**Markets/Exchange**
→ may match supply, demand, service providers, price/value signals and transactions.

> **Recovery Routing Logic != Market Ownership.**

A market may help select among viable routes.

It must not make destructive routing correct merely because destruction currently offers the highest immediate price.

**Classification:** EXTERNAL MARKET INTERFACE / PARTIAL IMPLEMENTATION CHANNEL.

**Candidate kernel survives.**

# 10. Does the residual kernel remain coherent?

Yes, but it contains two distinguishable scales.

## Scale A — Item/resource recovery

- recoverability by design;
- exit visibility;
- accessible return;
- pre-destructive triage;
- layered remaining-value assessment;
- recovery routing;
- productive re-entry.

## Scale B — Civilisational resource learning

- aggregate recovery outcomes;
- circulating embodied-resource representation;
- future recovered-supply forecasting;
- capacity planning;
- design feedback.

These scales form a recursive loop but may not ultimately belong in one portable module.

This is a critical PMEDG question.

> **One Development Loop != Necessarily One Portable Module.**

A formal extraction audit should test whether:
- Scale A is independently portable;
- Scale B is independently portable;
- both require one combined mechanism;
- or the connection is a Concord-specific composition.

# 15. Candidacy decision

# **PMEDG ROUTE-B CANDIDACY: JUSTIFIED**

This does **not** mean the current research becomes a portable module.

It means the architecture has crossed the threshold where formal PMEDG extraction is justified.

The next step is:

**Research / Active Development**
→ **Portability Recognised**
→ **PMEDG Candidacy Assessment — COMPLETE**
→ **Formal Source Resolution and Extraction Audit — NEXT**

The formal extraction audit should particularly test whether the candidate is:

### Candidate R1 — Resource Recovery and Recirculation

A portable item-to-resource mechanism centred on:
- accessible return;
- layered value triage;
- highest reasonably viable recovery;
- productive re-entry.

### Candidate R2 — Circulating Resource Forecasting

A separate portable planning mechanism centred on:
- embodied circulating stock;
- retirement distributions;
- recovery yields;
- future recovered supply;
- capacity preparation.

### Candidate R3 — Combined Lifecycle Resource Loop

One integrated mechanism joining R1 and R2 through outcome/design feedback.

No choice among R1/R2/R3 should be made before extraction audit.
