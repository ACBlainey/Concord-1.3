# Distributed Product Return and Recovery Pathways — Adversarial Test 001

**Author:** Alexander C. Blainey — Independent Researcher  
**Project:** The Concord Framework  
**Framework Version:** Concord V1.3  
**Status:** ACTIVE DEVELOPMENT / ADVERSARIAL TEST / NON-CANONICAL  
**Date:** September 2026

---

# 1. Purpose

Test the emerging distributed product-return architecture against difficult cases.

The architecture under test proposes that multiple recovery entry routes may coexist:

- ordinary separated collection;
- civic/recycling centres;
- distributed collection points;
- retailer hand-in;
- old-for-new retailer return;
- OEM/manufacturer return;
- OEM renewal/upgrade;
- repair/refurbishment;
- trade-in;
- resale;
- donation;
- specialist hazardous recovery.

No single route is assumed to own the system.

The test asks a stronger question than:

**Does a recovery route technically exist?**

It asks:

> **Can the participant reasonably reach an appropriate recovery route from the product's actual point of exit?**

---

# 2. Candidate propositions under test

P1. Resource Stewardship != Centralised Resource Collection.

P2. Collection Interface != Recovery Ownership.

P3. Multiple legitimate return paths can coexist.

P4. Recovery accessibility is part of practical recoverability.

P5. Hand-In != Waste Declaration.

P6. OEM Responsibility != OEM Monopoly.

P7. System responsibility can mean ensuring a credible path exists rather than performing every step.

P8. Recovery-path redundancy can improve accessibility and resilience.

P9. The appropriate route should preserve the highest reasonably viable remaining value without externalising greater harm/cost elsewhere.

P10. Participant convenience can materially affect recovery participation.

---

# 3. Case A — Multiple routes for one household appliance

A participant replaces a working refrigerator.

Available routes:
- retailer old-for-new collection;
- municipal bulky-item collection;
- civic recovery centre;
- manufacturer take-back;
- private resale;
- donation.

No single route is mandatory.

**Result: STRONG PASS.**

The architecture benefits from parallel routes.

> **Multiple Valid Recovery Paths Need Not Be Collapsed Into One Preferred Path.**

---

# 4. Case B — Retailer hand-in during replacement purchase

A participant buys a new small appliance and hands the old one to the retailer.

The retailer aggregates returns and a recovery operator collects them periodically.

The retailer does not determine final material disposition.

**Result: PASS.**

Confirms:

> **Collection Interface != Recovery Ownership.**

The participant combines product replacement and product return in one journey.

---

# 5. Case C — Home delivery removes old product

A large appliance is delivered to a participant's home.

The logistics operator removes the replaced appliance on the return journey and transfers it into an appropriate recovery chain.

**Result: STRONG PASS.**

The return route is embedded in an activity already occurring.

> **Existing Forward Logistics Can Sometimes Create a Low-Friction Reverse-Logistics Opportunity.**

Whole-route efficiency must still be checked.

---

# 6. Case D — Rural participant

The nearest civic recovery centre is distant.

Retailer collection is available only in a distant town.

Ordinary scheduled separated collection accepts the product class.

**Result: PASS BECAUSE MULTIPLE PATHS EXIST.**

A centralised drop-off-only model would have failed accessibility.

> **Nominal Availability != Reasonable Accessibility.**

---

# 7. Case E — Participant with limited mobility

A participant cannot reasonably transport a bulky product.

A civic centre technically accepts it, but only by self-delivery.

Retailer pickup, scheduled collection or manufacturer pickup is required for a practically accessible route.

**Result: CENTRAL DROP-OFF ALONE FAILS.**

This strengthens:

> **Physical Accessibility Is Part of Recovery Accessibility.**

The architecture should not assume participants possess transport, strength, time or mobility.

---

# 8. Case F — OEM ceases trading

A product was designed around manufacturer take-back.

The OEM later fails.

Independent repair, civic recovery, retailer aggregation and specialist recycling remain available.

**Result: DISTRIBUTED MODEL PASS / OEM-ONLY MODEL FAIL.**

> **A Product's Recovery Path Should Not Necessarily Depend on the Continued Existence of Its Manufacturer.**

This is a strong argument for pathway redundancy.

---

# 9. Case G — Local retailer stops accepting returns

The participant still has civic collection, OEM postal return and independent repair/resale routes.

**Result: PASS.**

Redundancy prevents a local interface failure becoming a lifecycle dead end.

---

# 10. Case H — All convenient routes disappear

A product is theoretically recyclable, but the only accepting facility is hundreds of kilometres away and no collection service exists.

**Result: PRACTICAL RECOVERABILITY FAILURE.**

> **Theoretically Recoverable != Practically Recoverable.**

This extends the existing rule:

**Theoretically Recoverable != Operationally Recoverable.**

Operational capacity and participant access are separate constraints.

---

# 11. Case I — Working product handed into recycling centre

A functioning device is surrendered because the participant no longer needs it.

The facility automatically shreds all received devices.

**Result: FAILURE.**

Hand-in must not automatically classify an object as material waste.

> **Hand-In != Waste Declaration.**

Triage should test higher-order remaining value where proportionate.

---

# 12. Case J — Broken product still repairable

A participant believes a product is worthless.

Assessment finds a minor replaceable component failure.

Repair/refurbishment has greater whole-route value than material recovery.

**Result: PASS IF TRIAGE EXISTS / FAIL IF AUTOMATICALLY RECYCLED.**

Participant perception of value need not establish actual remaining value.

---

# 13. Case K — OEM upgrade programme

A durable device is returned to its manufacturer.

The structure, housing and mechanical system remain sound.

The OEM replaces the control electronics, battery and communications module, tests the product and returns it to the participant.

**Result: STRONG PASS.**

Confirms:

> **New Function Need Not Always Require a New Whole Product.**

and:

> **Product Lifetime and Component Generation Need Not Be Identical.**

---

# 14. Case L — OEM uses stewardship to block independent repair

Manufacturer claims that because it is responsible for recovery, only authorised OEM channels may repair or reuse the product.

Independent repair is safe, competent and legitimate.

**Result: REJECTED.**

> **OEM Responsibility != OEM Monopoly.**

Resource stewardship does not itself establish exclusive control.

---

# 15. Case M — OEM refuses end-of-life product

A manufacturer designed and sold a difficult-to-recover product but offers no return route.

Independent recovery is expensive and civic systems bear the burden.

**Result: RESPONSIBILITY GAP DETECTED.**

The architecture can represent the failure, but the appropriate legal/economic producer-responsibility rule belongs elsewhere.

This is an interface requirement, not authority for this architecture to invent liability.

---

# 16. Case N — Imported product with no domestic OEM

The original manufacturer has no local recovery infrastructure.

Retailer return, civic collection and independent specialist recovery remain possible.

**Result: DISTRIBUTED MODEL PASS.**

Possible producer/importer responsibility requires later Commerce/Law treatment.

---

# 17. Case O — Hazardous product offered through ordinary collection

A product contains a damaged hazardous battery.

Ordinary refuse collection is convenient but unsafe.

**Result: ORDINARY CONVENIENCE OVERRIDDEN.**

> **The Easiest Route Is Not Necessarily a Legitimate Route.**

Accessibility must remain bounded by safety and other independent requirements.

---

# 18. Case P — Data-bearing computer

A participant hands in an old computer through a retailer.

The hardware is suitable for reuse, but storage contains personal data.

**Result: PASS ONLY WITH DATA-CUSTODY/SANITISATION INTERFACE.**

> **Physical Return != Consent to Transfer Personal Data.**

Convenience must not erase privacy.

---

# 19. Case Q — Low-value bulky product

A large low-value product costs more to transport than the recoverable material is worth.

A distant specialist route exists.

**Result: WHOLE-ROUTE ASSESSMENT REQUIRED.**

The architecture must not equate recovery with stewardship automatically.

Local dismantling, aggregation, alternative use or bounded disposal may be better.

> **Recovery Route Value Must Include the Cost and Externalities of Reaching the Route.**

---

# 20. Case R — Tiny low-value products

Individual collection trips would be disproportionate.

Participants accumulate suitable items and return them during ordinary shopping or scheduled collection.

**Result: PASS.**

Aggregation can reduce recovery friction and logistics cost.

---

# 21. Case S — Deposit/return incentive

A product class has a modest return deposit.

Return rates increase.

**Result: REPRESENTABLE / NOT UNIVERSALLY REQUIRED.**

Incentives can lower perceived return friction, but this architecture does not establish a universal deposit regime.

---

# 22. Case T — No financial incentive but very easy return

Old product is collected automatically when replacement is delivered.

Participation is high despite no payment.

**Result: STRONG PASS.**

This demonstrates that participant behaviour is influenced by more than monetary incentive.

> **Convenience Can Function as a Recovery Incentive.**

---

# 23. Case U — High reward creates perverse behaviour

A recovery payment exceeds legitimate recovery value and encourages unnecessary product retirement or fraud.

**Result: FAILURE OF INCENTIVE DESIGN.**

> **Recovery Incentive Should Not Become Premature-Retirement Incentive.**

---

# 24. Case V — Donation/reuse route

A participant no longer needs a functioning product.

A local reuse organisation can place it with another participant immediately.

Formal recycling would recover only materials.

**Result: REUSE ROUTE PREFERRED WHERE OTHERWISE LEGITIMATE.**

Distributed architecture should preserve non-industrial reuse paths.

---

# 25. Case W — Recovery network capacity shock

A large product cohort reaches retirement earlier than forecast.

OEM and civic facilities become temporarily saturated.

Retailers can still collect but storage capacity is limited.

**Result: PARTIAL FAILURE / RESILIENCE BENEFIT FROM MULTIPLE ROUTES.**

The resource forecast and capacity-planning architecture should detect concentration risk.

Path redundancy helps but does not create infinite capacity.

---

# 26. Case X — Duplicate routing information

Participant receives conflicting instructions from OEM, retailer and civic system.

One says recycle, another says return to manufacturer, another classifies the product as hazardous.

**Result: INTERFACE FAILURE.**

Multiple paths should increase choice without making legitimate routing incomprehensible.

> **Pathway Diversity Requires Routing Clarity.**

A product/resource information layer may expose currently valid route options without forcing one universal operator.

---

# 27. Case Y — Recovery route exists but participant does not know it

A free local collection service exists, but return information is absent from product documentation and retailer interfaces.

Product enters general waste.

**Result: ACCESS FAILURE.**

> **An Unknown Recovery Path Is Not Fully Accessible in Practice.**

Accessibility includes discoverability.

---

# 28. Case Z — Participant deliberately chooses lawful disposal

Several recovery routes exist, but participant chooses an independently lawful disposal route.

**Result: AUTHORITY BOUNDARY.**

This architecture does not itself create power to compel a different choice.

Any mandatory treatment for hazardous/scarce materials requires independent legitimate authority.

> **Recovery Architecture != Automatic Compulsion Authority.**

---

# 29. Case AA — Product changes hands repeatedly

A product is resold several times.

The final owner has no original receipt or manufacturer account.

A recovery route remains available using product class/identity rather than original purchaser identity.

**Result: PASS.**

> **Recovery Eligibility Should Not Unnecessarily Depend on Original-Purchaser Continuity.**

This is particularly important for durable products.

---

# 30. Case AB — Manufacturer learns from returns

OEM observes that one inexpensive bonded assembly causes most end-of-life material loss.

Next generation is redesigned with a replaceable/separable assembly.

**Result: STRONG PASS.**

Confirms:

> **The Returned Product Is Also Evidence About the Product That Was Designed.**

---

# 31. Case AC — Too many routes create fragmentation

Every retailer, manufacturer and municipality uses incompatible categories, labels and handoff records.

Participants have many choices but recovery operators face high interoperability cost.

**Result: FAILURE MODE DETECTED.**

Distributed operation benefits from common interfaces where appropriate.

> **Standardise the Interface; Preserve Legitimate Pathway Diversity.**

This aligns with existing Concord contextual-wrapper principles without making the wrapper architecture owner of recovery.

---

# 32. Case AD — One mandatory route removes useful alternatives

A central system requires all products to enter one recovery facility.

Direct reuse, repair, OEM upgrade and local refurbishment become impossible or uneconomic.

**Result: REJECTED.**

> **Centralisation Can Destroy Recovery Value as Well as Create Efficiency.**

---

# 33. Accessibility dimensions

The test shows that recovery accessibility is multidimensional.

A route may be technically available but inaccessible because of:

- distance;
- transport requirement;
- mobility;
- opening times;
- cost;
- packaging/shipping burden;
- lack of information;
- digital-access requirement;
- product size/weight;
- hazardous handling;
- data/privacy risk;
- eligibility restrictions;
- retailer/OEM account dependence;
- capacity saturation.

A provisional representation is:

`RecoveryAccessibility = <RouteExists, Discoverability, PhysicalReachability, CostBurden, TimeBurden, HandlingBurden, Eligibility, SafetyCompatibility, DataCompatibility, CapacityState>`

This is not intended as a universal score.

It is a checklist against false claims of practical availability.

---

# 34. Recovery friction

A useful qualitative concept is **Recovery Friction**.

Recovery friction is the burden between:

**Participant Decides Product Should Leave Current Use**

and

**Product Successfully Enters a Legitimate Next Path.**

Possible friction sources:
- extra journey;
- booking;
- fees;
- transport;
- unclear instructions;
- packaging;
- account requirements;
- waiting;
- limited opening;
- incompatible collection rules.

The architecture should seek to reduce unnecessary friction without erasing legitimate safety, privacy, ownership or certification requirements.

> **Low Friction Is Desirable; Unbounded Friction Removal Is Not.**

---

# 35. Redundancy

The test supports a bounded redundancy principle:

> **Recovery-Path Redundancy Can Increase Accessibility and Resilience.**

But redundancy is not automatically valuable.

Duplicated routes may be wasteful where they add cost without meaningful:
- accessibility;
- resilience;
- specialisation;
- competition;
- recovery quality.

Therefore:

> **Pathway Redundancy Should Be Function-Justified, Not Duplication for Its Own Sake.**

---

# 36. Emerging topology

The stronger topology is now:

**Participant/Product Exit Event**
→ **Discover Available Legitimate Paths**
→ **Participant Selects / Appropriate Process Directs**
→ **Accessible Collection Interface**
→ **Aggregation / Reverse Logistics where useful**
→ **Triage**
→ **Highest-Value Reasonably Viable Safe Route**
→ **Reuse / Repair / Upgrade / Refurbish / Repurpose / Component Recovery / Material Recovery / Residual Treatment**
→ **Recovered Resource / Continued Productive Use**
→ **Resource Inventory / Forecast Evidence**
→ **Design and Capacity Feedback**

Multiple entry paths may feed the same downstream recovery processes.

Multiple downstream operators may also coexist.

# 38. Overall result

**RESULT: PASS WITH MATERIAL REFINEMENT.**

The distributed-return model survives the adversarial test.

The strongest refinement is that practical recoverability requires more than a technically valid downstream process.

A resource can be:
- theoretically recoverable;
- operationally recoverable;
- yet not practically recoverable from the participant's actual context.

Therefore the architecture should distinguish:

**Theoretical Recoverability**
→ **Operational Recoverability**
→ **Participant-Accessible Recoverability**
→ **Actual Recovery**

The test also supports a multi-path model.

No evidence currently justifies one universal return route.

Instead:

> **The Objective Is Not to Route Every Product Through the Same System; It Is to Make an Appropriate Next Route Reasonably Easy to Reach.**

This remains domain-level development. It does not yet establish a new portable module.
